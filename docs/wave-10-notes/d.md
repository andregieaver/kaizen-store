# Wave 10 unit D: discount combinations (D367)

## Decision row (for `docs/decisions.md`)

| D367 | **Discount combinations between campaigns and codes (wave 10 unit D, `docs/wave-10-must-haves.md` section 4, D); built.** An owner says whether a campaign combines with discount codes (`campaigns.combines_with_codes`, the campaign editor's *Can be used with discount codes*) and whether a code combines with campaigns (`discount_codes.combines_with_campaigns`, the code editor's *Can be used with campaigns*, beside its combinations with other codes of D299 E2); both are on by default, so every existing campaign and code behaves as before (campaigns first, codes count what they leave). Where they do not combine, the basket takes whichever saves the shopper more, decided once by `campaignsAndCodes()` (`src/server/discount-combinations.ts`, pure rules in `src/lib/discount-combinations.ts`) for `cartSummary()` and `placeOrder()` alike: (a) every campaign, with the codes they let in (`codeRuleFor()`: `any` while no campaign gives the basket anything, `combining` while every campaign that gives combines with codes, `none` once one does not), or (b) the codes as they would be used with no campaign, with only the campaigns that combine with codes, or none at all when a code used does not combine with campaigns (`evaluateCampaigns()`' `leaveOut`). The saving counts the campaigns' lines, a free product's worth and shipping made free, the codes (shipping included) and what the group's discount (D108) and the friend's welcome discount (D131) then take, each by the caller's own arithmetic (`AfterCampaigns`); the codes win only when strictly more and a code is used at all (`codesWin()`), a tie keeps the campaigns. The alternatives are evaluated only when a code on the cart is kept out by the campaigns, so a basket without such a conflict costs one evaluation as before. The group's discount, the welcome discount and bonus credits keep their order (after the campaigns, before the codes; credits last); `placeOrder()` now reads the basket's delivery, the group's discount and the friend's state before the campaigns, so a checkout rule's refusal, unanswered questions or no shipping are said before a stock problem. The loser is said, never hidden: a code kept out is refused as `with_campaigns` (`m.codeProblems.with_campaigns`, never `alone`, so it does not stop the checkout), a campaign left out is `cartSummary().campaignsLeftOut`, said in the cart with `m.campaignNotWithCode` (both by hand in nb, sv, da and en). At checkout a code typed on the waiting order is let through when only the order's campaigns keep it out (`checkCodeForOrder()`), since placing the order again weighs it, and the order's codes are shown with the rule its campaigns set (`stackOnOrder()`, from the lines' `campaign_parts` and `campaign_shipping`). The AI manager's `create_campaign` and `create_discount` take `combines_with_codes` and `combines_with_campaigns` (on unless said; the approval names it), and `list_campaigns`/`list_discounts` say which do not. A store's copy carries both (`duplicate_store()` patched in place); `clone_store()` copies no campaigns or codes. Scenarios in `checkout-kinds.int.test.ts`, in kroner and shown in euro: a non-combining code where the campaign gives more, where the code gives more, a campaign that does not combine with a combining code that gives more (a combining free product staying), both combining, and a non-combining campaign that gives more for a group member; cart and order agree to the minor unit and the order keeps the code only when the cart used it. `customers.automatic-discounts` moves to full. Migration versions: `20261028153829_discount_combinations`, `20261028154037_discount_combinations_copy`. |
