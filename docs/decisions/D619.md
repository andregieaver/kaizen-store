# D619: A cart or checkout render works the basket out once, and asks nothing of a feature that is off

**A cart or checkout render works the basket out once, and asks nothing of a feature that is off (bloat review step 0.22; 15 November 2026; D618 is the other session's, cited in its commit 9f468db2).** `requestCartSummary(store, market)` holds the cart and its summary for one render (`perRequest`, key `cart-summary:{storeId}:{market}`), read by the cart page, the checkout's credits and its delivery choice; server actions still call `cartSummary()` themselves, reading after they write.
`getCustomer()` is read once a render (key `customer:{storeId}:{sha256(token)}`, so a new session token reads again), as are the cart link's count and a product page's stock.
`cartSummary()` given the store's features skips `bonusProgram()` with Bonus off (`bonusProgramOff()`) and the friend's state with Referrals off: the same answers, since the program and the referral program are off in the database whenever their feature is (`commerce.bonus_program_on()`, `affiliate_program_on()`), and `cartBonusOff()` is the one 'off' object. Production: the cart and the checkout show the same totals.
The checkout rules' own cache was left out: `cacheLife()` throws outside Next in the integration tests that reach `cartSummary()`; it waits for a next/cache stub in the integration config. Kaizena Flow sells plans through Stripe, with no cart, so nothing applies there. No migration. Commits f4a3ce81, 89f5459d.
