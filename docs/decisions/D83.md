# D83: A store's All products page, at /products, can be one of its own pages built in the page builder, as its front page can; a product grid can offer shoppers Filter and sort, and follows each choice while the dialog is open

**A store's All products page, at /products, can be one of its own pages built in the page builder, as its front page can; a product grid can offer shoppers Filter and sort, and follows each choice while the dialog is open.** The page is chosen on the Pages list (`stores.products_page_id`, kept to the store's own pages and let go when deleted; not the front page too), marked All products page there, served at `/products` with its own title and search texts while published (its own address leads
there, and sitemaps leave it out), and product pages' back link returns to it by its title in the market's language. New stores get the template's, a heading and every product in a grid with Filter and sort.
A content grid of the store's own products can have Filter and sort (`ContentGridBlock.filters`): on the site it shows the listing's controls (D78, `ListingControls`: count, dialog, chosen filters) over the grid and reads the choices from the address (`GridPlace.listing`), per request, with the grid as set as the prerendered stand-in.
Listings are now live (the search page aside, whose searches are logged): each choice in the dialog goes to the address a moment after it is made (typing waits for a pause), so the products behind the dialog follow, seen beside it on larger screens and counted in it; closing keeps the choices.

Date: 2026-09-28

Asked for by the owner. The same pattern as the front page (D54) keeps it one editor and one way of choosing; the address stays the one menus and search engines know. Following choices through the address keeps filtered lists shareable and server-rendered (prices as shown to the buyer, stock), and one set of controls serves the listing pages and grids. The search page stays apply-to-show, as every change there would be a new search.
