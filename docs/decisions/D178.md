# D178: Store features

**Store features: a master switch for the online shop and a switch per feature, so an owner sees only what the store uses (step 1 of 6: foundation and the Features page).** `docs/store-features.md` is the contract.
Features (`src/lib/store-features.ts`): `shop` (off: a website), Selling (`subscriptions`, `boxes`, `appointments`, `bookings` = stays, rentals and hosts), Countries and languages (`countries`, `languages`, `currencies`), Customers (`business`, `bonus`, `referrals`, which needs `bonus`); Selling, Customers and currencies need the shop.
`stores.features` keeps what the owner switched on; a feature is on with everything it needs (`featureOn()`, `commerce.feature_on()`), so its switch is remembered while the shop is off. Existing stores keep on what they use (backfill); new stores from the template start with the shop alone, a store template's copy and a duplicate keep the source's. `stores.modules`' `bookings` and `deliveries` follow the features both ways (`stores_features_sync()`).
Only owners switch (`setFeature()`), audited as `store.feature`; switching off is refused while customers would be hit (running subscriptions and box lists, bookings to come, unpaid host commissions, unsent paid goods for the shop, subscriptions or lists abroad for countries) and confirmed over warnings (credits held, referrers, VAT numbers in carts, extra currencies and languages). Nothing is deleted.
Step 1 gates the navigation, the admin map, the AI manager's tools (`TOOL_FEATURES`) and the gated pages (`FeatureOff`); hiding inside pages, the storefront, server enforcement, website mode and onboarding are steps 2 to 6. The Features page is read by every member who may read the settings (was owner-only).

Step 6 (onboarding, `docs/store-features.md` 4f, no migration): the setup wizard asks "What will you sell?" first (products to ship, downloads, appointments, stays or rentals, subscriptions, subscription boxes, or just a website; several countries, several languages, sell to businesses); `featuresForAnswers()` maps the answers and `answerFeatureQuestion()` applies them through `setFeatures()` (the whole set in one transaction, owners only, needs, blockers and confirmed warnings as on the
Features page, each switch audited `store.feature` with `via`), the bonus and referral programs keeping their switches; the answer is known from one `store.features_chosen` activity entry, never stored apart. The wizard's steps follow the features (`setupStepsFor()`: no payments or products for a website, which opens with its details and country alone; a bookings step while appointments or stays are on), and so does `setup_progress`.
A store template's features are set on its platform page (`setStarterFeatures()`), reach new stores through the next Publish, and show on the cards (*Starts with: …*); a store made from one gets the question pre-filled. New stores from the default template keep the shop alone. The AI manager has `list_features` (read-only) and `set_feature` (gated `public`, the approval written from the registry with the store's warnings, which are kept with the call and must be unchanged at the yes).
