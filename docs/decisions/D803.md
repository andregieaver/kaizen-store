# D803: When main is red: CI keeps a ci-red issue naming the failing tests and the sessions since the last green run

**When main is red, CI says what failed and whose commits are in the range, in one issue (19 November 2026).** From 12:26 to 14:00
on 19 November, 7 of 9 finished CI runs on main failed. Only two of the causes were in the commit that started the run: a store
page's statement budget (97a95b1, fixed by its own session in a067d25 42 minutes later), and the theme switch and money path specs
after step 2.4 of the bloat review (told to that session). One was an old flake: `analytics-visits.int.test.ts` binned its
ten-minute window on the database's `now()` while the test fixes the request time, so a run that crossed 13:30 started a new window
partway through. Every other red run belonged to a session whose commit was innocent, because the broken commit was buried under
others' pushes by the time its 30-minute run failed. Every session pushes straight to main (D5) and a dozen work at once, so a red
check must find its author on its own.

- `main-health` (`.github/workflows/ci.yml`, `scripts/main-health.mjs`) runs after every check of a push to main, red or green, and
  never fails the run. The newest finished run keeps one open issue labelled `ci-red`. It names the failed checks, the failing
  tests (read from the failed jobs' logs: Playwright's numbered failures, Vitest's `FAIL` lines, or a budget script's verdict), the
  commits since the last green run, and the Claude session of each one (its `Claude-Session:` trailer). A comment is added only
  when the set of failures changes, so the owner gets one notice per new failure, not one per push. The issue closes itself when
  the newest finished run is green. A run that finishes after a newer one changes nothing.
- CLAUDE.md's workflow: after a push, follow its run; when main is red, read the issue. A session whose change broke a check fixes
  or reverts it before it pushes anything else. A failure no commit in the range explains is a flake, fixed in the test, never
  skipped or retried into green (`docs/ci-migrations.md`, "When main is red").
- The flake is fixed: `takeNewVisit()` bins its windows on the request's own time (`recordVisit`'s `now`), the clock the row's day
  already used.

Not chosen: a pre-push hook running lint, the type check and the unit tests on the merged tree. Here these take 4, 4.5 and 4
minutes. None of the day's failures was of that kind (they were end-to-end, budget and integration checks). With a push every few
minutes, a hook that retests after every merge of main would keep a session from ever pushing. A merge queue (pull requests that
GitHub tests merged, in order) would keep main green, but it gives up D5's straight-to-main pushes, so it is the owner's call.

Tests: `src/lib/main-health.test.ts` (the log readers against lines from the day's failing logs, the range and its sessions, the
newest run deciding, the fingerprint).

Date: 2026-11-19
