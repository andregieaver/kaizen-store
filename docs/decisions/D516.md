# D516: Workflows on Kaizena Flow's own events

**Workflows on Kaizena Flow's own events (C4 step 3 of `docs/platform-parity-plan.md`, 9 November 2026, `commerce.platform_workflows`, `commerce.platform_workflow_runs`, `src/lib/platform-workflows.ts`, `src/server/platform-workflows.ts`, Platform → Settings → Workflows).** The owner: *continue* (C4's steps 3 and 4).
A store's workflows (D356) for the platform: a trigger is one of the platform's events (D465: a store requested, made or opened, a plan started, changed, cancelled or not paid, a notice of illegal content) or a schedule in Oslo's time; conditions test the event's fields as its endpoints get it (`platformPayload()`, D515: the store's country, the plan's name, price, interval and status, the language of a request, a notice's category); the actions are the platform's: *Email staff* (to the
platform's owners), *Post to Slack* (its channel, `postPlatformSlack()`) and *Send to an endpoint* (one of its own, D515).
Separate `platform_*` tables on D465's model, as D515's; `queue_platform_event()` now also queues a run for each workflow that is on and starts with the event, once per event and transaction and `capped` past 100 an hour, as `queue_integration_event()` does a store's; `runPlatformWorkflows()` runs them every minute in the integrations job, a failure there never holding the stores' back.
Saved off, tested on the latest event of its kind, then switched on: the database refuses a workflow on whose version was not tested, strictly (`coalesce(tested_version = version, false)`; the stores' check passes a workflow never tested when it is switched on in SQL, as a NULL passes a check, which their server code guards, and is left as it is).
The store's editor, checks and words are shared through a kit of triggers, fields and actions (`WorkflowKit`: `STORE_WORKFLOWS`, `PLATFORM_WORKFLOWS`; the editor's `scope`). A platform owner makes them (the settings area, D510); every role reads. **Next (C4 step 4):** an Admin API scope for the platform's own tools.
