# D825: Crawlers get the cached page; only link previews keep the blocking render

**Crawlers get the cached page; only link previews keep the blocking render (bloat review step 2.5; 19 November 2026).** Next
renders every page per request, static ones included, for the user agents on its `htmlLimitedBots` list, so their metadata is in
the head. Our prerendered pages already hold title and description in the head (`scripts/render-modes.mjs` checks it), so
`next.config.ts` sets the list to link-preview fetchers only (Facebook, Twitter, LinkedIn, Slack, Discord, WhatsApp, Skype,
Reddit, Quora, VK, Tumblr, Bitly), which never run scripts and come once per shared link. Bing, Apple, Yandex, Google's shop and
ads fetchers and Meta's catalogue now get the cached page, as Googlebot always has. `e2e/crawlers.spec.ts` holds it. On
production on 19 November, a Bingbot request for a demo product page and front page was answered from the cache (HIT) with title
and description in the head, and the docs site's front page prerendered; facebookexternalhit still gets a fresh render (private,
no-store). The owner checks Google's Rich Results Test and Bing Webmaster Tools, and a day's runtime logs are sampled for crawler
renders. Commit 51234b9bd.
