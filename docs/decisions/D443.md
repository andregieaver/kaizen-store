# D443: The docs' search and filters

**The docs' search and filters (wave 14 unit E3, `docs/wave-14-developer-platform.md` E3); built.** *The index:* `commerce.docs_index` (SQL only, as `knowledge_chunks`: its vector is a type of another schema; RLS on, no policy) holds one row per part of an article (its start, the summary and the words before the first heading, then each `##` and `###` with the words below it, a `####` staying in its part) and of the changelog, and one per reference item of unit A's contracts (each `ADMIN_API`
operation, `WEBHOOK_TOPICS` topic, owner MCP tool, shopping agent's tool, error code and Admin API scope, `src/lib/docs-reference.ts`): track, kind, item, areas, features, plans, language, section, the address with its anchor, title, headings, code, summary and words, a `tsvector` stemmed by the row's language through `commerce.search_config()` (english, norwegian; the title weighs A, headings and code B, words C), the same unstemmed (`words`, for a word's start while it is typed), trigram text
of the title, headings and code (`trgm`, pg_trgm, already in `extensions`; a GIN `gin_trgm_ops` index) and an embedding with its model's `space`, as the chat's knowledge (D81).
`docsIndexRows()` (`src/lib/docs-index.ts`, pure) makes the rows from the compiled docs and the contracts; `refreshDocsIndex()` (`src/server/docs-search.ts`), in the five-minute dispatcher (`docsIndex`), compares the sha256 of their fingerprint with `commerce.docs_index_state` and rewrites the index in one transaction under an advisory lock when it moved (after a deploy that changed an article, a contract or how rows are made), keeping a row's vector while its words (`text_hash`) are the same
and removing the rows no longer made; then it gives up to 256 rows a run vectors from the platform's AI (AI feature `docs_search`) while it has an embedding model. A search that meets an empty index writes it first (the minutes after the first deploy, a fresh database, CI's browser tests).
Until the generated reference (E4) has pages, a reference item leads to the article whose front matter names it (`operations`, `tools`), else to the developers' overview's part about its kind (`REFERENCE_PAGES`, held to real headings by a test). *Search:* `searchDocs()` alone, through `GET /api/docs/search?q=&track=&kind=&area=&lang=&section=&sort=&cursor=` (filters comma-separated, an unknown value or order left out, a cursor that is not one a 400) and the search page.
Keyword: every word (`websearch_to_tsquery` in each row's language, OR'd with the synonyms' alternatives, `expandQuery()` over the reviewed `DOCS_SYNONYMS`: VAT, MVA, moms, merverdiavgift; quote, offer, tilbud, quotation; shipping, frakt; refund, refusjon; stock, lager; and a few more, both ways), a word's start while typing, or a title, heading or code within pg_trgm's word similarity 0.5 of what was typed; scored by `ts_rank`, a heading holding the words leading to that heading and a title
holding them to the page's top, an exact title or code first, reference items weighed 0.8 against articles; when no part has every word, the parts with some (said as such).
Meaning: with the platform's embedding model, the 40 closest parts within 0.1 of the closest and above its `minSimilarity` (a vector waits 3 s at most, else words alone); the words searched go to the platform's embedding model for their vector, as a shopper's do in a store's search by meaning (D74), and are kept nowhere but the gap list's count.
The two lists are merged by reciprocal rank (`fuseRanks()`, k 60, as `searchKnowledge()`), parts grouped into documents at their best part, filtered (any value within a filter, every filter across), each filter's values counted with the others applied and not its own (`facetCounts()`), ordered by best match (the docs' reading order without words), recently checked (the reference last), A to Z or most read, and paged by 20 with a keyset cursor of the last document's place.
The answer says how the words matched, whether meaning took part, how many documents the words found before the filters (`found`) and after (`total`). *On the page:* the top bar's search is a link to the search page until its script runs, then a button opening a `<dialog>` as a modal (⌘K, Ctrl+K and `/` say `DOCS_SEARCH_EVENT`): it searches as the reader types (200 ms), starts within the page's language and, on a track's page, that track (two chips, one press each to take away), shows *For*
and *Language* with their counts and the kinds, topics and orders under *More filters*, each result with its track, section (or what kind of reference item) and heading, its code, its words with the search's marked (text, never HTML) and its kind; ↓ from the field to the results, ↑ and ↓ between them, Enter opens one (in the field, the first), typing goes back to the field, Esc, the close button or a click outside closes it and the focus goes back; the count is said politely.
`/docs/search` (`/search` and `/no/search` on the docs' host, `docsHostRoutes()`) draws the same panel with the search done on the server (`instant = false`: no static shell and no streamed part, which would need a script to show), so it works without JavaScript: the form submits there with its filters, and every chip, order and *Show more* is a link there, which a plain click with JavaScript follows in place (keeping the address in step).
The dialog's *Open this search as a page* is the address to share. `noindex`, and disallowed in the docs' host's `robots.txt`. A section's page lists its kinds and topics with their counts and the four orders as links to the search page with the section as a filter (`DocsSectionFilters`, counted at build by the same `facetCounts()`), so a section stays prerendered.
A search that finds nothing offers the whole docs when filters hid it, else tips, says it is counted, and offers the AI guide with the question filled in only once the guide exists: the hand-over is `DOCS_ASK_EVENT` with `{ question }` in the dialog and `/docs?ask=…` (`docsAskSub()`) on the page, shown while `DOCS_GUIDE_READY`, which unit E5 sets.
Words in `platformText(lang).docs.finder`, English and Norwegian (the chrome scan holds the new components). *Counts, nothing about the reader:* a search that found nothing in the docs at all (`found` 0) is counted for the gap list (`commerce.docs_search_misses`: the words as `missQuery()` reads them, never an email address, a long number (seven digits or more, as a phone's or an order's), or a token; the language; how often; first and last seen) by the dialog once it has stood 1.5 s
(`POST /api/docs/search/miss`, `sameSite()`, budget `docs_miss`) and by the search page when it draws one; a page read is counted for *Most read* (`commerce.docs_reads`, a count per page, language and day) by `DocsReadCount` with `sendBeacon`, never under Global Privacy Control or Do Not Track (`POST /api/docs/read`, `sameSite()`, budget `docs_read`, a page the docs have); one reader's same search or page counts once an hour, by a counter in `chat_usage` keyed by the budgets' daily hash of their
address and a hash of what was counted (gone after two days). Reads count 90 days and are then forgotten, misses after 180 days unseen. Platform → Docs feedback lists the misses of the last 90 days, the most often first, each to try or take off the list (audited with its language and count). Both tables in `NOT_PERSONAL`.

*Why the index is rows made from code and a fingerprint, not a build step:* the deployed files and contracts are the build's, the cron already runs every five minutes and reads them at no cost, and a fingerprint of the rows themselves moves with any change to an article, a contract or the way rows are made, so nothing has to remember to rebuild it. *Why the API has no same-site rule:* it is a read that changes nothing, as the neighbouring public reads (the domain search, D315; *Show more
reviews*; the storefront and shopping agents' APIs) have none, and the docs are meant to be searched by tools (E5's guide, AI tools reading `llms.txt`); what writes (misses, reads) is a POST of its own that is same-site. *Why `docs_search` fails closed:* each search may ask the platform's AI for its words' vector, which costs money, so a counter that cannot count must not let searches through unmetered (`report`'s reason). *Why misses are counted by the dialog after a pause, not by the API:* a
word half typed is not a gap, and a GET that writes would count every keystroke and every prefetch. *Why a section's filters are links to the search page:* the section stays prerendered, its filtered list is an address to share and the page works without JavaScript; the counts are the search's own. *Why the guide's offer waits for E5:* an offer that leads nowhere is worse than none; the hand-over is in place for E5 to switch on. *Why no new dependency:* Postgres's text search, pg_trgm and
pgvector are already the store search's and the chat's; the dialog is the platform's `<dialog>`.
