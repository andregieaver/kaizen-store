# D883: The cookie popup's own look

Date: 2026-11-23

**Why.** The cookie banner and its settings popup (`ConsentManager`) had no settings of their own: they read the theme's variables
(`--background`, `--foreground`, `--muted`, `--border`, `--accent`, the button corners, the headings' font) from wherever they sat. Drawn over
the whole page and outside any row, they took the site's colour set, while a row with its own dark background (a backdrop, D534) holds the
dark set (`kz-on-dark`, D390). So on a dark cookies page the popup came out light, and the owner could not change it.

**What.** `ThemeSettings.consent` (`ConsentLook`, optional; a theme without it draws the popup as before):

- `scheme`: `site` (the default: the site's set, as before), `light` or `dark` (always that set). Homer's one choice, on the *Cookie popup*
  card in Design settings.
- Behind *Customise the cookie popup* (Lisa): `colours` of its own in the light and the dark set (background, text, secondary text, lines,
  main button and its text, other buttons and their text; started from what it shows, so choosing them changes nothing), the box's
  `corners` (else the cards'), the `buttonCorners` (else the buttons'), the `heading` font (`body` to use the body text's) and the
  `shadow` (none, soft, strong; strong by default). *Follow the theme again* keeps the set chosen.

**How.** globals.css's `:root` works out `--consent-*` from the page's own variables, so a theme without a look of its own writes nothing
(page budgets in `e2e/performance.spec.ts`). `themeCss()` writes the colours (from `consentColours()`) only where the look names a set or
colours of its own, never in a row's colour set (rows never hold the popup), and each corner or shadow only where it is set; the admin's
preview, which is not the root, always gets them; globals.css's `.consent-look` puts them in place of the page's variables, and `.consent-secondary` draws the other buttons. The
banner and the popup carry `.consent-look`, so only the popup's own variables decide how they look, wherever they sit. `themeWarnings()` checks its own colours where it shows them. The editor's
preview draws a small popup with the same classes.

**Words.** The card's words are their own server-only area, `consentLook` (`HandedArea`): English in `src/lib/consent-look-words.ts`,
which the editor reads when nothing is handed down, Norwegian handed down by the pages that draw `ThemeEditor` in the admin's language.
The design catalogue gains only the area's name in *What's new*, so the builder's screens (the sandbox is the largest admin entry,
`admin-text-reach.scan.test.ts`) load nothing more.

**Platform.** Kaizena Flow's own site edits its theme with the same `ThemeEditor` (Site design), so it has the card in the same change.

**The cookies page** is not part of this: where a store (Kaizena Flow's own store included, D484) has its own page for it (D113), that page is
built and styled in the builder; the standard list follows the theme like any page.
