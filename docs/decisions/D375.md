# D375: Sign in with Google for customers

**Sign in with Google for customers (wave 10 unit L, `docs/wave-10-must-haves.md` 4); built against a stand-in, live once Kaizena Flow's Google client is set.** Google lets one OAuth client name only the redirect addresses registered for it, and stores live on many hosts, so the sign-in passes through Kaizena Flow's own host: the store's sign-in form (`SignInForm`) shows *Sign in with Google* while `googleSignInOffered()` (the client in `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` through
`googleEnv()`, the server's `SETTINGS_ENCRYPTION_KEY`, the store's accounts on, D365); `/api/auth/google/start` on the platform's host keeps the state, a PKCE verifier and a nonce in the signed, HttpOnly cookie `kaizen_google` (ten minutes, path `/api/auth/google`, in `KNOWN_COOKIES`) and sends the browser to Google asking only `openid email`; `/api/auth/google/callback` checks the state against the cookie, exchanges the code with the client's secret and the verifier at Google's token endpoint
(8 s, no redirects) and checks the ID token (`checkIdToken()`: issuer, audience and `azp`, expiry, the nonce, `email_verified`; the token comes straight from Google's endpoint over TLS, so its signature is not checked again, OIDC Core 3.1.3.7).
Only an account the store already has, by that email, signs in: nothing is created and nothing else of the Google account is kept (no id, no name, no picture); an email with no account goes back to the form (`?google=no_account`), anything else that fails to `?google=failed`, worded by hand in nb, sv, da and en (`m.account.google*`).
The hand-over is a `customer_sign_in_links` row of two minutes, used once by `/api/shop/google/enter` on the market's own origin (`marketOrigin()`), which starts the session there (its cookie is that host's) and marks the email proven, as Google's word stands for the code the store would email. Every redirect goes to Kaizena Flow's or the store's own address, never one from the request; Google's endpoints are constants in `src/lib/google-sign-in.ts`, given only by tests.
A unit test holds the sealed state and the token's checks; `google-sign-in.int.test.ts` runs the flow against a stand-in for Google's token endpoint (the secret and verifier sent, a sign-in, the link spent, no account made, another browser's state, nonce or client and an unverified email refused). `customers.customer-accounts` moves to full. To go live: a Web application client in Google Cloud with `{SITE_URL}/api/auth/google/callback` as its redirect URL, its id and secret in the environment.
No migration.
