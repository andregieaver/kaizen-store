# D795: Contracts' upkeep runs in the five-minute dispatcher, and it calls the PDF route only when a signed contract waits for its seal

**Contracts' upkeep runs in the five-minute dispatcher, and it calls the PDF route only when a signed contract waits for its seal
(19 November 2026).** The first contract signed in production (Kaizena Flow's "Test deal with contract", signed by both sides at
12:38 and 12:40) got no sealed PDF: D695 step 3 put the seal, expiry, reminders, used codes and retention in `/api/cron/document-pdfs`,
and nothing calls that route (bloat review finding CR-11; step 3.7 is to call it, after step 3.1's one-minute tick). So no contract
would ever have expired, no signer been reminded and no signed PDF been made. Now `DISPATCHER_JOBS.contracts` (`runContractUpkeep()`,
`src/server/contract-upkeep.ts`, no Chromium and no seal library) asks one question (any contract out for signing, any signed one
without its seal, any code, any signed one at all) and does only what waits: expiry and reminders, used and lapsed codes, retention in
the first five minutes of each hour; and, when a signed contract waits for its seal, it asks the PDF route (`POST
/api/cron/document-pdfs` with the cron bearer, waiting up to 110 s, as `triggerLook()` waits for a look), whose run is now the seals
alone (`signedPdfJob()`). Two asks make no second file: the database sets a seal once. Idle cost: one statement and no rows a run
(`dispatcher.contracts` in the query budget, 1/0 with one store and with twenty); the dispatcher holds 79 jobs. The invoices' PDFs are
still made only on first download, as before: step 3.7 is unchanged. Tests: `contract-signing.int.test.ts` (the route asked only while
a seal waits, and its run seals it once).

Date: 2026-11-19
