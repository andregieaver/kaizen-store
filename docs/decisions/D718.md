# D718: Ecosystem plan phase 3

**Ecosystem plan phase 3: one nervous system (17 November 2026, `docs/audits/ecosystem-2026-11.md` E3.1 to E3.7).** Built in two waves; wave A is E3.1, E3.2, E3.3 and E3.6, E3.7 is released with the CRM tools (E2.5r); E3.4 and E3.5 moved to the email plan (D720, M2.3 and M1.5). **E3.1:** an append-only log of what happened, `commerce.events` (ids only, one row per transaction, store, event and subject), written first by `queue_integration_event()`, `queue_store_event()` and the platform's queue
through `commerce.log_event()`; read in `(tx, id)` order below the oldest running transaction, so an event whose transaction commits late is never skipped (a long transaction anywhere on the database server holds every reader back until it ends), with a cursor per reader (`commerce.event_cursors`, `src/server/event-log.ts`: `readEventsAfter`, `advanceCursor`, `consumeEvents` with a claim so two runners never take the same events); kept 90 days (`daily.events`), never changed, deleted early only
with its store or a purged sandbox.
No engine reads it yet: `processStoreEvents()` is the first to move, then the autopilot (E4.2). **E3.2:** fourteen events that had none, each a webhook topic, an app topic where an area fits and a workflow trigger: `deal.created`, `deal.stage_changed`, `deal.won`, `deal.lost`, `subscriber.subscribed`, `subscriber.unsubscribed`, `conversation.ended`, `conversation.rated`, `review.published`, `checkout.abandoned` (only where cart reminders capture checkouts), `work_client.created`,
`work_invoice.sent`, `work_invoice.paid`, `work_invoice.credited`; imports send none; erasure blanks their deliveries; contract 1.40.
Left: lead, activity and domain-problem events. **E3.3:** a paid order's workflow knows what an order rule knew (`PAID_ORDER_FIELDS`, read only when a condition needs one), with *is at least*, *is one of* and a *Hold the order* action; rules are moved by code to workflows (`src/lib/rules-to-workflows.ts`), each keeping its id, state and saver, by themselves when every rule can move, a rule matching *any* condition staying a rule; orders paid before the move run once.
Settings → Automatic lists in order what happens when an order is paid and everything that runs by itself. **E3.6:** segments on what people bought (a product or a category, ever, lately or not), deals, support (a conversation lately, a bad rating), reviews, subscription boxes and the texts list, each fact read only when a rule asks (`src/server/segment-facts.ts`) and not while its feature is off; a workflow's condition *the customer is in segment X* (`SEGMENT_FIELD`).
Left: email engagement (no opens are kept). **The AI:** no prompt or tool description changed in wave A: `count_segment`, `save_segment` and `draft_workflow` keep frozen copies of their schemas (`toolSegmentRulesSchema`, `draftWorkflowInputSchema`) and Automatic is in `NOT_YET_IN_PROMPT`, so the recorded eval stands; E2.5r opens them with a new recording. **The platform:** the log holds its rows (`store_id` null) and its support desk's conversation events; its event list offering them, an
Automatic page of its own and segments are the next step (the platform has none of the three today); the hold is store-only, as Kaizena Flow sends no parcels. Migrations `20261117134850_aspiring_centennial` (the tables) and `20261117134853_event_log_rules` (the functions, guard and triggers), applied by CI on 17 November 2026 (production 6f2b0718); advisors INFO only (RLS on, no policy, on `events` and `event_cursors`; their indexes not used yet).
