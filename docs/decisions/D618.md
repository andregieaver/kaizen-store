# D618: A checkout question can be asked only for some baskets

**A checkout question can be asked only for some baskets (the last step of task 4 of `docs/checkout-fields-tasks.md`; 15 November 2026).** `checkout_fields.conditions` holds the checkout rules' own conditions (`RuleCondition`: a country, the basket's value in the currency it is shown in, its weight, products, categories, tags, the buyer's customer groups), all of which must hold (`fieldAsked()`, `conditionHolds()`), so there is one condition model and not two.
The basket is read by `cartFacts()`, taken out of `checkoutRuleOutcome()` so rules and questions read it the same way, and only when a question has conditions; `askedFields()` is read by the cart (`checkoutQuestionsFor()`, which now takes the market and the customer), by the answers kept from it and by `placeOrder()`, so a question not asked is never required and its answer is not kept, and one a changed basket now asks stops the order until it is answered.
Without a cart a question with conditions is not shown. Not a delivery method: the questions are asked in the cart, before a delivery is chosen. Express checkout still stays off while any question is on, asked of this basket or not (the cautious choice). In the editor the conditions are under *Customise* with the width (the rule editor's own `ConditionsEditor`, taken out of it), open from the start for a question that has some; the list says *Some baskets*.
A change without conditions keeps them; `[]` asks it always. Two bugs found on the way: saving refused every product a condition named, a rule's too, since `knownIds()` leaves products out by design and saving never read the named ones (`knownForSaving()` now does, `checkout-rules.int.test.ts` saves a rule naming the store's own product); and the checkout page gave the editor no `bounds` (D613), so editing a number or a date question cleared its limits. Admin API contract 1.22 (`conditions`).
