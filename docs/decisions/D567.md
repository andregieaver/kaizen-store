# D567: Every query the app sends is bounded, and every payment webhook route

**Every query the app sends is bounded, and every payment webhook route (11 November 2026, code review step 1.5, finding FD9, migration `statement_timeouts`, `longerTimeout()` in `src/db/client.ts`).** The app, CI's migrations and Supabase's tools reach the database as the `postgres` role through Supavisor, whose transaction mode drops a connection's own start-up settings, so the limits are the role's: `statement_timeout = 15s` and `lock_timeout = 5s`, set only on Supabase (where
`supabase_admin` exists) so developers' and CI's databases stay unbounded. Supabase had already given the role `idle_in_transaction_session_timeout = 30s` and `transaction_timeout = 60s`. A job that needs longer raises its limit for one transaction with `longerTimeout(tx, seconds)` (`set local`, 1 to 55 s; never a plain `set`, which the pooler would carry to another request); the migration runner sets its own per file. The role's slowest statement in production's recorded history was 6.6 s.
The five payment webhook routes (Stripe's store, Connect, Connect accounts and billing, Mollie) have `maxDuration = 60`, and `cron-routes.scan.test.ts` requires one on every route under `api/stripe`, `api/mollie` and in a `webhook(s)` folder. Seen in production after the deploy (17:23 UTC): the role carries both limits and `select pg_sleep(20)` is cancelled with *canceling statement due to statement timeout*; the site and `/api/health` answer as before.
Migration version (applied by CI): `20261111151548_statement_timeouts`. Advisors checked after: no new finding (security INFO only, as every private table).
