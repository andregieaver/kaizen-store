# D627: One field for a discount code or a gift card; the checkout's preview shows the store's questions; the phone's product bar above every row

**One field for a discount code or a gift card; the checkout's preview shows the store's questions; the phone's product bar above every row (15 November 2026).** The owner asked for one field, so the cart's and the checkout's code field takes both: what is shaped like a gift card (`looksLikeGiftCode()`: sixteen characters of its alphabet) goes on as a card, a payment, through the gift card's own action and its guard on tries; anything else is a discount code, so a mistyped code never counts
against the gift card's tries. A card stays money and a code a discount (D300 F3): they are listed apart under the field, each with Remove, and apart in the totals; only the field is shared (`GiftCardForm field={false}`).
On Settings → Checkout rules, *What a shopper fills in* (D624) lists the questions switched on, each a link that opens it in *Questions at checkout* (`openCheckoutQuestion()`, or `#question-{id}`), *Add a question*, and a link back to what the checkout asks; Rules and Questions say *Start from an example, or add your own* above their example chips, which read as rules already made (the owner could not find the list on a store with none).
The product's bottom bar on a phone is drawn in the product's own part, where a row's own layer kept it under the tiles of *You may also like*: once the page has hydrated it is moved to the end of the body (`createPortal`, z-40, under the admin's own buttons at z-50).

Date: 2026-11-15

The owner's three asks of 15 November 2026. Platform: Kaizena Flow sells plans through Stripe's page, with no code field of its own here, no checkout questions and no product bar (D357). No migration.
