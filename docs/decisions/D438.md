# D438: Contracts

**Contracts: one registry per API, generated OpenAPI 3.1, typed webhook topics, the MCP catalogues, versions and a changelog (wave 14 unit A, `docs/wave-14-developer-platform.md` A1 to A5).** The Admin API is described once, in `ADMIN_API` (`src/lib/admin-api-routes.ts`, pure): each operation's method, path, name, scope, words, and the zod of its path parameters, query, body and answer, with the errors it can answer.
`routeOf()` is made from it (the most literal template whose parameters read), and so is the Apps and API page's list (`API_ROUTES`); `routeOf()` and `API_ROUTES` moved there from `admin-api.ts`.
Every write reads its body with its operation's zod before any screen's check (`readBody()`, the problems in the API's words by `bodyProblems()`, the nearest shape of a union told): discount codes (`discountBody`, snake case as before), checkout rules and questions (the screens' own `ruleInputSchema`/`fieldInputSchema`; an update is `{ enabled }` alone or the whole of it), customer tags; the screens keep their checks.
Every answer is built as `AdminAnswer<name>` (`z.output` of its `response`) and checked against its schema on the way out: one of another shape is logged (`admin_api.answer_shape`, the paths only) and still sent.
`adminOpenApi()` (`src/lib/admin-openapi.ts`) makes the OpenAPI 3.1 document from the registry with `z.toJSONSchema()` (`jsonSchemaOf()`, `src/lib/openapi.ts`): parameters, bodies, answers, each refusal at its status in the error envelope, the bearer scheme (`kf_`), `x-required-scope` and the scope in `security`, `x-pagination`, `x-rate-limit` (120 a minute a token, 1,200 a store), `Idempotency-Key`, `Retry-After` and `Idempotent-Replayed`, and the webhook topics under `webhooks`; served at
`/api/admin/v1/openapi.json` (a static segment beside the catch-all, public, an hour's cache). The storefront document gains every route's query, body and answer from zod (`STOREFRONT_ROUTES` entries carry `query`, `body`, `response`, `status` and `errors`; the answers' schemas are new, written from the storefront's readers and typed against them in the integration test).
The webhook topics are `WEBHOOK_TOPICS` (`src/lib/webhook-topics.ts`, made from `EVENTS`): each topic's receivers (services and endpoints, or endpoints), its subject and the zod of its `data`; `subjectData()` builds each subject as `WebhookSubject<…>` and checks it (`webhooks.payload_shape` logged, the payload sent as built), `PAYLOAD_VERSION` stays 1 and no receiver sees a change, except that a test's sample order now has the three fields a real order had and it lacked (`referral_discount`,
`vat_kind`, `vat_relief`). The catalogue (topics, version, headers, signature steps, retries) is at `/api/webhooks/v1/topics.json`.
The owner MCP's tools moved to `src/lib/mcp-catalogue.ts` (`MCP_TOOLS`, pure, re-exported by `store-mcp.ts`), each with a title and MCP annotations worked out beside the tools (`toolAnnotations()`: read-only for no gate and a `:read` permission or `OWNER_KEY_READS`; destructive for gates `spend`, `domain` and `access` and names that delete, archive, refund, cancel or end; idempotent for reads and state-setting verbs; open world for gates `send` and `domain` and `OPEN_WORLD`), so no tool's
description or input changes and the eval's `toolsVersion()` stays `578ddaf06260`; `tools/list` answers them, and `/api/mcp/catalogue.json` publishes every tool's title, description, input schema, gate, permission, feature and annotations with no store's data. The shopping agents' tools get the same (`src/lib/ucp-catalogue.ts`, `tools/list` of `/api/ucp/{store}/mcp`, `/api/ucp/catalogue.json`).
The whole contract (both documents, the topics, both catalogues) is hashed over canonical JSON (`src/lib/api-contract.ts`) into `src/data/api-contract.json` with its version (`1.0`), and its surface (every operation, topic and tool, every field of an answer or a payload, every field a request must send) kept in `src/data/api-contract-surface.json`; `api-contract.test.ts` fails when the contract changes without a new version recorded
(`WRITE_API_CONTRACT=1 pnpm exec vitest run src/lib/api-contract.test.ts` records it as the next `1.<n>`, or the next major when something breaks) and an entry for it at the top of `content/docs/developers/changelog.md`, and when a field or a path is taken away, or a request must send a new field, within the same major version.
Tests: the registry whole and its router (`admin-api-routes.test.ts`), every `route.ts` under `api/admin/v1` and `api/storefront/v1` matched both ways (`api-routes.scan.test.ts`), both documents checked against the structure OpenAPI 3.1 asks (`openapi.test.ts`, written by hand: no validator of the format is among the dependencies, and none was added), the annotations decided for every tool (`mcp-catalogue.test.ts`), every Admin API answer and every storefront answer parsed in their integration
tests, every topic's payload built on a store's real subjects and parsed (`webhook-topics.int.test.ts`).
