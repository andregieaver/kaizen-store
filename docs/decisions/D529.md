# D529: A webhook event is claimed before it is worked on

**A webhook event is claimed before it is worked on (10 November 2026, `commerce.claim_webhook_event()`, `webhook_events.claimed_at`, `src/server/stripe-webhooks.ts`; step 0.6 of `docs/audits/code-review-2026-11.md`, finding FV6).** Stripe may deliver one event twice at the same moment.
`recordEvent()` called an event new while `processed_at` was null, so the second delivery worked on it as well: order completion and renewals were safe to repeat, but a confirmation email, a dispute or a payout could be written twice.
The event is now recorded and claimed in one statement by a database function: true for a new event, for one that failed (the handler gives its claim up with the error) and for one whose claim is more than five minutes old (its worker died); false for one that is done or being worked on. The route still answers 200 to the delivery that was refused: the one at work answers for the event, and a failure there is a 500 that Stripe retries.
Tested in `src/db/commerce.test.ts` against the migrations (five cases); no test delivers twice at once against a real database, because none could be run where this was written. **The platform:** Kaizena Flow's own billing webhook does not record events in `webhook_events` (its steps are written to be safe to repeat), so nothing changes there. (Numbered D528 for an hour, in the migrations' own comments too; another change took that number the same morning.) **Corrected the same day:** the first
function called a claim its own when `claimed_at` equalled its statement's `now()`, which two deliveries in one clock tick both pass (it failed CI's unit tests, where the clock ticks in milliseconds). `20261110103657_webhook_claim_exact` replaces it with explicit steps, each decided by whether a row was written. Migration versions: `20261110094246_webhook_claim`, `20261110094326_webhook_claim_rules`, `20261110103657_webhook_claim_exact`, applied by CI on 10 November 2026 (run 1176).
Advisors checked after: no new warning about the function or the column; INFO only (RLS on, no policy, as every private table).
