# D358: Versions compared, and staging inside the store

**Versions compared, and staging inside the store (wave 9 unit E, `docs/wave-9-platform.md` section 3, E and section 4); built.** Comparing: `compareVersions()` (`src/lib/version-compare.ts`, pure) says what differs between two versions of a page, article, header, footer or product layout in words: the page's own fields (title, address, summary, search texts, picture, CSS, categories and tags, countries, search switches), each text that changed with its label and both words (`mapTexts()`, rich
text as its plain words), rows added, removed or moved (only the rows outside the longest run kept in order are said to move), components added or removed in a row both have, and rows, columns and components whose own settings changed (measured with the words blanked, so a change of words is not also a change of settings); `compareLooks()` names the areas of a look that differ (`LOOK_AREAS`).
Both dialogs' versions (`PageVersionsDialog`, `LookVersionsDialog`) have *Compare*, against what is in the editor now; nothing is changed by comparing.
Staging, **changed from decision 5 of the wave's plan** (a hidden copy of the site merged back): a staging set inside the store, `commerce.site_stagings` (one open per store, a name, a theme install, menus as staged JSON, the outcome) and `site_staging_pages`, written only by `src/server/site-staging.ts`, at Website → Staging (`/admin/{store}/staging`, `website:read` to see, `website:write` to change).
A store already holds every change a visitor does not see as a draft, an installed theme that is not live and the menu editor's input, so a set only chooses which go live together; a hidden store would have copied pages, the theme, menus, saved parts, terms and pictures out and back with every id mapped twice.
A set holds the store's own pages of the site's kinds (`STAGED_TYPES`: page, article, header, footer, product layout; never an A/B test's version or an entry layout), one theme installed and not live, and menu changes checked by `menuInput` (the menu editor's staging mode, `/menus?staged=1`).
The page lists each page whose draft differs from what visitors see with `compareVersions()`, each waiting theme with `compareLooks()` against the live one, and each menu with its staged counts. *Make live* (`publishStaging()`) claims the set, then publishes each page through `savePage()` (only a kind the member may write, `pageTypeKey()`; anything the builder's Publish refuses is refused for that page and said, the others go live), switches the theme through `switchToInstall()` (a premium theme
the store does not own is refused there) and saves each menu through `saveStoreMenu()`, each making the version it makes anyway and moved addresses leaving their redirect; the outcome is kept on the set and audited `store.staging_published` with counts. *Discard* closes it and changes nothing. Products, orders and customers are never part of a set. Both tables `never` copied, `NOT_PERSONAL`.
`platform.store-duplication-staging-theme-versions` stays partial (the site's own CSS keeps no versions, and a set stages the store's drafts rather than a copy). Migration versions: `20261028122130_site_staging` (applied by CI on 28 October 2026, run 697; advisors to check).
