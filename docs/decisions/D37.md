# D37: A function never leaves a database connection half-used

**A function never leaves a database connection half-used.** The app talks to Postgres through node-postgres, which sends a query and its values in one message, one query at a time per connection. postgres.js, used before, sent a query with values in two halves without prepared statements and pipelined queries; through the transaction-mode pooler the second half could reach another Postgres connection once the pooler had handed the first back, so the query waited forever while a Postgres
connection sat holding its first half. That was the main cause of pages hanging under load. Also, Vercel freezes a function instance between requests. Frozen in the middle of a query, it left the pooler's connection to Postgres waiting for the rest of it (seen: two such connections held for five minutes); enough of those and every query waits for a free connection, so pages hung on their loading placeholders until the pooler let go. Frozen with connections open, it woke up to dead ones.
Now every query asks Vercel (through its `attachDatabasePool`) to keep the instance running until the query is done and its connections have been idle for five seconds and closed. As a safety net, Postgres ends any transaction of the app's role open for a minute, or idle inside a transaction for 30 seconds, so a connection is never held for long. The cached reads pages are built from try once more on a passing error (a timeout, a lost connection), so one hiccup does not fail a page or a build.

Date: 2026-09-25

After pages intermittently hung on "Loading …" in stores and the admin, and a build failed on a timed-out read. The app's transactions take milliseconds and call no outside service, so the limits never cut a real one.
