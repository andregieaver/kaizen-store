# D610: Fallback text models, and the autopilot's work side by side

**Fallback text models, and the autopilot's work side by side (`docs/100-day-challenge.md` F1 and H1; 14 November 2026, `ai_providers.fallback_models`, `gatewayOptions()` in `src/server/ai.ts`, `runAutopilot()`, `runGoalReviews()`, `runEvents()`, `/api/cron/autopilot`, migration `20261114202420_overrated_whirlwind`).** **F1:** a provider through Vercel's AI Gateway may name up to three fallback text models (Platform → AI or a store's own AI settings, *Fallback text models*, written
provider/model); every text and chat call sends them as `providerOptions.gateway.models`, which the gateway tries in order when the text model fails, within the same EU and zero-retention rules (checked against Vercel's documentation of model fallbacks). Embeddings never get them: another model would put vectors in another space.
Usage is still recorded at the text model's price; a fallback's own price is a later refinement. **H1:** the loop took at most three plan steps, two reviews and two events a minute across every store, one after another, so ten challenge stores would wait on each other.
Now each part claims up to twelve, one per store, and runs them side by side, and the route runs the steps, the reviews and the events side by side too (`Promise.allSettled`); each part's own claims keep two runs from taking the same work, and the per-store and per-day limits (D604) still hold. Tests: `ai-provider.test.ts`, `ai.int.test.ts`; the autopilot's integration tests pass unchanged.

Date: 2026-11-14

Unit 8 of the preparation for the challenge, for up to ten stores. Platform: Kaizena Flow's own provider takes fallback models the same way; its own autopilot runs in the same loop.
