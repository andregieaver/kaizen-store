# D666: The admin's colour roles follow the site's colours outside the admin

**The admin's colour roles follow the site's colours outside the admin (bloat review step 0.34; 16 November 2026).** Thirteen admin colour roles had a value only under `html[data-admin]`, so the submit button on Kaizena Flow's /status and /report had no fill and 20 role classes in seven shop and site files drew nothing. The seven files now write the site's names (`border-border`, `bg-background`, the storefront's red pair).
For the admin parts drawn on public pages (`ActionForm` and its buttons, imported by hundreds of files; the hosted invoice's print button; the on-site editor's toolbar and fields) the roles are mapped to the site's colours in one `:where(html:not([data-admin]))` block in `globals.css`, mirroring `admin.css`, at specificity 0 so an owner's own `:root` variables of the same names still win.
`src/lib/stylesheet-sources.scan.test.ts` holds three rules: shop and site files write no role; a file a public page reaches outside them (admin parts and `src/lib/submit-class.ts`) reads only mapped roles, with a dark value for a literal colour; the block stays inside `:where()`. An e2e check holds the filled button on /report and /status in light and dark, and `admin-look.spec.ts` now expects the storefront's brand role to be its accent.
These pages are Kaizena Flow's own, where the fault showed. Commits ca2e4455, 4f7639cd, 8a5e02cb.
