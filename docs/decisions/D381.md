# D381: Money held for customers

**Money held for customers (wave 11 unit B, `docs/wave-11-core-and-psi.md` 2.B); B1 built: what is owed on Finance.** Finance's *Owed to customers* (`LiabilitiesView`) is a row for bonus credit and one per gift card currency, each a roll-forward from its ledger's own sums only (`liabilityRows()`, `src/server/liabilities.ts`; `rollForward()`, `liabilityRow()` in `src/lib/liabilities.ts`): the sum of entries dated before the period's first instant (the store's day), each kind's entries in the
period in a column (`COLUMN_OF`: given, used, given back, taken back, expired, changed by staff, a kind not mapped in *other*), and the sum before its end (or now), so it adds up by construction and a row that does not says by how much. *Held now* is bonus credit's `bonus_balance()` (available and pending) summed over the store's customers, the bonus page's figure, and delivered live gift cards per currency; the difference from *at the end* (credit that ran out awaits the night's job, a card not
yet delivered) is said in words, never hidden. Bonus credit in a currency other than the main one shows the main one beside it, for display only; nothing is converted into or added across currencies. Defined first in `docs/analytics.md` (*Owed to customers*), CSV `finance.liabilities`.
No migration for B1. **B2 built: a new code.** A delivered, live card gets a new code only through `commerce.gift_card_new_code()` (migration `20261028231844_gift_card_new_code`, applied by CI, run 718; advisors: INFO only): it locks the card, refuses one that is not active, not delivered or expired, and replaces the hash and last four under the setting `kaizen.gift_card_new_code` (the card's id), the one exception `gift_cards_rules()` allows to a delivered code, so the old code stops working
and the balance is untouched.
Staff with `products:write` press *Send a new code* on the card's page (`sendNewGiftCardCode()`): the code is shown once to them and emailed only to the address the card was delivered to (the recipient's, else the order's own while it is not restricted or anonymised), with its own idempotency key; the audit entry `gift_card.new_code` never holds the code. **Course change: the shopper's own amount is not built.** A gift card's price is a variant's price, set only through `set_price` and read by
every price reader (the cart, `line_price()`, `placeOrder()`, the invoice snapshot, feeds, the agents); an amount the shopper types would be a second way a line is priced through all of them, and the row stays partial on the voucher review in any case, so fixed amounts stay the way to sell one until that review is done.
