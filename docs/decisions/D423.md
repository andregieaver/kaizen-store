# D423: Leaving a page in Safari goes where the visitor asked

**Leaving a page in Safari goes where the visitor asked.** Next.js's router fetches a page's data and, when that request fails for any reason but its own cancel, loads the page's address in full (`fetchServerResponse()`, `next/dist/.../router-reducer/fetch-server-response.js`).
Safari's engine cancels a page's requests the moment a whole-page load starts (`beforeunload` fires, then the requests fail with *Load failed*), before `pagehide` and while the page's scripts still run, so a visitor who left a page while the router was still fetching the next one (an address typed, a bookmark, a plain link, a form) was taken to the page being fetched instead. CI's WebKit search test met it (run #891, both tries), and so did 6 of 70 runs of it locally.
`patches/next.patch` (`patchedDependencies` in `pnpm-workspace.yaml`, for any version of Next.js): while a router request is out, a `beforeunload` listener notes the time; a request that fails within three seconds of it, or after `pagehide`, waits instead of falling back; if the visitor comes back to the page from the back-forward cache (`pageshow`), it is answered with a fresh load of the page as it stands, the address they came back to, never the one it was on its way to.
`e2e/store-pages.spec.ts` holds the search page's request and leaves by a whole-page load: WebKit failed it every time before the patch.

Date: 2026-11-02

*Why a patch, not app code:* the decision to load the page is made inside the router, and a wrapper around `fetch` would not see a failure while the response body streams.
Next.js 16.4.4 and 16.5's canary still fall back the same way (checked 2 November 2026). *Why the listener only while a request is out:* a standing `beforeunload` listener can keep a page out of the back-forward cache. *Why three seconds:* the cancel comes within milliseconds of `beforeunload`; a leave called off at an admin editor's *leave this page?* prompt must not keep a later real failure from falling back. *On a Next.js upgrade:* the patch goes with it while the lines it changes are the
same (16.4.4's are); where they change, pnpm refuses the install until the patch is moved, or dropped once Next.js stops falling back on a cancel; the test says which. First kept for 16.4.2 alone, which stopped Dependabot's Next.js updates (its run of 2 November failed on `next`); keyed by name the same day.
