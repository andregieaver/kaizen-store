# D314: Usage, limits, scaling and hosting levels

**Usage, limits, scaling and hosting levels (`docs/capacity.md`), built in phases.** Kaizena Flow sells one platform at three levels of isolation (*Shared*, *Dedicated*, *Private cloud*) chosen by the plan, not three hosting products: same code, admin and addresses, a store moved between cells by the platform.
Usage is measured per store and UTC day first (`store_usage_daily`: storage, catalogue, staff, domains, emails, AI on Kaizena Flow's key, and traffic from Vercel's log drain keeping no IP, agent or path), then limited: a limit is the store's override, else its plan's while on it, else the platform default, else unlimited (`plan_limits`, `limit_overrides`, `limitFor()`); numbers are data the platform admin edits.
Hard limits refuse only costly actions (uploads, products, staff, domains, stores per owner, marketing email, AI on Kaizena Flow's key); traffic is a soft limit that warns and never takes a storefront offline; transactional and legal emails are never limited; templates and demo stores are never limited. Protection in the shared cell: statement timeouts, per-store budgets on costly public endpoints, the edge firewall, a read replica only for analytics and exports.
Peaks: a peak calendar, a checkout queue under database pressure, load tests off production, service levels and restore drills. Cells (a Vercel and a Supabase project each, the current one `eu-1` and the control plane) start with a spike, `docs/cells.md`, before anything is built. The word *hosting* stays D71's in code.
