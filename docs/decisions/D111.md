# D111: The platform chooses the languages stores can offer, and the interface text of new languages is translated by AI into data, read by a person and used key by key

**The platform chooses the languages stores can offer, and the interface text of new languages is translated by AI into data, read by a person and used key by key.** *Registry* (`commerce.platform_languages`, `src/server/languages.ts`, `/admin/platform/languages`): each language has its code, its locales (the main one first, then variants such as `de-AT`), its English name, a switch and a direction; it starts with every language stores could already be in (D109) and a platform admin adds more
from the world's languages (`src/lib/languages.ts`: a curated list of about 85 with names from `Intl`, or any ISO code `Intl` knows). A store picks its languages among the enabled ones at `/admin/{store}/settings/localization`, which shows where each one's interface text stands; a language stores use, and English (everything falls back to it), cannot be switched off.
Products, pages, menus, alt texts and the AI translations of D109–D110 already worked in any language; this adds the *interface*: buttons, cart, checkout, account pages and the shoppers' emails (`src/lib/i18n.ts`, `src/lib/email-text.ts`), written by hand in Norwegian, Swedish, Danish and English and never in the database. *Catalogue* (`src/lib/ui-catalog.ts`): the English messages as entries with a key (`ui:cart.title`, `email:orderSubject`) and a text, or, for a message that takes arguments
(about 170, of which 28 choose by a number or a yes or no, `CHOOSING`), a template in a small ICU subset (`src/lib/icu-lite.ts`: `{0}`, `{0, plural, one {# day} other {# days}}` with the language's own plural forms from `Intl.PluralRules`, `{1, select, true {…} other {…}}`); a test holds every template to the English function's output for arguments of each kind, so a new English message is found by the catalogue at once and one that chooses must be added to `CHOOSING` with its case in
`ui-catalog.test.ts`. *Texts* (`commerce.ui_translations`: language, key, text, a fingerprint of the English it was translated from, `ai` or `staff`, and when a person read it): the platform admin's page for a language (`/admin/platform/languages/{lang}`) plans what is missing, out of date (English changed) or everything the AI wrote, sends it in chunks of 40 to Kaizen's own AI (`aiFor(null, { feature: 'ui_translation' })`, never a store's key), and keeps only what passes the checks
(`src/lib/ui-translate.ts`: every placeholder kept and no new one, named placeholders such as `{left}` kept, a select's options kept, a plural in the language's own forms, plain text, not far longer than the English); what fails is listed and left for a person.
A person edits a group of texts (checked the same way, kept as `staff` and reviewed, never replaced by the AI, not even by translating everything again), marks texts reviewed, or removes a language's texts to start again. *Reading* (`src/server/ui-text.ts`, `src/lib/ui-registry.ts`): `t(lang)` and `emailText(lang)` stay synchronous; for a language without hand-written text they read a registry on `globalThis` of `Messages` built from the texts (`overlayMessages()`: each text or template replaces
the English one, a template becoming a function of the same arguments, and anything the language lacks stays English, key by key rather than the whole language).
A server instance reads the texts when it starts (`src/instrumentation.ts`, `startUi()`) and looks for changes each minute; pages never wait on the database for text, and it is not read while a page is prerendered (which would break `cacheComponents`), so a page cached before a language was translated shows English until it is drawn again. The storefront layout hands the language's texts to the browser (`UiTexts`, which registers them so client components' `t(lang)` speak it).
Not yet: right-to-left layout (the registry keeps each language's direction, but nothing sets `dir` or mirrors the layout), fonts in scripts beyond Latin, Greek and Cyrillic, keyword-search stemming beyond the twelve languages Postgres has (`commerce.search_config()`; others match without stemming), and legal texts, which stay out of the catalogue and need a person's translation.

Date: 2026-09-29

Asked for by the owner: expand multilingual support beyond Norwegian, Swedish and Danish with any language chosen from a full list in the platform admin, translated to it. The content layer was already language-open; the interface was the gap (English for every other language), and moving it to data lets Kaizen add a language without a deploy while keeping the hand-written languages as they are.
Templates with plural and select, checked against the language's own plural forms, are what let an AI translate messages that are functions in code without breaking numbers, names or gender-like choices; keeping every text a person writes and a fingerprint of its English makes re-translation safe and a changed original noticeable. Translating the interface is a platform job (once, for every store), reviewed once, rather than each store paying for it.
