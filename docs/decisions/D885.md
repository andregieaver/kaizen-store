# D885: The navigation doc written from the menu: a script writes docs/admin-navigation.md's tables from the nav data at all thr

**`docs/admin-navigation.md`'s tables are written from the menu's data at all three levels, and CI fails while they differ (code
review step 4.3, finding FN11; 23 November 2026).** The doc was kept by hand and described a smaller admin: a store without Analytics
or Support and with 45 of its 117 pages (one, Chat agent, no longer in Settings), the owner's level without Support and Books.

Generated, between six pairs of `nav:generated` markers: each level's tabs (label, icon, the address it opens and whether that is the
section's own page, its sidebar's pages, groups and Basic count, what a store's tab needs or whom an owner's tab is for), and under
*Every page* a table per section with a sidebar: group (on its first page), label, address (with `also`), view (`advancedIn()`) and
need. A store page's need is its features, one of which is enough (`FEATURES_BY_ID`'s labels), its paid extension (`EXTENSION_NAMES`)
and `customer` ("not Kaizena Flow's own store"); an Account page's is `owner` or `holder`. Whom an owner's tab is for is found by asking
`ownerTabs()` with one `OwnerWho` flag at a time, so the doc follows the code, not a copy of its rule. Descriptions and permission areas
are left out: the pages of cards show the first, the move tests hold the second.

Shape: one table per section (the store's 117 pages in nine), not one per level, so a person reads one section at a time and a row needs
no section column. Each level's tabs stay where the level is described; the page tables are at the foot.

How: `src/lib/admin-navigation.ts` is pure, beside `parity.ts`, whose marker functions now take a tag (`parity` by default) and whose
`table()` and `cell()` it shares. `scripts/admin-navigation.mjs` (`pnpm nav:write`, `pnpm nav:check`) runs it under node's type
stripping: the nav modules import their neighbours without an extension, so the script resolves a TypeScript file's relative and `@/`
imports as the bundler does (`registerHooks`); no database, secrets or build. CI holds it as it holds the parity report:
`src/lib/admin-navigation.test.ts`, in the static job's unit tests on every push with code. A push of the doc alone runs nothing and needs
nothing: the doc can only fall behind when a nav file changes. The test also renames a page in a copy of the menu and finds only
`store-pages` stale, written back with the words around it unchanged.

Rejected: a writer in the test alone (`WRITE_…=1`, as the glossary's), whose exports only tests would use, which the unused-code budget
refuses; a CI step running `nav:check`, a second run of what the unit tests already do; a marker per section, fifteen blocks to keep in
order by hand. Not a budget (nothing is counted), so no row in `docs/rules/budgets.md`.

Words changed by hand where they contradicted the menu: the hand tables went; Marketing opens on a page of its own (D612), as Website and
Settings do; staff see Support, Books and Work where a store gives them those; the control center points to the owner's tabs. The rule
(`docs/rules/admin/platform.md`) names `pnpm nav:write` and no longer lists each level's sections.
