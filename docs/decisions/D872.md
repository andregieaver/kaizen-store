# D872: Marketing email through Amazon SES in Ireland, off until its keys are set (D748 E10 part one)

Date: 2026-11-23

D748 section 10 sends bulk marketing through Amazon SES in eu-west-1 (about $0.10 per 1,000 emails) and keeps transactional mail on
Resend. This is that part, built so nothing changes until a platform admin sets `AWS_SES_*` in Vercel.

- **Which mail.** A store's broadcasts and flows (`SES_KINDS`, the sending guard's `MARKETING_KINDS`: `marketing.broadcast`,
  `marketing.automation`). Order, account, security and staff emails never go through SES.
- **Which way** (`marketingRoute()`): from the store's own domain through SES once SES has verified it; else through Resend while Resend has
  verified it (D727); else from the shared address, through SES when the shared address is on Kaizena Flow's own sending domain and SES has
  verified that, through Resend otherwise. Without SES's keys, Resend from the same address as before. Kaizena Flow's own marketing (no
  store) takes the same way: the platform has it in the same change.
- **Domains at SES.** Each sending domain is also a domain identity at SES (Easy DKIM, so mail is signed as the domain itself and DMARC
  passes; a MAIL FROM on `ses.` so SPF is the domain's own). SES's five records are kept apart from Resend's (`ses_records`), written into
  the zone when Kaizena Flow keeps it (D315) and shown on the same card to copy otherwise. `ses_status` is `none` until SES is set up; the
  owner's *Check now* and the daily job ask SES too; a domain SES gave up on is made again with new records. A domain added before the keys
  were set is made at SES by the daily job.
- **Sending.** `SendEmail` on SES's v2 API, signed with Signature Version 4 in `src/server/aws-sigv4.ts` (a page of code, tested against
  AWS's published example) rather than the AWS SDK. A broadcast's batch sends its SES emails eight at a time and the rest through Resend's
  batch. SES has no idempotency key, so a call that broke off without an answer is never repeated (`UNCERTAIN`): a reader may miss one
  marketing email, never get it twice. Throttling and SES's own failures are tried again; an email SES refuses outright (its domain
  unverified since the last check, the account held) goes through Resend instead. Names that are not plain ASCII are written as RFC 2047
  words.
- **Events.** The configuration set publishes deliveries, bounces, complaints and rejections to an SNS topic whose HTTPS subscription is
  `/api/ses/events`. Only that topic's messages (`AWS_SES_EVENTS_TOPIC_ARN`), signed with SNS's own certificate within the hour, are taken;
  the subscription is confirmed there. Each event is recorded as Resend's are (`applyEmailEvent()`, by the SES message id), so a hard
  bounce or a complaint takes the address off the store's list and the sending guard (D730) counts it.
- **Staff.** Platform → Emails says which way newsletters and flows go, and what to set when SES or its events are not set up.

Setting it up (the platform admin, once): an AWS account with SES out of the sandbox in eu-west-1; an IAM user limited to `ses:SendEmail`,
`ses:CreateEmailIdentity`, `ses:GetEmailIdentity`, `ses:DeleteEmailIdentity` and `ses:PutEmailIdentityMailFromAttributes`; a configuration
set with an SNS event destination for delivery, bounce, complaint and reject; then `AWS_SES_ACCESS_KEY_ID`, `AWS_SES_SECRET_ACCESS_KEY`,
`AWS_SES_CONFIGURATION_SET` and `AWS_SES_EVENTS_TOPIC_ARN` in Vercel. The region defaults to eu-west-1 and is refused outside the EU.

Idle cost: none until the keys are set; then one more read of `sending_domains` per marketing email or broadcast batch, and the daily
job's calls to SES for domains it has not verified.

Migration versions: `20261123102718_youthful_starhawk` (three columns on `sending_domains`).
