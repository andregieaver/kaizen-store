# D179: Responsive editing and visibility in the page builder, after Beaver Builder

**Responsive editing and visibility in the page builder, after Beaver Builder.** `docs/responsive-editing.md` is the contract and the record of what was built.
Four screen sizes (Small, Medium from 768, Large from 1024, Extra large from 1280, `ThemeSettings.breakpoints`, editable in Design settings); a part's settings are its Extra large values with per-size overrides in `PartBase.at`, larger to smaller (`valueAt()`), written as `:where()`-scoped CSS rules (`src/lib/part-css.ts`; media queries on the site, container queries on the builder's canvas), so owner CSS and the replicator's rules still win.
The old one-off phone switches and per-block text fields are folded in on read and never written again. The builder's Responsive mode (a bar with size, width, height, zoom and Exit; a device icon on every field that can vary; inherited values greyed with a reset) draws the canvas at the chosen width.
A Typography group per kind of text (family, weight, size with unit, line height, alignment, letter spacing, transform, decoration, style, variant, text shadow) on every component, row and column, so every text the builder edits has a font size; entrance effects take a delay and a duration.
Visibility: per screen size (CSS), and Display by sign-in or conditions (shopper facts, country, language, currency, date, weekday, hour, cart value and contents, an address parameter; groups of AND joined by OR), decided on the server in a Suspense hole (`<VisiblePart>`, `visitorFacts()`), so hidden parts are never in the HTML; excerpts, structured data and chat knowledge read only what everyone sees.
A parity check (`e2e/responsive-parity.spec.ts`) compared every saved page's computed styles at four widths with the build before each phase: no difference. Kaizen's own pages use the standard screen sizes (no place to store others yet).
