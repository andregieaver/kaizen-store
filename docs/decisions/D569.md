# D569: Migrations that keep the busiest tables writable

**Migrations that keep the busiest tables writable (code review step 1.6, finding FD4; 11 November 2026, `scripts/db-migrate.mjs`, `scripts/lib/migrations.mjs`, `src/db/migration-safety.scan.test.ts`, `src/db/migrate-no-transaction.int.test.ts`, `docs/ci-migrations.md`).** Every migration ran in one transaction, so none could build an index `concurrently`, and every index on orders or visits blocked their writes while it was built.
A file whose first line is `-- kaizen:no-transaction` now runs statement by statement outside a transaction, wherever migrations are applied (production's runner, the CI and lane databases, the tests' PGlite); its ledger row follows its last statement, and when one fails, an index the file names that was left invalid is dropped again (concurrently), so the file, written to run again, goes through on the next run once fixed.
A scan test holds every new migration to the rule on orders, order_lines, visits, products, product_variants, customers, carts and cart_lines: indexes concurrently in a marked file, foreign keys and checks `not valid` and validated in a later statement that commits on its own; a table the file makes is exempt. *Why:* milliseconds today (in production every foreign key on these tables is indexed and the largest is 700 kB, so no index was added), a checkout that stalls once the tables are large.
*Rejected:* marking the generated files themselves (a file with a schema change and its index would lose its all-or-nothing transaction); a lint of every table (most are small and written by staff, and the rule would only teach people to ignore it). No migration.
