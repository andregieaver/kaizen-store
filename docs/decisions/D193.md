# D193: Editing words on a store's own domain

**Editing words on a store's own domain.** Stores live on a domain of their own (P7), so the admin's sign-in cannot be seen there and *Edit text* (D192) would never appear to the staff who need it.
For staff who came from the admin, *Edit text* on such a page is now a short visit to the admin: the admin checks, as *Edit page* does, that the person may change the store's website and sends the browser back to the store's host with a signed link token (ninety seconds, store and account, good for the exchange only); the store's host swaps it for a pass, an HttpOnly cookie of that host for half an hour that the editing routes (and nothing else) accept, and the page opens in editing.
The pass is looked up again at every use, so removing a member, ending a collaborator's time or closing the store ends it at once; *Done editing* ends it on the spot. It is a deliberate, narrow exception to P7: a script on a store's page cannot read the pass, but while one is valid a script on that page can ask the editing routes to change the words of headings and texts, which is all the pass opens (nothing of the admin, no code, no other content).
The second step is checked when the pass is given and not again for the half hour.

Date: 2026-10-10

Needed by D192's wording ("as long as I am logged in") on the stores the owner actually uses. No migration; the key is the existing `SETTINGS_ENCRYPTION_KEY`. `edit-grant.test.ts` holds the tokens, `edit-pass.int.test.ts` the lookup at each use and `page-text-edit.int.test.ts` the routes' rules with a pass; `e2e/inline-edit-live.spec.ts` the refusals; the button, the visit to the admin, the return and *Done editing* were driven in a real browser against stand-ins for the admin and the routes.
Not yet tried on a real store domain with a real sign-in.
