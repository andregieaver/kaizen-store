# D453: Tripletex

**Tripletex: a store's books follow it, set up with one paste (proposed 29 September 2026 as `docs/tripletex.md`, re-planned and started 4 November 2026; built: the rules, the two tables, the client, the sync, the page, PDFs attached, the checkup and the daily alert, and Tripletex on Work; the AI manager's tools wait for a new eval run).** *What is sent:* every issued Work invoice and credit note and every shop invoice and credit note (D159), in Norwegian kroner, each as one Tripletex ledger
voucher: the receivable on a customer for the total, and one income posting per line (a shop credit note per VAT bucket) with the line's VAT code, so Tripletex, which works VAT out of each gross amount, lands on the VAT charged. Kaizena Flow's number stays the invoice's only number: it is the voucher's external number (`kf/{store8}/{number}`, looked up before every retry so a lost answer is adopted, never booked twice) and the receivable's invoice number.
A Work client is a customer of its own (a consumer: name and country only); a shop order from a business with a Norwegian organisation number is that business; every other shop order goes on one customer per store, *Online shop customers*, so no shopper's name reaches the books. A gift card sold goes to a debt account, not income. Other currencies, IOSS and any VAT kind without a place wait visibly for a person. Payments are not read back yet. *Set up for Homer:* the owner pastes one token.
Its kind and environment are read from the token itself (`tlxr_` is the company's own API token; anything else is an employee token for the app Kaizena Flow, used with Kaizena Flow's consumer token, `TRIPLETEX_CONSUMER_TOKEN` and `TRIPLETEX_TEST_CONSUMER_TOKEN`, environment variables like every other app credential; `test-` is Tripletex's test environment), so the owner chooses neither. The company is read (`whoAmI`) and compared with the store's organisation number.
Accounts and VAT codes are chosen from the company's own chart (`planSetup()`: Norway's standard where it fits, else the nearest account that takes the code and asks for no department, project or dimension), and the owner is asked only what cannot be chosen, then presses Start; nothing issued before that day is sent unless the owner picks an earlier day.
Customise holds every account, code, the voucher type, language, the start day and the switches. *Kept:* `commerce.tripletex_connections` (one per store, the token encrypted, one company per store) and `commerce.tripletex_sync` (one row per object and company: state, Tripletex's id, external number, attempts; kept on disconnect so a reconnect never books twice); both RLS on, never copied, no person's data.
Not a row of `store_integrations`: Tripletex is not a webhook. *Needed outside the code:* Kaizena Flow's application for a Tripletex consumer token (2 to 3 weeks), Tripletex's developer terms, a test company for the sandbox checks (`docs/tripletex.md` Appendix A), the accountant's sign-off on vouchers and the default accounts and codes, and Tripletex's hosting region in the residency register before live data is sent.
