# D504: Receipts by email

**Receipts by email: the books' inbox (subscriptions step 3, 8 November 2026, `commerce.books_email`, `commerce.books_inbox`, `src/lib/books-inbox.ts`, `src/server/books-inbox.ts`, *Receipts by email* on Settings → Books).** Step 3 of the owner's ask (D502): a subscription's invoice comes by email, so each store gets a books address, `books-{key}@` the receiving domain (D332, the same Resend receiving as the support desk and the filing address, D476; made the first time the Books screen asks,
a random key). The owner forwards receipts to it, or better gives it to Anthropic, Vercel or Supabase as the address their invoices go to. Each PDF or picture attached (not a picture inline in the mail, such as a logo; no larger than a voucher, 3 MB; its type read from its first bytes) is kept in the private `documents` bucket as a document waiting in the inbox; the same file twice is kept once, at most 100 a day per store.
Mail from a supplier's billing system is taken (it is a machine's by nature); mail that fails DMARC is not.
A waiting document is offered with the bank line it most likely is (`inboxMatches()`: within ten days, carrying the line's subscription's word, D503, or else the charge's first word of four letters or more, the nearest first, each document to one line): the line's receipt form opens with the document chosen in *Or a receipt from your email*, so a subscription's charge is posted with one press, its document the entry's voucher (D490); the document is then `used` and its inbox file goes (the
voucher keeps its copy). The owner can open any waiting document and set aside one that is not for the books. Nothing is posted by mail alone. A document changes only once (used or set aside) and is never deleted (a trigger). `support_inbound_emails.purpose` takes `books`. Kaizena Flow's own store has the same (D466).
