# D863: Each working store page loads its own parts

**Each working store page loads its own parts (bloat review step 2.9; 20 November 2026).** A built working page (the cart, checkout,
order, My account, wishlist, deliveries, subscription, cookie list, a category, tag or search listing, the private landing page)
draws the shop's parts through its route's own parts module (`cart-parts.tsx`, `checkout-parts.tsx`, ... on `storePartDrawer()`,
`src/components/store-part-frame.tsx`), which imports only that route's sections; the one switch that knew every working page is gone,
and `store-part-drawers.scan.test.ts` fails when a page draws a part its module lacks. The cookie list's settings button no longer
carries the consent manager. The shop's lazy stand-ins are one module per group under `src/components/lazy/` instead of one module
holding them all. `pay-routes.graph.test.ts` now walks through each pay route's parts module with no door to stop at. First scripts,
measured locally: a category, tag or search page 729,906 to 621,749 bytes (as the store's front page), My account 634,240, the
wishlist 622,192, the order 644,334, the cookie list 625,054, the checkout 668,938, all under the brief's 670,000; the cart 678,956,
8,956 over, because its own forms (discount code, gift card, Klarna, the VAT number) and its add-to-cart parts are pressed at once
and stay in the first scripts. `e2e/performance.spec.ts` holds the cart at 705,000 and the checkout at 694,000 (752,000 before).
