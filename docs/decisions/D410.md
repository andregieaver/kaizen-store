# D410: Rotating the settings key

**Rotating the settings key (PSI SEC-06).** A kept secret names its key: `v2.<kid>.<iv>.<tag>.<ciphertext>` (`src/lib/secret-box.ts`, `keyId()`: eight hex digits of the key's SHA-256, which says nothing of it); `v1.…` (no key id) is still read, with the current key and then the previous.
While `SETTINGS_ENCRYPTION_KEY_PREVIOUS` is set the server reads with both and writes with the current only, and the five-minute dispatcher's `secretRotation` job (`reencryptSecrets()`, `src/server/secret-rotation.ts`) writes up to 200 secrets a run again under the current key, each row changed only if it still holds what was read; outside a rotation it reads nothing.
The columns are found, not listed (every text column of `commerce` whose name says it may hold a secret, and in them only values in the box's format), so a new secret column is moved without being named; counts and column names are logged (`secrets.rotation`), never a value; a `v2` naming a key the server does not have is never picked.
Gift card and recovery codes are kept only as hashes and cannot be moved, so they take keys of their own, `GIFT_CARD_HASH_KEY` and `RECOVERY_CODE_HASH_KEY`, falling back to the keys made from the settings key; `scripts/hash-keys.mjs` prints those so they can be set once with nothing changing (`hash-keys.test.ts`). The procedure is `docs/runbooks/key-rotation.md`. New secrets are written as `v2` from a second push on the same day, once every running server read it (CI #786 deployed the reader).

Date: 2026-10-30

The PSI re-score's third improvement (SEC-06, critical). *Why found columns and not a list:* the breach runbook's hand list had already missed nothing only by care; a column added later would have kept the old key for good. *Why own hash keys and not re-hashing:* the codes are never kept, so a hash cannot be made again under a new key; a key of its own set to today's value changes no card.
