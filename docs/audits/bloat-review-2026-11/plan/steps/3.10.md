# Step 3.10: Run the platform's workflows, own endpoints and integration deliveries on the stores' engine with a scope

Phase 3 (One of each) of `docs/audits/bloat-review-2026-11.md`. Effort M. Read [how to carry out a step](../README.md) first.

**Who:** a stronger model. Commits 1 and 3 are specified moves held by six int tests that may not change, so the cheap model may make them; commit 2's scope is now spelt out to the clause, but it carries a store's owner filter into statements the ratchet cannot see, and commit 4 lifts 'the largest remaining runs' the counter prints until five pairs share under 60 lines, a measure-then-cut choice for the stronger model. A smaller model may still do commits 1, 3 alone. *(Rating checked twice, 12 November.)*

**Goal:** The stores' and the platform's workflows, own endpoints and integration deliveries run on one piece of code each, called with a scope (which tables, which owner filter); the platform keeps its own tables, addresses and every feature; and CLAUDE.md's parity rule says a platform version uses the store's module with a scope, not a copy.

**Why:** Today 26 to 55% of the platform's lines in these modules are the stores' own (209 shared lines in runs of three or more across five pairs; the claim statement `for update skip locked` is written once in each of workflows.ts and platform-workflows.ts), so a fix to retry or signing is made twice. After: the claim is in src/server/workflow-engine.ts only and the five pairs share under 60 lines.

**Decided by the owner (12 November, the recommended way):** Twins on shared code: the platform keeps its four engines and their tables, and this step is built (the finding says to keep them unless one engine is wanted, and it is the smaller change). Yes, CLAUDE.md's parity rule gets the sentence: where the platform's version does the same job on its own rows, it uses the store's module with a scope, not a copy.

### Commit 1 of 4: Workflow runs are claimed and run by one engine, with a scope for the stores and one for the platform *(a smaller model may do this one alone)*

- **create** `src/server/workflow-engine.ts`: A new server-only module (`import "server-only"`). It holds the part of runWorkflows() (src/server/workflows.ts, from `const claimed = await typedRows(` to the final `return`) and of runPlatformWorkflows() (src/server/platform-workflows.ts, the same span) that is the same in both. Export a type `WorkflowScope<Run>` with these members, and nothing read from a string: `runs: SQL` and `flows: SQL` (the two table names as drizzle sql fragments written in code, for example sql`commerce.workflow_runs` and sql`commerce.workflows`; never sql.raw), `returning: SQL` (the columns the claim's update returns, each prefixed `r.`), `select: SQL` (everything after `select c.*, w.name, w.conditions, w.actions` up to the end of the statement: the extra columns and the joins), `row: z.ZodType<Run>` (the zod object for one claimed row; it must include id, workflow_id, event, subject_id, name, conditions, actions), `payloadOf: (run: Run) => Promise<Record<string, unknown> | null>` (the event's facts for every event, 'schedule' included: {} for a schedule, null when the subject is gone or the owner is not open; the engine never decides this itself), `allowedActions: (event: string) => readonly string[]`, `act: (run: Run, action: WorkflowAction, index: number, data: Record<string, unknown>) => Promise<ActionOutcome>`, `logPrefix: string` ('workflows' or 'platform_workflows') and `logFields: (run: Run) => Record<string, unknown>`. Export `async function runQueued<Run>(scope: WorkflowScope<Run>, limit: number): Promise<{ runs: number; matched: number }>`. Its body, in this order, is the stores' code with the scope's parts put in: (1) the claim statement exactly as today: `with due as (select r.id from ${scope.runs} r where r.status = 'pending' and (r.claimed_until is null or r.claimed_until < now()) order by r.created_at limit ${limit} for update skip locked), claimed as (update ${scope.runs} r set claimed_until = now() + interval '5 minutes' from due where r.id = due.id returning ${scope.returning}) select c.*, w.name, w.conditions, w.actions ${scope.select}` read through typedRows(scope.row, ...); (2) the loop: for each run, data = await scope.payloadOf(run); matched = data !== null && workflowMatches(conditions, data); for each action, 'invalid' when not in scope.allowedActions(run.event), else scope.act(...) with the catch that logs `${scope.logPrefix}.action_failed` and returns { kind, ok: false, problem: 'failed' }; (3) the outcome update on ${scope.runs} with the same status, matched, outcome JSON, finished_at and claimed_until = null, `where id = ${run.id}::uuid`; the per-run catch logs `${scope.logPrefix}.run_failed`; (4) `delete from ${scope.runs} where created_at < now() - interval '90 days'`; (5) the return. Import workflowMatches, WorkflowAction, WorkflowCondition and ActionOutcome from where workflows.ts imports them.
