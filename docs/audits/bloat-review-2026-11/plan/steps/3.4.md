# Step 3.4: Give every daily function a ledger row of its own

Phase 3 (One of each) of `docs/audits/bloat-review-2026-11.md`. Effort M. Read [how to carry out a step](../README.md) first.

**Who:** a smaller model; a stronger one reads the diff before the push. The conversion is mechanical and held by a source scan and an int test, but it rewires the GDPR retention run and 40 jobs in one file and replaces cron_due() by migration, so a stronger model should read the diff before the push.

**Goal:** Every function the daily route calls is a registry entry with its own ledger row daily.<name> at 86,400 s; one that throws no longer stops the others, a prune reports its own failure, and a daily job that failed or was not reached is tried again the same day, at most three times.

**Why:** The 40 daily functions share 2 ledger rows and 19 of them catch their error to the console (rg -o 'console.error' src/app/api/cron | wc -l prints 19), so a prune that fails every day is not seen. After the step: one row per function and 0 console.error under src/app/api/cron.

**Closes:** [CR-17](../../findings/scheduled-work/CR-17.md), GAP-scheduled-s6. Each finding's file has the evidence.

## Migration

Two files. Generated (pnpm db:generate): commerce.cron_jobs gains day date and day_tries integer not null default 0 (a small table, not hot). Custom: replaces commerce.cron_due() with one more row for the daily route's same-day retry. Running code keeps working: old code ignores the two columns, and until the new route is live a retry call simply runs the old route once more, which the old route tolerates only because each reminder goes once whoever calls; to be safe, ship the route change and the migration in the same push (CI applies the migration first, the deploy follows within minutes, and cron_due() names the daily route only after 07:30 UTC, so push outside 07:00 to 09:00 UTC). ## Stop and report if

- runRegistry() does not exist (step 3.3 not done), commerce.cron_due() does not exist (3.1 not done), or vercel.json still schedules /api/cron/subscription-reminders (1.22 not done).
- Two daily functions depend on each other's result in a way the registry's order cannot keep (read lines 61 to 79 for a value passed from one call to the next).
- commerce.visits or commerce.product_views has no index starting with (store_id, day): the exists() would scan.
- The budgets of the daily registry add up to more than 960,000 ms.
- After the first production run a daily job shows failures: that is the step working; report the job and its last_error, do not catch the error again.
