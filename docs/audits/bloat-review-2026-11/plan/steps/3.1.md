# Step 3.1: Run one tick a minute, and call a route only when work waits

Phase 3 (One of each) of `docs/audits/bloat-review-2026-11.md`. Effort L. Read [how to carry out a step](../README.md) first.

**Who:** a smaller model; a stronger one reads the diff before the push. Commit 1 changes queue claims in three runners with int tests and touches no money or permissions; commit 2 is a migration that replaces production's scheduler, and its cron block is skipped in PGlite and CI's Postgres, so no check runs the real tick command, and a predicate copied narrower than its claim would pass every test, so a stronger model should read the migration before the push. A smaller model may still do commit 1 alone. *(Rating checked twice, 12 November.)*

**Goal:** pg_cron runs one job a minute, commerce.cron_claim_tick(), which posts to a cron route only when its queue holds claimable work, and to every route once in 15 minutes as a sweep; the six queue routes and their runners send at most 3 statements when idle and take no lock before asking.

**Why:** Nine routes are called every minute whether or not anything waits: 12,960 calls a day of full-application functions (three carry Chromium) and about 13,250 rows a day in cron.job_run_details. After the step: 1 every-minute schedule, about 1,750 log rows a day, and route.page-jobs runs at most 100 times on a quiet day (1,440 today).

**Closes:** [CR-1](../../findings/scheduled-work/CR-1.md), [CR-7](../../findings/scheduled-work/CR-7.md), [DQ-1](../../findings/queries/DQ-1.md), [DP-7](../../findings/dependencies/DP-7.md), [SF-10](../../findings/server-functions/SF-10.md), GAP-scheduled-s1. Each finding's file has the evidence.

## Migration

One custom migration (drizzle-kit generate --custom --name cron_tick, then node scripts/prune-snapshots.mjs): two functions in schema commerce (cron_due, cron_claim_tick) and a guarded DO block that schedules kaizen-tick and unschedules the nine every-minute jobs. No table is altered and no index built (the six predicates are served by page_ai_jobs_waiting_idx, page_looks_queue_idx, dream_runs_due_idx, theme_shots_queue_idx, cookie_scans_one_active_idx; store_starters is a small platform table), so the hot-table rules do not apply. Running code keeps working: the routes and their addresses are the same before and after, and the first commit (already deployed) made them correct when called rarely. CI applies it after every check passes and before the deploy (docs/ci-migrations.md); never apply it by hand. After the deploy check the Supabase security and performance advisors for project ybsozesfuxuitoacntfo and record the file's version in docs/decisions.md under Migration versions.

## Do not

- Do not edit a baseline migration file. The nine old schedules are removed by cron.unschedule in the new file.
- Do not unschedule kaizen-cart-reminders, kaizen-subscription-reminders, kaizen-usage or the two retention jobs.
