# Step 1.7: Put a cart with products and the checkout's payment step into the measured set

Phase 1 (Budgets, so it stays removed) of `docs/audits/bloat-review-2026-11.md`. Effort M. Read [how to carry out a step](../README.md) first.

**Who:** a stronger model. It touches the payment path's client set-up and needs design choices the brief cannot make without running the checkout: how the fixture store gets a key, which Stripe calls the stand-in must answer, and how much of Stripe.js the browser stub needs.

**Goal:** The end-to-end build can show a cart with two lines and the checkout at its payment step against a payment stand-in, and e2e/performance.spec.ts holds for both: first scripts, the document, router requests after load, and third-party requests and bytes; both pages are in measure-routes.mjs.

**Why:** The cart was measured empty (591,352 bytes on the wire) and the checkout's load ended on the cart because the demo store takes no payments, so the money path has no figure with anything in it. After: both pages have first figures held within 5%, 0 router requests while the payment form shows and the payment provider's script as the only third-party request.

**Closes:** GAP-shopper-browser-2. Each finding's file has the evidence.
