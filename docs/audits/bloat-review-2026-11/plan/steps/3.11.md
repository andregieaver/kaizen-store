# Step 3.11: Fold order rules into Workflows

Phase 3 (One of each) of `docs/audits/bloat-review-2026-11.md`. Effort M. Read [how to carry out a step](../README.md) first.

**Who:** a stronger model. Commit 1 is now placed in 3.10's engine and store scope with no fallback, but the step still maps the 13 rule condition kinds to workflow facts, designs an editor from a description, copies the hot commerce.queue_integration_event function by hand, changes when the new-order alert is claimed, removes an AI tool (eval re-record) and drops two production tables, which needs a stronger model's judgement throughout. *(Rating checked twice, 12 November.)*

**Goal:** One engine decides what happens when an order is paid: Workflows has the hold action, 'any' matching and the order facts; order rules ('Automation'), their four pages, their AI tool and, one release later, their two tables are gone.

**Why:** Today two engines do this job: order rules are about 1,900 lines, 4 pages, 2 tables and 1 AI tool beside Workflows, with two editors, two logs and two links under Settings. After: `find src -iname '*order-rule*' | wc -l` prints 0 (5 today) and the store navigation has no /settings/automation link.

**Decided by the owner (12 November, the recommended way):** Yes. Order rules fold into Workflows, so one engine decides what happens when an order is paid, as the surface's card proposes. It is cheapest now, while no owner has a rule to convert.

**Closes:** [FT-8](../../findings/features/FT-8.md). Each finding's file has the evidence.
