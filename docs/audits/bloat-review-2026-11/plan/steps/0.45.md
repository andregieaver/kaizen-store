# Step 0.45: Cap the dispatcher at four jobs at a time

Phase 0 (Before the doors open) of `docs/audits/bloat-review-2026-11.md`. Effort S. Read [how to carry out a step](../README.md) first.

**Who:** a smaller model alone. One small pure function with a full fake-timer unit test, a one-line change in runJobs() with two int cases, and a docs sentence with one fixed place; the tests catch a wrong pool and nothing touches money, data or permissions. *(Rating checked twice, 12 November.)*

**Goal:** runJobs() in src/server/cron-runs.ts runs the dispatcher's jobs at most four at a time, and a job that has run for 60 seconds gives its lane to the next job while it goes on and is still recorded when it ends.

**Why:** Today runJobs() starts all 78 dispatcher jobs at once with Promise.all on a pool of 5 database connections with a 5 s wait, so the first slow job makes others fail with 'timeout exceeded when trying to connect'. After: never more than 4 jobs hold a lane, and four hung jobs cannot stop the rest.

**Closes:** GAP-database-s3. Each finding's file has the evidence.

## The work

### Commit 1 of 1: The dispatcher runs four jobs at a time, and a job past 60 s gives up its lane

- **create** `src/lib/job-pool.ts`: A pure module (no imports but types; no 'server-only'). Export async function pooled<T>(tasks: readonly (() => Promise<T>)[], options: { lanes: number; laneMs: number; onLaneGivenUp?: (index: number) => void }): Promise<T[]>. Behaviour: results is an array of promises, one per task, in the tasks' order. A shared counter next starts at 0. A lane is an async loop: while next < tasks.length: take i = next++; start the task with const run = Promise.resolve().then(tasks[i]) and store results[i] = run; then wait for whichever comes first: the task settling (run.then(() => 'done', () => 'done')) or a timer of laneMs milliseconds (a setTimeout whose handle is cleared with clearTimeout as soon as the task settles first); when the timer came first call options.onLaneGivenUp?.(i) once and go on to the next task WITHOUT waiting for the slow one (it keeps running and its promise stays in results). Start Math.max(1, Math.min(lanes, tasks.length)) lanes and await them all (Promise.all); then return Promise.all(results). So: at most `lanes` tasks that have run for less than laneMs are running at any time; a task that rejects makes the returned promise reject, as Promise.all did (runJobs' tasks never reject, because tracked() catches); a task that never settles means the returned promise never settles, but every other task is still started and finished. An empty list returns []. Doc comment: why (the pool of database connections), and that step 3.3 of the bloat review adds cadences and time budgets on top.
- **create** `src/lib/job-pool.test.ts`: Vitest unit test, fake timers (vi.useFakeTimers(); advance with await vi.advanceTimersByTimeAsync(ms)). Helper: a task factory that records running++ at start, tracks the highest value seen (peak), and resolves after a given number of milliseconds (setTimeout) with running--. Cases: (1) 'never more than four at once': 20 tasks of 100 ms each, lanes 4, laneMs 60_000: after advancing 1,000 ms the promise resolves with 20 results in order and peak is 4. (2) 'a job that throws does not stop the others': tasks whose index 3 rejects, each wrapped as runJobs wraps them (the test wraps every task in async () => { try { return await t(); } catch { return null; } }): all 20 finish, result[3] is null. (3) 'a job that never returns gives up its lane after laneMs': 10 tasks, index 0 never resolves (new Promise(() => {})), lanes 2, laneMs 1,000, the others take 100 ms: after advancing 5,000 ms the other 9 have all finished (count them with a finished counter), onLaneGivenUp was called once with 0, and the pooled promise is still pending (track with a flag set in .then). (4) 'four hung jobs cannot stop the run': 4 tasks that never resolve followed by 6 quick ones, lanes 4, laneMs 1,000: after 3,000 ms all 6 quick ones have finished. (5) lanes larger than the list, and an empty list, work. Restore real timers in afterEach.
