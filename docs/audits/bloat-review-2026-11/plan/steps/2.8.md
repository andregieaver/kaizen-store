# Step 2.8: Bound what a real listing fetches ahead, and decide partial prefetching by trial

Phase 2 (Load on demand) of `docs/audits/bloat-review-2026-11.md`. Effort M. Read [how to carry out a step](../README.md) first.

**Who:** a smaller model; a stronger one reads the diff before the push. The code change, the seed and the budget are fully specified and the tests catch a wrong edit, but the trial's table and the sentence that decides between the first-screen rule and a shared shell should be read by a stronger model before the decision row is pushed.

**Goal:** On a full listing only the first screen of product tiles is fetched ahead on sight and the rest when touched, swatch links wait for intent, a seeded 48-product category read to the end on a phone makes at most 20 router requests, and docs/performance.md and docs/decisions.md hold the partial-prefetching trial on four pages with the decision it led to.

**Why:** Today a real listing prefetches every product tile and up to six swatch links under each: about 96 router requests for 48 products, which no test sees because the test stores have 10 products. After: at most 20 for the same listing, held by e2e/prefetch.spec.ts.

**Decided by the owner (12 November, the recommended way):** Yes. On a full listing only the first screen of product tiles is fetched ahead on sight and the rest when touched, and on a computer the main menu's links wait for the pointer (step 2.6 sets that policy); the critic says the shopper's browser needs this for an A. The trial decides whether one shared product shell replaces the rule; without a clear gain the first-screen rule stands, since it needs no router setting.

**Closes:** [PF-13](../../findings/prefetching/PF-13.md), [PL-5](../../findings/page-payload/PL-5.md), [PF-9](../../findings/prefetching/PF-9.md). Each finding's file has the evidence.
