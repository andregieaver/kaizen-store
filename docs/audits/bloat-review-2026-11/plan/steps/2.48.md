# Step 2.48: Give a placed order a ceiling, and stage placeOrder where the first figures are over it

Phase 2 (Load on demand) of `docs/audits/bloat-review-2026-11.md`. Effort M. Read [how to carry out a step](../README.md) first.

**Who:** a smaller model; a stronger one reads the diff before the push. The ceilings are fully specified test cases, but the two conditional commits change how an order's lines and triggers are written, so a stronger model must read those diffs before the push.

**Goal:** The write budget of step 1.12 asserts five ceilings for one placed order (same statements with 10 and 2,000 earlier orders; at most 3 more per added line; triggers under a fifth of the order's database time; a counted visit at most 3 statements and 2 rows; optional features' triggers under 2 ms on a shop-only store), and placeOrder is staged only where a measured figure is over one.

**Why:** Step 1.12 counts what one placed order writes but sets no ceiling and nobody has judged the count; code review step 3.7 (Stage placeOrder) is open. After this step each figure has a line in docs/performance.md and a failing test behind it.

**Closes:** GAP-database-s7, GAP-surface-s5. Each finding's file has the evidence.

- **create** `src/server/shop-journey.int.test.ts`: The real file is the int test step 1.12 made; its name may differ. Find it: rg -l 'placeOrder' src/server -g '*.int.test.ts' | xargs rg -l "features|\['shop'\]" , and check the Progress table's row for step 1.12, which names it. Use THAT file; do not create this one if another exists (if none exists, stop). Do not overwrite it. First read the figures it already records for placeOrder (statements, rows written, tables touched) and print them. Then add one describe block 'a placed order's ceilings' with five cases, all on the counter of step 1.9 (src/db/client.ts): (1) Seed store A with 10 earlier orders and store B with 2,000 (insert them with the test file's own seeding helper, in batches); place one identical one-line order in each through the same function the journey uses; expect the two statement counts to be equal. (2) Place a one-line, a two-line and a five-line order; expect statements(n lines) - statements(1 line) <= 3 * (n - 1). (3) Trigger time: around one placed order run `set local track_functions = 'all'` in the session if the test database allows it and read pg_stat_user_functions (calls, total_time) before and after for functions in schema commerce, after `select pg_stat_force_next_flush()`; expect the summed total_time of trigger functions to be under 20% of the order's whole database time (the sum of the counter's statement durations). (4) One counted visit (the function the /api/visit route calls; find it: rg -n 'export async function' src/server/analytics-visits.ts | head): at most 3 statements and at most 2 rows written. (5) A store with features ['shop'] only: the triggers of optional features (bonus, gift cards, affiliates, creators, standing orders, bookings, suppliers: those whose function body reads a table of a switched-off feature) take together under 2 ms of one paid order, by the same pg_stat_user_functions difference. Each expectation's failure message names the figure and says: lower the cost or do code review step 3.7 for that part; never raise the ceiling.

## Migration

Only if the 2 ms line fails. A custom migration (drizzle-kit generate --custom, then node scripts/prune-snapshots.mjs) that replaces trigger functions with the same body plus a first-line test of the store's feature switch. It touches functions only: no table is altered, no index built, so the hot-table rules do not apply although the triggers fire on commerce.orders. Running code keeps working because a store with the feature on gets the same behaviour. CI applies it after the checks pass; never apply it by hand; afterwards check the Supabase advisors and record the version in docs/decisions.md under Migration versions.

## Do not

- Do not raise or remove a ceiling to make the test pass, and do not skip a case other than case 3 on a database that cannot time functions.
- Do not stage placeOrder where no figure is over its ceiling: no multi-row insert and no migration 'while we are here'.
- Do not drop, disable or rename a trigger; do not change what a trigger writes for a store that has the feature on.
- Do not alter commerce.orders or commerce.order_lines (hot tables) and do not add an index in this step.
- Do not change insertOrderLine's signature: three other writers call it.
- Do not apply the migration to production by hand.

## Stop and report if

- The int test of step 1.12 cannot be found, or the Progress table does not show 1.12 and 1.9 as Done.
- Case 1 fails (statements differ between 10 and 2,000 earlier orders): that is a read that grows with history; report the differing statements, do not fix it blind.

- A trigger function to gate reads the feature switch from somewhere other than commerce.stores.features, or the function is security definer with a search_path you would have to change.
- Any checkout int test or e2e/cart.spec.ts fails after a staging commit.
