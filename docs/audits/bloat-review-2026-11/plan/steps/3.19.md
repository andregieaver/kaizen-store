# Step 3.19: Let a burst of pushes share one deploy

Phase 3 (One of each) of `docs/audits/bloat-review-2026-11.md`. Effort S. Read [how to carry out a step](../README.md) first.

**Who:** a smaller model; a stronger one reads the diff before the push. The script and the two `if:` conditions are fully specified, but a mistake here leaves a commit undeployed with a green run, so a stronger model should read the ci.yml diff before it is pushed.

**Goal:** A CI run on the no-migration path skips its deploy when a newer push that will itself deploy is already on main, so a burst of pushes shares one production deploy; a run that applied a migration always deploys; the repository variable SHARE_DEPLOYS set to 'false' turns the skip off.

**Why:** Each deploy empties every store's cached pages and starts every function cold, and 11 November had up to 52 deploys. Today two pushes one minute apart make two production deploys; after this step they make one, and /api/health reports the second commit.

**Decided by the owner (12 November, the recommended way):** Yes. A CI run on the no-migration path skips its deploy when a newer commit is already on main, so a burst of pushes shares one deploy; a run that applied a migration always deploys. It keeps stores' cached pages through a burst, and a repository variable turns it off.

**Closes:** [CA-2](../../findings/caching/CA-2.md). Each finding's file has the evidence.

## The work

### Commit 1 of 2: A burst of pushes shares one deploy: a run steps aside for a newer push that deploys

- **create** `scripts/lib/deploy-share.mjs`: A pure module (no imports). Export `deployable(files)`: given an array of repo-relative paths changed between two commits, return true when at least one of them would make a push deploy. A path does NOT count when it ends `.md` or starts `docs/`, unless it starts `content/` (the docs portal's articles deploy: this mirrors the `paths` filter at the top of .github/workflows/ci.yml). If step 0.38's tests-only skip is in the pending job, open it, read its rule for 'only tests changed' (its script or inline shell), and make deployable() also return false for a list in which every path matches that same rule; import 0.38's function if it is a module, do not write a second copy of the pattern. Export `superseded({ sha, head, changed, share })`: returns false when share is the string 'false'; false when head equals sha; otherwise deployable(changed).
- **create** `scripts/deploy-share.mjs`: A Node script (ES module, node:child_process execFileSync, node:fs appendFileSync). It reads GITHUB_SHA and SHARE_DEPLOYS from the environment. Steps: `git fetch --depth=1 origin main`; head = `git rev-parse FETCH_HEAD`; if head differs from GITHUB_SHA, changed = lines of `git diff --name-only <GITHUB_SHA> <head>` (a two-dot diff of two commits both present in the clone; it needs no history). Call superseded(). Append `superseded=true` or `superseded=false` to the file named by GITHUB_OUTPUT (print it too when GITHUB_OUTPUT is unset). When true print: 'Main is at <head>, and what it adds will deploy: that push's run deploys main with this commit in it. This run asks for no deploy.' When false because nothing deployable was added, print: 'Main is at <head>, but nothing it adds deploys: this run deploys.' If any git command fails, write superseded=false (the safe side is to deploy) and print why.
- **edit** `.github/workflows/ci.yml`: Only in the job `pending`. Directly after the step with id `head` ('Is a migration pending at the head of main by now?') add: `- name: Is a newer push on main that will deploy it? (a burst of pushes shares one deploy)`, `id: newer`, the same `if:` as the head step (`steps.status.outputs.pending == 'false' && vars.DEPLOY_VIA_CI == 'true'`), `env: SHARE_DEPLOYS: ${{ vars.SHARE_DEPLOYS }}`, `run: node scripts/deploy-share.mjs` (wrapped in the recorder of step 1.20 if the job's other steps are). Then add `&& steps.newer.outputs.superseded != 'true'` to the `if:` of the two steps after it: the deploy step ('No migration to apply and the quick gate passed, so ask Vercel to deploy the head of main now', or the vercel build/deploy steps step 1.21 put in its place) and 'Wait until production runs this commit'. If step 0.38 added its own condition to those two `if:` lines, keep it and add this one with `&&`. In the comment block above the job ('no pending migration: ...') add two lines: a run whose commit has been followed on main by a push that will deploy asks for no deploy (the newer run deploys main, with this commit in it; SHARE_DEPLOYS = 'false' turns this off), and a run that applied a migration always deploys. Change nothing in the jobs `release`, `redeploy`, `baseline`, `static` or the browser jobs, and nothing in `concurrency`.

Cases: deployable(['README.md', 'docs/plan.md']) false; deployable(['content/docs/x.md']) true; deployable(['src/lib/money.ts']) true; if 0.38's tests-only rule exists, deployable(['src/lib/money.test.ts']) false; superseded with head equal to sha false; with share 'false' false even for a deployable change; with a deployable change true; with only docs changed false. ## Do not

- Do not add the skip to the `release` job: a run that applied a migration always deploys.
- Do not skip when the newer commits are words only (*.md, docs/**) or tests only: no run would then deploy this commit.
- Do not make a skipped run wait on /api/health, and do not make it fail: it ends green with the sentence.
- Do not change `concurrency`, cancel runs on main, or add a job: the gate stays one job, one runner to wait for.
- Do not move reads to 'use cache: remote' or unstable_cache in this step (the finding says why: remote entries do not survive a deploy either).
- Do not use a paid Vercel or GitHub feature (no Rolling Releases, no larger runner, no paid monitoring).
