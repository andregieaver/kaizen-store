# Step 3.20: Show how long due work waits, and say so when it is too long

Phase 3 (One of each) of `docs/audits/bloat-review-2026-11.md`. Effort S. Read [how to carry out a step](../README.md) first.

**Who:** a smaller model; a stronger one reads the diff before the push. The function's branches (each table, its unfinished rows and its time column, pack-pictures and the excluded feature routes included), the limits, the table, the email and the watcher's one edit are specified, but a wrong 'not finished' line hides the very fault this step is for and the step adds a migration and an alert email, so a stronger model reads the SQL before the push. A smaller model may still do commit 3 alone. *(Rating checked twice, 12 November.)*

**Goal:** A SQL function beside commerce.cron_due() returns, for each gated queue, how long its oldest unfinished row has waited; the outside watcher reads it every 15 minutes, emails the platform admins when a queue a person watches is over 3 minutes or another over 20, and keeps each queue's worst wait of the day, which Platform, Usage and limits shows.

**Why:** After step 3.1 a route is called only when a predicate finds work, so a wrong predicate makes work start up to 15 minutes late (at the sweep) and nothing says so: the wait is not measured today. After: the wait of every gated queue is measured every 15 minutes, with limits of 3 and 20 minutes and an email over them.

**Decided by the owner (12 November, the recommended way):** 3 minutes for work a person watches (an AI page build, a look at a page, the Dream Factory) and 20 minutes for the other queues, as the step and the scheduled card assume. Both are constants in one file, so another figure is a one-line change.

**Closes:** GAP-scheduled-s4. Each finding's file has the evidence.

## The work

### Commit 1 of 3: commerce.cron_waits(): each gated queue's oldest unfinished row, by a condition wider than the tick's

- **create** `src/lib/queue-waits.ts`: A pure module. Export `WATCHED_MINUTES = 3` and `OTHER_MINUTES = 20` (the two limits; another figure is a one-line change here). Export `WATCHED_QUEUES: readonly string[] = ["page-jobs", "page-looks", "dream-factory"]` (work a person watches: AI page builds, looks at a page, the Dream Factory). Export `limitSeconds(queue: string): number` (WATCHED_MINUTES * 60 for a watched queue, else OTHER_MINUTES * 60), `overLimit(queue: string, seconds: number | null): boolean` (false for null) and `type QueueWait = { queue: string; seconds: number | null; waiting: number }`.
- **create** `supabase/migrations/*_cron_waits.sql`: A custom migration (`pnpm exec drizzle-kit generate --custom --name cron_waits`, then `node scripts/prune-snapshots.mjs`) with one statement: `CREATE OR REPLACE FUNCTION commerce.cron_waits() RETURNS TABLE (queue text, seconds integer, waiting integer) LANGUAGE sql STABLE SET search_path TO ''` whose body is one `select ... union all select ...` with one branch per queue that commerce.cron_due() gates. First open the newest definition of commerce.cron_due() (`rg -l 'FUNCTION commerce.cron_due' supabase/migrations | sort | tail -1`) and list its queues and the table each reads. Each branch returns the queue's name exactly as cron_due() names its route, `extract(epoch from now() - min(<last change>))::int` as seconds (null when no row) and `count(*)::int` as waiting, over the rows of the queue's table that are NOT FINISHED. The rule for 'not finished' is the point of this step: use only the row's status (every status that is not an end state) and never the conditions cron_due() uses to decide a row is claimable (no `claimed_until`, no `tries <`, no `next_attempt_at <=`, no `last_attempt_at <`), so a row the tick's predicate wrongly skips is still seen here. `<last change>` is the table's updated_at where it has one, else created_at, so a long job that is advancing does not count as waiting. The six queues of step 3.1 are: 'page-jobs': commerce.page_ai_jobs where status = 'waiting', by updated_at; 'page-looks': commerce.page_looks where status in ('queued', 'running'), by created_at; 'dream-factory': commerce.dream_runs where status = 'running', by updated_at; 'theme-shots': commerce.theme_shots where status in ('waiting', 'running'), by created_at; 'cookie-scan': commerce.cookie_scans where status in ('queued', 'running'), by coalesce(started_at, created_at); 'pack-pictures': commerce.store_starters where pictures_wanted_at is not null (the table has no status column: runPackPictures() in src/server/content-packs.ts clears pictures_wanted_at when the pictures are done or given up, line 792 and 807), by greatest(updated_at, pictures_wanted_at), never reading picture_claimed_until or picture_failures. If cron_due() also names 'document-pdfs' (step 3.7 has landed), add its branch: invoices and credit notes with pdf_path is null and anonymised_at is null and fewer than 5 attempts in commerce.document_pdf_state, by issued_at, without the five-minute back-off. The three routes cron_due() names always or by feature, 'autopilot', 'broadcasts' and 'integrations' (step 3.2 gates them by its own due functions), get no branch: they have no single table of rows that wait, so they are not queues here. Grant nothing: the function is called by the server's own role, as cron_due() is.
- **create** `src/server/queue-waits.int.test.ts`: Cases against the seeded test database: (1) with no unfinished rows every queue returns seconds null and waiting 0, and the set of queue names equals `select route from commerce.cron_due(timestamptz '2026-01-05 09:00:00+00')` minus 'autopilot', 'broadcasts' and 'integrations' (at minute 0 of an hour cron_due() names every queue route, its sweep flag being true, whether or not a row waits); (2) insert a commerce.page_ai_jobs row with status 'waiting' and created_at and updated_at four minutes ago: 'page-jobs' returns seconds between 235 and 300 and waiting 1; (3) the wider condition: set that row's claimed_until to an hour from now and tries to 3 (so the tick's predicate would skip it): cron_waits() still returns it; (4) a row with status 'done' is not counted.

## Do not

- Do not copy cron_due()'s predicate into cron_waits(): the wait must be read by a wider condition, or it cannot see a predicate that is wrong.
- Do not count a row by created_at where the table has updated_at: a long build that is advancing must not alert.
- Do not email on every reading: one email per queue per clock hour, through the idempotency key.
- Do not call the queues' routes from the watcher or change commerce.cron_due() in this step.
- Do not add a paid monitoring service or Vercel's Observability Plus: the watcher is Vercel's one free cron and the email goes through the platform's own sender.
- Do not put a person's data in the email or the table: queue names, counts and seconds only.

## Stop and report if

- commerce.cron_due() is not in any migration (step 3.1 not done), or src/server/watchdog.ts with runWatchdog() does not exist (step 1.22 not done).
- A queue's table has no status column that tells finished from unfinished: list the queue and ask.
- The int test shows 'dream-factory' or 'page-jobs' over 3 minutes during a normal, advancing run (updated_at does not move while the work advances): report which column moves instead.
- commerce.cron_waits() takes more than 200 ms on the seeded test database.
