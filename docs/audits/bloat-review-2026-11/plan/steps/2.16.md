# Step 2.16: Keep a page's title and flags in columns

Phase 2 (Load on demand) of `docs/audits/bloat-review-2026-11.md`. Effort M. Read [how to carry out a step](../README.md) first.

**Who:** a smaller model; a stronger one reads the diff before the push. The schema lines, SQL and tests are given word for word, but it is a migration that rewrites a table, so a stronger model should read the generated SQL before the push.

**Goal:** commerce.pages has three stored generated columns (published_title, published_titles, remembered_modal) that the database fills for every writer, and publishedPageNames(), usesRememberedModals() and the page index read them instead of digging through page documents.

**Why:** Today menus pull titles out of each page's JSON (57,930 calls in 78 days) and the consent banner runs jsonb_path_exists over every published page of a site for one yes or no (68,878 calls, 121 s). After: both read plain columns; timed on 1,392 pages the title read falls from 1.5 ms to 0.8 ms and the modal check from 1.4 ms to 0.6 ms a call, and neither statement names a document.

**Closes:** [DS-4](../../findings/database-shape/DS-4.md), [PM-6](../../findings/page-builder-model/PM-6.md). Each finding's file has the evidence.

## Migration

Two files in the first commit. (1) Custom: commerce.page_titles(jsonb), an immutable SQL function with a fixed search_path (pnpm exec drizzle-kit generate --custom --name page_titles_fn, then node scripts/prune-snapshots.mjs). (2) Generated by pnpm db:generate from src/db/schema.ts: alter table commerce.pages add three stored generated columns. Add only: no rename, no drop, no backfill, no writer changes, so the code that is running keeps working while the deploy finishes (every insert into pages names its columns; the tests of the copy paths prove it). commerce.pages is not on the hot-table list, so no concurrent file is needed; adding a stored generated column rewrites the table under a lock, which is instant at about 1,400 rows and fits the 15 s statement limit and 5 s lock wait. No index is added. CI's release job applies both files after the checks pass; never apply them by hand. The readers (second commit) may ride in the same push: the release job applies the files before the deploy. They must never be pushed BEFORE the migration commit. After the deploy check the security and performance advisors of project ybsozesfuxuitoacntfo and record the versions.

## Do not

- Do not write the columns from application code, and do not add them to any insert or update: a generated column refuses a written value.
- Do not push the readers (commit 2) without, or before, the migration commit (commit 1).
- Do not rename, drop or change the type of draft, published or any existing column.
- Do not remove 'set search_path' from the function to make it inlinable.
- Do not change the JSON path of the modal rule; copy it from src/server/page-modals.ts as it is.
- Do not add an index in this step (the bar is statements that open no document; pages is filtered by its existing store index).
- Do not apply the migration to production by hand or with the Supabase tools.

## Stop and report if

- pnpm db:generate writes anything besides the three added columns.
- PGlite or Postgres refuses the generated column (for example 'generation expression is not immutable'): report the message; do not switch to columns written by the application.
- A test of a copy path (store copy, page duplicate, house site, design presets, starters, sandboxes, staging) fails with 'cannot insert a non-DEFAULT value into column': report the statement that copies without naming columns.
- CI's release job fails to apply either migration file: do not retry by hand; report the job's message.
- The plan test shows published or draft in a plan after the change.
