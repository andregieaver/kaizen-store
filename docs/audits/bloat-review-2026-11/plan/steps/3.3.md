# Step 3.3: Run the dispatcher from a registry: a cadence and a time budget per job

Phase 3 (One of each) of `docs/audits/bloat-review-2026-11.md`. Effort L. Read [how to carry out a step](../README.md) first.

**Who:** a stronger model. runRegistry() is concurrency and ledger code on top of two earlier rewrites of runJobs(), and filling the registry means a why, a work label and a budget per job read from each job's own code and its written promises (stop_if 3), which the brief can give as rules but not as a checked list; the cadence list, the files and the tests that follow the new entry shape are now named. *(Rating checked twice, 12 November.)*

**Goal:** The five-minute dispatcher runs from one registry in which every job names its cadence (300, 3,600 or 86,400 s) with a reason, how its work grows, and a time budget; a job runs only when due and when its budget fits, idle jobs share one ledger write, and the ledger shows each job's last real work.

**Why:** All 83 dispatcher jobs run every five minutes and each writes its own ledger row: at least 248 statements for an idle tick, and Kaizena Flow's payouts are read from Stripe 288 times a day. After the step at most 58 jobs have a 300 s cadence, an idle tick sends at most 125 statements whatever the number of stores, and payouts.list is called once per mode in an hour.

**Closes:** [CR-2](../../findings/scheduled-work/CR-2.md), [CR-8](../../findings/scheduled-work/CR-8.md), [DQ-5](../../findings/queries/DQ-5.md), GAP-scheduled-3, [CR-14](../../findings/scheduled-work/CR-14.md), GAP-scheduled-s3. Each finding's file has the evidence.
