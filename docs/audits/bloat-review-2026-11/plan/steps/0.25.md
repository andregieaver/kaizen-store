# Step 0.25: Prune the scheduler's own log

Phase 0 (Before the doors open) of `docs/audits/bloat-review-2026-11.md`. Effort S. Read [how to carry out a step](../README.md) first.

**Who:** a smaller model; a stronger one reads the diff before the push. The SQL is given whole and the text test now holds the file to it exactly, but it is a migration that deletes production rows and first runs in the release job, so a one-minute read of the diff against the brief comes before the push. *(Rating checked twice, 12 November; first written as cheap.)*

**Goal:** pg_cron's run log holds at most about eight days of rows: its backlog is emptied once and a daily pg_cron job deletes rows older than seven days.

**Why:** cron.job_run_details is 564 MB of the 731 MB database and nothing prunes it (about 13,250 rows a day). After the one-off emptying and a week of the daily prune the cron schema is under 80 MB (eight days of rows are 58 to 64 MB).

**Closes:** [CR-5](../../findings/scheduled-work/CR-5.md), [DS-8](../../findings/database-shape/DS-8.md). Each finding's file has the evidence.

## The work

### Commit 1 of 1: The scheduler's own run log is emptied once and kept to seven days

- **create** `supabase/migrations/*_cron_run_log_retention.sql`: Make the file with `pnpm exec drizzle-kit generate --custom --name cron_run_log_retention` (it writes an empty file with a new timestamp into supabase/migrations and adds it to the journal), then `node scripts/prune-snapshots.mjs`. Do not hand-pick the timestamp. Put exactly this SQL in the file, nothing else: -- pg_cron's own run log (cron.job_run_details) grows by one row a run and nothing pruned it: 564 MB of a 731 MB database on 11 November 2026. -- Emptied once here, then kept to seven days by a daily job. Nothing reads the log: the app's own ledger of jobs is commerce.cron_jobs. -- A database without pg_cron (the tests' PGlite, CI's Postgres) has no cron schema and skips all of it. DO $do$ BEGIN IF EXISTS (SELECT 1 FROM pg_namespace WHERE nspname = 'cron') AND EXISTS (SELECT 1 FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace WHERE n.nspname = 'cron' AND c.relname = 'job_run_details') THEN IF has_table_privilege(current_user, 'cron.job_run_details', 'TRUNCATE') THEN TRUNCATE cron.job_run_details; ELSIF has_table_privilege(current_user, 'cron.job_run_details', 'DELETE') THEN DELETE FROM cron.job_run_details WHERE coalesce(end_time, start_time) < now() - interval '7 days'; ELSE RAISE NOTICE 'cron.job_run_details: no right to truncate or delete; the backlog stays'; END IF; -- cron.schedule with a name replaces the job of that name, so this can run again. PERFORM cron.schedule('kaizen-cron-log-retention', '41 3 * * *', $job$ DELETE FROM cron.job_run_details WHERE coalesce(end_time, start_time) < now() - interval '7 days' $job$); END IF; END $do$; No `-- kaizen:no-transaction` line: no hot table is touched and the block must run as one unit. CI's runner gives a file 10 minutes per statement and a 30 s lock wait (scripts/db-migrate.mjs), which the one-off delete fits where TRUNCATE is not allowed.

## Migration

Custom (`pnpm exec drizzle-kit generate --custom --name cron_run_log_retention`, then `node scripts/prune-snapshots.mjs`). It touches only cron.job_run_details, which is pg_cron's own table and not one of the hot tables, so no concurrent index and no `-- kaizen:no-transaction` marker. It changes no commerce table, column or function, so the code that is running keeps working before, during and after. It is guarded: a database with no cron schema runs nothing. Push the file; CI's release job applies it after every check passes (a direct Postgres connection, 10 minutes a statement) and then deploys. Never apply it by hand first: CI would run it again. After the deploy check the Supabase advisors and record the version in docs/decisions.md.
