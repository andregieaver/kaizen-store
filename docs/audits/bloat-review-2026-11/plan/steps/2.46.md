# Step 2.46: Keep schemas apart from the helpers beside them, so zod loads only where a screen runs one

Phase 2 (Load on demand) of `docs/audits/bloat-review-2026-11.md`. Effort L. Read [how to carry out a step](../README.md) first.

**Who:** a smaller model; a stronger one reads the diff before the push. Each commit is a mechanical cut-and-paste held by the type check and the import walk, but it is many files and the schemas guard saved data, so a stronger model should read each diff for a changed rule or a value re-export.

**Goal:** zod reaches the browser only on screens that run a schema: every src/lib file an admin client component imports for a helper or a constant has its schema in a file of its own beside it, and admin-bundle.scan.test.ts names each client module that may reach zod.

**Why:** After step 0.9 'ZodError' is still in the first-load chunks of about 144 admin routes (432 today) though 4 of 332 admin client files call a schema; the target is at most 60 routes, and the product editor at or under 1,100,000 bytes (2,130,796 today).

**Closes:** GAP-owner-browser-s1. Each finding's file has the evidence.

## Do not

- Do not re-export a schema file from its helper file (no `export * from './x-schema'`, no value re-export): that puts zod back on every importer.
- Do not change a schema's rules, messages or limits while moving it. Cut and paste only.
- Do not replace zod validation in a client component by hand-written checks to get it off the list; a screen that runs a schema is allowed, by name.
- Do not move schemas out of files under src/server or src/db: this step is about src/lib files that client components import.
- Do not add a module to the 'only shrinks' list of step 1.4 at any point.
- Do not edit src/db/schema.ts beyond the import path: pnpm db:check must show no schema change.
