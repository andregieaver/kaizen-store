# Step 3.17: Keep one stored page shape

Phase 3 (One of each) of `docs/audits/bloat-review-2026-11.md`. Effort M. Read [how to carry out a step](../README.md) first.

**Who:** a stronger model. Commit 1's decisive part is still an inventory the brief cannot give (tracing about 28 more callers to the tables and jsonb columns that hold page JSON, nested ones included), commit 2 rewrites production JSON, and commit 3, though mechanical, is safe only if commit 1 missed no holder. *(Rating checked twice, 12 November.)*

**Goal:** Every stored page document equals its own parse, counted by scripts/page-shapes.mjs on a seeded database in CI and on production through a manual CI job, and the four upgraders for old page shapes are gone from src.

**Why:** Every read of a stored page runs upgradeRow, upgradeBlock, upgradeLegacy and the text fold for three shapes nobody writes since step 0.46 (about 240 lines, pinned by a rule and two specs), and nobody knows how many of production's 1,389 pages and 642 versions are in an old shape. After: the count is 0 in both places and rg finds none of the four names outside tests.

**Closes:** [PM-9](../../findings/page-builder-model/PM-9.md), [DD-9](../../findings/unused-code/DD-9.md). Each finding's file has the evidence.

### Commit 1 of 3: Count the stored page documents that differ from their parse

- **create** `src/server/page-shapes.ts`: `import "server-only";`. First make the inventory: run rg -n 'parsePageContent|pageInput\b|pageRowSchema|pageColumnSchema|pageBlockSchema' src --glob '!*.test.ts' (34 server files and 15 lib files on 12 November 2026) and, for each caller, find the table and jsonb column the value was read from. Export `PAGE_HOLDERS: { table: string; column: string; key: string[]; schema: "page" | "rows" | "row" | "blocks" | "nested"; path?: string }[]`: one entry per column that holds page JSON. It must contain at least: commerce.pages draft and published (schema page), commerce.page_versions content, commerce.site_staging_pages content, commerce.saved_parts content, commerce.store_starters draft, commerce.design_presets snapshot and draft, commerce.design_preset_versions snapshot, commerce.theme_submissions snapshot and pages, commerce.content_entries draft and published, (checked on 12 November: src/server/site-layouts.ts, product-layouts.ts, global-parts.ts, home-takes.ts, experiments.ts and platform-legal.ts read their page documents from commerce.pages.published or draft, and global-parts.ts also from commerce.saved_parts.content, all already in this list; experiments.ts reads commerce.experiment_variants only to join the pages). The other callers the rg lists are still to be traced to their tables; that inventory is the part of this commit that needs judgement. `key` is the primary key columns (read them in src/db/schema.ts). For a column whose JSON holds page documents inside a larger object (a theme snapshot holds several pages), `schema` is "nested" and the entry names the function of the reader that pulls the documents out; reuse that reader, do not write a second walker. Export `parseHeld(holder, value): unknown | null` which applies the same schema the reader of that column applies (pageInput for a page, z.array(pageRowSchema) for rows, and so on) and returns the parsed value, or null when it does not parse. Export `async function countPageShapes(executor = db()): Promise<{ holder: string; rows: number; differ: number; unreadable: number }[]>`: for each holder it reads key and column in pages of 200 ordered by key (keyset paging, `where (key) > (last) limit 200`; never offset), and counts a document as differing when `JSON.stringify(parseHeld(...)) !== JSON.stringify(stored)` after both went through one function `canonical(value)` that sorts object keys (jsonb does not keep key order, so key order alone must never count as a difference), and as unreadable when parseHeld returns null. Reads go through typedRows() with `col` (a new file starts with no unchecked reads). Nothing is written in this commit.

### Commit 2 of 3: Rewrite the documents that differ, once, in batches

- **edit** `src/server/page-shapes.ts`: Add `async function rewritePageShapes(): Promise<{ holder: string; rewritten: number; skipped: number }[]>`. For each holder, in pages of 100 by key: inside one transaction per page of rows call longerTimeout(tx, 60) (src/db/client.ts line 89), select the rows `for update skip locked`, and for each row whose document differs and parses, `update <table> set <column> = ${JSON.stringify(parsed)}::jsonb where <key columns> = ...` and, where the table has a store_id column, `and store_id = ...` (the ratchet counts writes that pick a row by id without the store). A document that does not parse is skipped and counted; nothing else of the row is touched: not updated_at, not a version number, not a published flag (if the table has an update trigger that bumps updated_at or writes a version, stop and report). No cache tag is refreshed: what readers draw from the rewritten document is what they drew from the old one. ## Do not

- Do not remove an upgrader before production's count is 0 and unreadable is 0: a page that no longer parses is not shown.
- Do not run the rewrite against production yourself, and do not put a production connection string anywhere: the owner starts the manual job.
- Do not write the rewrite as a SQL migration: only the TypeScript schema knows the shape.
- Do not change updated_at, publish state, versions or cache tags in the rewrite, and do not rewrite a document that does not parse.
- Do not delete foldTypography or headingLook, nor dropStrandedItems.
- Do not edit the nine hot tables' structure or add an index: this step changes JSON values only.
- Do not leave a holder out because its count is slow: page it by key.

## Stop and report if

- The first count on a fresh seed is not 0 (step 0.46 is not done, or the schema normalises something on every parse: report which holder and one example document's difference).
- parse(parse(x)) differs from parse(x) for any document: the rewrite would never reach 0.
- Production's count shows unreadable documents: list them (holder and key only, never content) and hand back.
- A holder's table has a trigger that fires on update of the JSON column (versions, updated_at, search vectors).
- The inventory finds page JSON reaching the schema from outside the database in an old shape: a theme file from outside (D344), the Admin API, an import, a prompt that tells a model to write `columns: { mobile, tablet, desktop }`. Those inputs would be refused after the removal: report them before removing anything.
- The type check shows PageContent, PageRow or PageBlock changed after the preprocess wrappers were removed.
