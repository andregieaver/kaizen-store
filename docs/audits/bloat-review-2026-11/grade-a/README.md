# What grade A means, area by area

Part of `docs/audits/bloat-review-2026-11.md` (its section 1 has the scale and the scorecard). Each area's bar was set by a steward, challenged by a second reviewer (is this truly an A; can the plan's steps reach it) and compared across areas by a critic. A grade is raised only for fixes seen working in production, measured as the area's file says.

| Area | Today | Grade A, in a sentence | In full |
|---|---|---|---|
| What a shopper's browser gets | C | A shopper's first page loads React and Next plus at most 168 KB of the store's own script on a built page (203 to 223 KB where it sells or pays), one document with nothing in it twice, and no more than 350 KB on the wire in all; left alone it fetches at most 6 answers ahead and calls the server for nothing. A themed store in production scores 90 on a slow phone every night, and a check fails on the day any of this slips. | `shopper-browser.md` |
| What an owner's browser gets | D | A plain admin screen starts with at most 650 KB of script (447 KB of it is React and Next), a product's editor with at most 1.1 MB and the page builder with at most 1.8 MB; nothing is downloaded for a part the screen does not draw, a screen is handed at most 1.1 times the words its parts name, and a screen nobody touches asks the server for nothing but a notice count every ten minutes. Every route sits under a budget that only falls, and owners' real page loads paint within 2.5 seconds. | `owner-browser.md` |
| What the server loads and asks | D | A function loads what its own job needs and little more: about 1 MB for a beacon and for the proxy, 4 to 5 MB for a store page, and a small, counted start for every instance. A page view asks the database only for what changes per view (stock on a product page, nothing on a home page), an admin screen shows its first content after one or two waves of reads, a cached page is drawn again only when something it shows has changed, and a test or a production figure holds each of these numbers. | `server.md` |
| Scheduled work | D | On a quiet day the scheduler makes at most 1,350 calls and 45,000 statements, none of them per store, and every job runs at the pace of its work, four at a time, inside a time budget. Every scheduled function has a ledger row that shows its work and its failures, due work starts within minutes, and a test or a daily production figure holds each of these. | `scheduled.md` |
| The database | C | A read or a scheduled run costs what the asking store holds and what has changed, never what the whole platform holds. No statement fetches a document it does not draw, asks twice, writes nothing or runs slow, and a test or a daily production reading holds each of these numbers. | `database.md` |
| The page builder's model and a built page | C | A built page is sent once and read once: one layout, each part once in the HTML and once in React's payload, only the documents it draws and only the scripts of the parts on it. A publish redraws that page alone, every owner's read stays inside that owner's rows, and tests on pages shaped like real stores' hold each figure. | `page-model.md` |
| Styles | C | A shopper's browser loads one stylesheet of at most 135 KB (20.6 KB compressed) with nothing in it that only the admin uses, a store's document carries each style sheet twice and no more, and every colour a public page reads has a value. A test fails, or a figure on the platform's own screen shows it, when any of this slips. | `styles.md` |
| Interface text | C | A shopper's function and scripts carry no admin words, an admin screen is handed the words its parts name and its function loads only the areas it names, a save sends no words again, and a translated language costs what it uses. Each of these is a number that a test fails on, for an English and a Norwegian owner. | `text.md` |
| AI calls | C | The AI manager's first round is a third of today's size or less (at most 56,000 characters, and a median of 15,000 real tokens a call), at least half of its input comes from the provider's cache, and an eval shows it still finds its tools. Small jobs run on a small model, nothing reads the AI connection or walks the stores when no model is called, and a test or a daily figure holds every agent's size, output and ceiling. | `ai.md` |
| The product's surface | C | A store that uses only the shop sends no statement, makes no call, gets no scheduled work and carries no AI tool for a feature it has off, from the front page to a paid order, and a test walks that road and fails on the next one. Every count of the product's size is held, and nothing is built twice unless the owner chose it in writing. | `surface.md` |
| The code itself | C | Nothing in the code is kept without a caller or written twice beyond a short list with reasons: no unused export, at most five small twin pairs, exact copies under half a percent, one site, one of each helper, no package or stored file that is not used, and no library or picture sent that the screen does not need. Eight checks, each proven by a planted mistake, fail the build when one of these numbers rises. | `code.md` |
| Tests, CI and the build | D | One push lints, checks and type-checks a commit once and builds it twice in CI; the gate before a deploy takes 90 seconds, a job a release waits for repeats no work and never runs over 10 minutes, the unit run 3 and a half, and a session's checks before a push 5. The production build keeps a quarter of its machine free, and a failing check holds every one of these numbers. | `build.md` |
| The written rules | D | A session starts with at most 11 KB of standing rules, finds any rule, decision or tracker row with one search that shows its text, and is never told to read more than 20 KB before it starts. A check on every push, docs-only ones too, holds each size, and a sample of real sessions shows a code change takes in at most 25 KB of rules and docs. | `rules.md` |
