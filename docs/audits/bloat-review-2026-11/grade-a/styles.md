# Grade A for: Styles

Part of `docs/audits/bloat-review-2026-11.md`. **Today: C.** The steward's C stands. The base is sound: hand-written CSS has almost no dead weight, a built page carries under 5 KB of inline style, the admin's own CSS is a file apart, and style generation and fonts are cached. But the one render-blocking sheet every shopper loads is 28% the admin's (183,124 bytes raw / 25,832 Brotli, re-measured on the build's file; 129,745 / 19,762 when the site's entry is compiled alone), a fixed sheet is copied once per row and a third time per document, and not one test or figure holds the sheet's size, its sources or the style text. It is not a D, because no page carries far more than its job needs, and not a B, because no budget exists. The main button of /status and /report has no fill (seen again in the built HTML and CSS): a fault, not waste, so it does not make an E.

**The bar, in a sentence.** A shopper's browser loads one stylesheet of at most 135 KB (20.6 KB compressed) with nothing in it that only the admin uses, a store's document carries each style sheet twice and no more, and every colour a public page reads has a value. A test fails, or a figure on the platform's own screen shows it, when any of this slips.

## An A lives with

- motion.css (18.7 KB raw, 3.4 KB compressed) stays in every store's stylesheet only if step 1.23's reading, taken now on the launch themes and the team's 60 stores, says half or more of published store pages use it. Under half, step 2.49 loads it where a page uses it (CS-2).
- Classes that only Kaizena Flow's own pages or the staff's on-site editor use sit in every store's stylesheet: at most 17 KB raw and 2 KB compressed (1.5 KB today). A third stylesheet for stores would save a shopper about 1.1 KB compressed.
- Plain admin screens carry about 49 KB raw of storefront and motion styles. The builder's canvas and the previews draw the storefront inside the admin, and two Tailwind sheets on one page cannot be ordered safely. It is one cached file for a signed-in owner.
- Each inline style sheet is in a document twice, once as HTML and once in the payload Next sends with it. That is the framework's floor. On Orbit's home it is about 31 KB raw.
- A store's layout-level CSS stays inline in the document, not in a file of its own, while the median store is under 10 KB and no store is over 20 KB. An external sheet would add a blocking request to every first visit.
- A themed store's first paint waits for three stylesheets: the site's and one per font family. They are asked for together on one connection.
- Each dark utility is written twice, by attribute and by the device's setting: 3.4 KB raw, 0.17 KB compressed. It lets a page be dark without scripts.
- Both admin colour schemes are in one file: the one not in use costs 0.44 KB compressed.
- About 2.5% of room between the expected stylesheet and its bar. A person who visits Kaizena Flow's site and then signs in downloads two full sheets once.

## The owner's choices here

- Step 2.11: after the split, a Tailwind class typed in a part's Advanced tab can show on the builder's canvas and not on the live site. Is it enough to say in the docs that only classes styled by the owner's own CSS are promised, or should the site's stylesheet keep a short fixed list of utility names owners may type?
- Motion styles are 3.4 KB compressed, a sixth of the stylesheet, and reach every store's first visit. A store started from a launch theme does not use them until its owner adds a builder effect. Loading them only where used is a medium step with one risk: a missed case breaks a background. The plan waits for the first quarter's figures from real stores. Do you want it built before opening instead? Either way the area can be an A; waiting means the A rests on that reading.
- An owner's own CSS is limited to 50,000 characters for each of three sheets (the store's, the header's, the footer's), and all three go into every document. Should the limit be on the sum? No real store is affected today.
