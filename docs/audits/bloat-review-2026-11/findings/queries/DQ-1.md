- **Evidence:** pg_cron schedules nine jobs with '* * * * *' (baseline_4:93-103; I counted 9), each a net.http_post that also reads the cron secret from Vault. Production: 352,514 calls, 3,974 s, 11.3 ms each. Each run polls without first asking whether anything waits. Cookie scan: two updates, then a CTE over every open site with two correlated subqueries on cookie_scans written 'is not distinct from' (cookie-scans.ts:94-99); the table's only fitting index is (store_id, created_at) (baseline_3:7591) and that wording cannot use it, so production shows 1,101,927 sequential scans of cookie_scans over 49,338 calls: 22 scans a call, 873 rows a scan. Theme shots: every run calls queueThemeShots() first (theme-shots.ts:331), which reads every published theme with its whole snapshot, the theme contents, the showcase stores and the stored queue, then opens a transaction with an advisory lock to claim; production shows 35,101 such theme reads (101 s) against a theme_shots table of 72 rows, although three callers already queue shots when a theme or demo store changes (askForThemeShots: store-starters.ts:326, design-presets.ts:825 and 2368) and a partial index on the waiting units exists (theme_shots_queue_idx, baseline_3:14031). Pack pictures opens a lock transaction each minute (content-packs.ts:735-737). Together the two lock claims are the 71,422 pg_advisory_xact_lock calls. The integrations route runs seven pollers a minute (inbound email, workflows, the platform's workflows, deliveries, the platform's deliveries, support emails, store events) and deliverDue() ends every run with a prune delete (integrations.ts:1062; 66,533 calls each of the claim and the delete). The autopilot's three runners each read the pause switch (ai-pause.ts:18; 69,075 calls). Eight of the nine routes answer first and work in after(), so the ledger's 0 to 1 ms durations do not show idleness; the row counts do.
- **Cost today:** 12,960 function calls a day by the schedule, fixed whatever the store count. At most about 150 s of database time a day for the calls themselves (13,248 calls at 11.3 ms). What grows: the cookie scan's who-is-due query does 2 table scans per open site per minute; estimate, at 1,000 open stores that is 2,000 scans a minute of a table of about 13,000 rows. The theme-shot polling grows with themes, not stores. Paid by: The database and the server (function invocations), every minute. No shopper or owner waits for it.
- **Saving:** Estimate. Steps 1 to 7: the 1.1 M sequential scans of cookie_scans and the 101 s of theme reads go, the 71,422 lock transactions stop while nothing waits, and the minute cost stops growing with stores. Step 8 would save up to 12,900 function calls a day while queues are empty; that saving shrinks once real stores give the queues work.
- **Risk:** A wrong due test leaves work waiting: a weekly cookie scan that never starts, or a theme published without photographs. Noticed by the platform home (route.cookie-scan and route.theme-shots still record every run), by cookie-scans.int.test.ts and theme-shots.int.test.ts, and in production by cookie_scans rows with status 'done' no longer appearing weekly per site. For the first weeks keep the daily theme sweep and compare its 'missing' count with zero.
- **Already tracked:** partly: docs/audits/psi-followups.md:477 REL-06 (open) says the routes that work after answering are not recorded in the job ledger. No step covers the polling itself.

## The fix

1. 1 (S, first). Cookie scan's due query, src/server/cookie-scans.ts:85-110: write the 'last' CTE so an index serves it. For stores: from sites s left join lateral (select max(c.finished_at) filter (where c.status = 'done') as done_at, max(c.created_at) as tried_at from commerce.cookie_scans c where c.store_id = s.store_id) l on true. For the platform's row: the same subquery with c.store_id is null. Combine the two with union all. Keep the insert, the order and the on conflict clause as they are.
2. No new index is needed. My EXPLAIN of the rewritten query on the local scratch database (read-only, enable_seqscan off) shows both branches as an Index Cond on the existing cookie_scans_store_created_idx (store_id = the site, and store_id is null for the platform); one site holds about 13 rows (a weekly scan kept 90 days). In src/server/site-cookies.ts:44-47 write the store filter with the owned() helper of DQ-8 so the banner's read of the latest finished scan is served the same way (my EXPLAIN: Index Cond on store_id, then a sort of that site's few rows).
3. Weekly scans from an hourly pass. Split claimScan(): keep, every minute, the stale-running update and the claim of a queued scan (my EXPLAIN: both go through the partial index cookie_scans_one_active_idx, which holds only waiting and running scans). Move the due query into a new queueDueScans(limit = 20) in the same file that inserts due sites as status 'queued' with requested_by null. Call it from the dispatcher as a job with an hourly cadence once DQ-5 gives jobs cadences; until then call it from src/app/api/cron/cookie-scan/route.ts only when new Date().getUTCMinutes() === 0 (the pattern autopilot-effects.ts:44 uses). One scan a minute still gives room for 10,000 weekly scans.
4. Theme shots, src/app/api/cron/theme-shots/route.ts:21-32 and src/server/theme-shots.ts:330-342: before after(), ask one statement, select exists (select 1 from commerce.theme_shots where status in ('waiting', 'running')), which my EXPLAIN shows as an index-only scan of theme_shots_queue_idx; when false answer { started: false } and do nothing else. In runThemeShots() stop calling queueThemeShots() on every run: work out wantedNow() only after the first unit is claimed (takeThemeShot needs it). Bring the queue in line where it changes: the three askForThemeShots() callers stay, and add one daily sweep (queueThemeShots() then pruneThemeShots()) as a dispatcher job claimed with claimDay('daily.theme-shot-sweep', …) as ui-nightly.ts:73 does.
5. Pack pictures, src/server/content-packs.ts:733-750 claimPack(): before opening the lock transaction ask select exists (select 1 from commerce.store_starters where pictures_wanted_at is not null) and return null when false.
6. Prunes out of the minute: remove the delete at src/server/integrations.ts:1062 from deliverDue() and its twin in src/server/platform-integrations.ts deliverPlatformDue(); export them as pruneDeliveries() and prunePlatformDeliveries() (platform-integrations.ts:484) and run both from the dispatcher with a daily cadence (DQ-5), or from runRetention().
7. Autopilot route, src/app/api/cron/autopilot/route.ts:19-30: read aiAutonomyPaused() once in the route and pass the answer to the three runners, which today each call skipWhilePaused() (autopilot-runner.ts:58, autopilot-reviews.ts:114, autopilot-events.ts:179).
8. 8 (optional, last, only if function invocations show on the bill). Put the due test in the scheduler's own SQL so no HTTP call is made when a queue is empty. It keeps each route's due test in two places (a migration and the code) and needs a heartbeat so the ledger does not read the route as late. Not recommended before opening: once real stores exist the queues have work most minutes and the saving shrinks.
