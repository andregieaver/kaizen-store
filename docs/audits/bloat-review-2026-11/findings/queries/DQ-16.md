- **Where:** `src/server/catalog.ts:284-330`, `src/server/catalog.ts:299`, `src/server/catalog.ts:302`, `src/server/catalog.ts:312`, `src/server/catalog.ts:638-689`, `supabase/migrations/20261111172839_baseline_1_schema.sql:20704-20725`, `supabase/migrations/20261111172839_baseline_1_schema.sql:12341-12350`, `supabase/migrations/20261111172839_baseline_1_schema.sql:18848-18853`, `src/server/embeddings.ts:31-45`, `src/db/vat.test.ts:771`, `CLAUDE.md:1`
- **Evidence:** Not in the verified report beyond one line on store_is_active(). listProducts() (catalog.ts:284-330) returns every active product of a store and market with no limit (code review step 3.9) and selects commerce.vat_rate(market, p.vat_category) (line 312) and commerce.media_alt(m.url, locale) (line 299) per row; listGridProducts() does the same (lines 676 and 689). Both are stable SQL functions with SET search_path (baseline_1:20704-20725 and 12341-12350), which Postgres does not inline, so each row runs the function's own query: vat_rate reads countries joined to vat_rates up to three times. My counts (rg, tests left out): vat_rate 48 uses in 33 files, media_alt 9 in 6, store_is_active 69 in 44; the local database has 91 stable SQL functions with a SET clause in commerce. Measured on the local scratch database (PostgreSQL 16.15, read-only, explain analyze): vat_rate over 10,000 product rows 112.9 ms, 11.3 µs a row; the same rows joined to a materialized list of the store's distinct VAT categories, each rate asked once, 0.9 ms; store_is_active over 10,002 rows 24.1 ms against 0.5 ms for the plain expression; media_alt 48.8 ms for 10,000 rows on an empty media table. Production agrees: countries (28 rows) is the second most sequentially scanned table, 375,215 scans reading 10.5 M rows, which is 28 rows a scan: whole-table reads of a table only this function family reads per row; my 10,000 local calls added 20,000 such scans.
- **Cost today:** About 11 µs per product row per catalogue read for the VAT rate, plus at least 5 µs per row for the alt text: 0.3 ms for a 20-product demo store; estimate 80 ms or more for a 5,000-product catalogue on each cold listing, grid, feed or sitemap read. Small today. It grows with one store's catalogue, and store_is_active() per row grows with all stores' rows in the jobs that call it over whole tables (embeddings.ts:31-45). Paid by: The database; the first visitor of a listing after its cache is cold.
- **Saving:** Measured: the VAT rate from 11.3 µs to about 0.1 µs per row (112.9 ms to 0.9 ms on 10,000 rows). Estimate: 5 µs or more per row for the alt text. Milliseconds for small stores, tens of milliseconds per cold listing for large catalogues.
- **Risk:** A wrong join would change a shown VAT rate or price label: the money tests and vat.test.ts hold it. A category with no row in the list cannot happen, because the list is read from the same store's products in the same statement. An alt text picked in a different order than the function's would show another picture's words: copy the function's order by exactly.
- **Already tracked:** no (code review step 3.9, Open, covers reading the whole catalogue for one page, not the per-row functions)

## The fix

1. In src/server/catalog.ts add one sql fragment used by listProducts() and listGridProducts(): a CTE rates as materialized (select c.cat, commerce.vat_rate(market, c.cat) as rate from (select distinct vat_category as cat from commerce.products where store_id = the store) c). Join it (join rates r on r.cat = p.vat_category) and select r.rate as vat_rate in place of the per-row call at lines 312 and 689. The rate still comes from commerce.vat_rate(country, products.vat_category), as the rule in CLAUDE.md (Database) asks; nothing reads countries.standard_vat_rate.
2. The alt text in the same two reads: replace commerce.media_alt(m.url, locale) by a lateral left join on commerce.media with the function's own where, order and limit (baseline_1:12345-12349), and take image_width from the same join; today line 302 reads commerce.media a second time per row for the width.
3. store_is_active() in statements that return many rows: join commerce.stores and write the three conditions through one shared fragment (export const activeStore = (s) => sql`${s}.status = 'active' and not ${s}.starter and not ${s}.sandbox` in src/server/stores.ts; media-library.ts:862 writes them by hand today). Move embeddings.ts:31-45 (with DQ-5 step 3) and the list reads in staff-alerts.ts, support-email.ts and the autopilot runners. Leave single-row guards on the function.
4. Do not remove SET search_path from the functions to make them inlinable: src/db/vat.test.ts:771, fulfilment.test.ts:874 and notifications.test.ts:482 hold a fixed search_path on every function for the security advisor.
5. getProduct() (catalog.ts:371) reads one product: leave it.
