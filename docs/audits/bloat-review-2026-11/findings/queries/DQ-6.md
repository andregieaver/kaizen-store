# DQ-6 ✓ The knowledge job reads every page whole every five minutes and re-cuts pages that have no text, forever

How data is asked for (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P0. **Effort:** S. **Confidence:** high. **Step:** 0.27.
- **Second check:** confirmed.
- **Where:** `src/server/knowledge.ts:166-232`, `src/server/knowledge.ts:234-258`, `src/server/knowledge.ts:296-312`, `src/lib/knowledge.ts:63-65`, `supabase/migrations/20261111172839_baseline_1_schema.sql:26639-26655`, `docs/rules/storefront.md:407-411`
- **Evidence:** For every site with its chat agent on, syncPageKnowledge() selects every published page and article with its whole published document (knowledge.ts:169-175; production: 2,571 + 17,955 + 3,608 calls in three shapes, the first returning 40 rows a call at 16 ms) and compares versions in code. I followed the comparison: the stored version is min(c.version) over the page's chunks (line 171); a page whose text cuts to no passages has no chunk, so its version is null, never equals the published date (line 186), and replacePassages() opens a transaction, deletes nothing and inserts nothing (248-258), on every tick. Production: 91,200 calls of 'delete from commerce.knowledge_chunks where page_id = $1' deleted 782 rows in all; that is 42% of the 216,877 transactions. Around it the job reads the site's languages (two reads), the blogs, every published content entry, deletes dropped passages, reads the AI connection and runs a vector pass, per site, one site after another (296-312).
- **Cost today:** 91,200 empty transactions (273,600 round trips: begin, delete, commit). Estimate: about 200 KB of page documents sent to the function each tick for the platform's site alone (40 rows at about 5 KB). After opening it is paid per store with the chat agent on (off by default): its whole published content and about eight statements every five minutes. Paid by: The database and the dispatcher function, every five minutes, for each site that uses the chat agent.
- **Saving:** Measured count: the 91,200 empty transactions and their round trips go to zero. Estimate: the whole-document read happens only when something was published, so the job's cost per store per tick drops to two small statements.
- **Risk:** A change the slim read does not see (a blog's address, a site's languages, a new embedding model) would leave passages stale until the hourly net; that is why the net stays. Noticed in the admin's knowledge status (passages and how many have vectors) and by the new test cases.
- **Already tracked:** no (docs/rules/storefront.md:407-411 states that the five-minute cron cuts pages published anew; the fix keeps it)

## The fix

1. Migration (the table in src/db/schema.ts, then pnpm db:generate; knowledge_chunks itself is SQL only because of its vector, this table has none): commerce.knowledge_sources (store_id uuid null references stores on delete cascade, page_id uuid null unique references pages on delete cascade, entry_id uuid null unique references content_entries on delete cascade, published_at timestamptz not null, slug text not null, type_version text null, path text null, cut_at timestamptz not null default now(), a check that exactly one of page_id and entry_id is set), row level security on as for every commerce table.
2. src/server/knowledge.ts replacePassages(): in the same transaction upsert the source's knowledge_sources row (published_at, slug, type_version, path), also when there are no passages. That alone ends the empty re-cuts.
3. syncPageKnowledge(): choose the pages to cut in SQL and fetch documents only for them. First a slim read: select p.id from commerce.pages p left join commerce.knowledge_sources k on k.page_id = p.id where the owner's branch and p.type in ('page', 'article') and p.published_at is not null and (k.page_id is null or k.published_at <> p.published_at or k.slug <> p.slug). Only when it returns ids, read siteLocales(), blogsNow() and select id, type, slug, published, published_at for id = any(the ids). The same for entries with type_version (the md5 at line 199). The delete of dropped passages (223-229) also deletes their knowledge_sources rows.
4. An article's address also changes when its blog's address does, without a new publish: where a blog is saved (saveBlog, src/server/blogs.ts:198), delete that store's knowledge_sources rows for articles, so the next tick cuts them again. Keep today's full compare as an hourly net (a full: true option that skips the slim read), on DQ-5's hourly cadence.
5. refreshKnowledge() (296-312): skip aiFor() and embedKnowledge() for a site when nothing was cut and no chunk lacks a vector (select exists (select 1 from commerce.knowledge_chunks where the owner's branch and space is null)); a changed embedding model is caught by the hourly net.
6. One-off, in a custom migration after it (pnpm exec drizzle-kit generate --custom --name knowledge_sources_fill, then node scripts/prune-snapshots.mjs): fill knowledge_sources from the pages and entries that have chunks today (published_at from the page, slug, path from min(c.path)), so the first tick after the deploy does not re-cut everything. Pages without chunks get their row on that first tick.

**Done when:** On production a day after the deploy the calls of 'delete from commerce.knowledge_chunks where page_id = $1' in pg_stat_statements grow by fewer than 20 a day (about 6,000 a day today), and the new case in chat.int.test.ts counts zero transactions for a second tick with nothing published.
