# DQ-11 ✓ Nothing counts queries: no budget per page or per tick, and production's statement statistics are not part of any routine

How data is asked for (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** no check. **Priority:** P0. **Effort:** M. **Confidence:** high. **Step:** 1.10.
- **Second check:** confirmed.
- **Where:** `src/server/ratchet.baseline.json:1`, `src/server/ratchet.scan.test.ts:22-56`, `scripts/ratchet.mjs:1-40`, `src/server/cron-runs.ts:106-119`, `src/app/api/cron/cart-reminders/route.ts:127-261`, `vitest.integration.config.mts:1-20`, `docs/audits/code-review-2026-11.md:110-134`, `CLAUDE.md:1`
- **Evidence:** My rg finds no statement counter in src (no queryCount, countQueries or statementCount; the pool's only listener is the error handler at client.ts:73), and the verified report found pg_stat_statements named only in the draft of this review. The ratchet (ratchet.baseline.json, ratchet.scan.test.ts:22-56) holds counts of casts, suppressions, unchecked reads and writes by id alone; none is about how many statements run or how much they return. The deploy routine in CLAUDE.md asks for the security and performance advisors after a migration, not for the statement statistics. What the findings here describe was visible there for weeks: 91,200 deletes that removed 782 rows, a slug lookup called 560,090 times, 22 table scans in one scheduler query.
- **Cost today:** No running cost of its own. It is why the others grew unseen. Paid by: Everyone later: each new section, job and cached read adds statements with no number to hold against. The number matters more once statements multiply by stores.
- **Saving:** Not a direct saving. It gives DQ-1, DQ-5, DQ-6, DQ-7 and DQ-9 a number to check their fix against and keeps them from coming back.
- **Risk:** A count that wobbles makes a flaky test: count on the seeded database with caches cold and files run one at a time, and count statements, not time. A job that reaches the network in the test would fail it; that is a finding in itself. Nothing in production changes except the move of the job list.
- **Already tracked:** no (code review step 4.6 'Measure, then tune', Open, is the admin audit's and names no query count)

## The fix

1. A counter for tests, with no change to production code: test/count-statements.ts exporting countStatements(run), which wraps pg's Client.prototype.query for the length of run and returns the number of statements and their first 80 characters (begin and commit counted apart). The 'use cache' functions run as plain functions under vitest, as today's int tests already call them.
2. Make the dispatcher's jobs reachable by a test: move the object passed to runJobs() at src/app/api/cron/cart-reminders/route.ts:128-261 into src/server/dispatcher-jobs.ts (export const DISPATCHER_JOBS); the route imports it. Update the regex in src/server/cron-routes.scan.test.ts line 41 to read the new file.
3. New src/server/query-budget.int.test.ts with three budgets: (a) one idle dispatcher tick over DISPATCHER_JOBS on the seeded database, and again after 19 more open stores are added, asserting the two counts are equal; (b) one idle run of each minute route's server function (claimScan, runThemeShots with a photographer that is never called, deliverDue, deliverPlatformDue, the pack pictures' claim, the autopilot's three runners); (c) the cold frame's loaders for the demo store and for the platform (getPlatformChrome, siteCookies and the readers PlatformRoot calls). The test database holds no provider keys, so no job reaches the network; a job that would is given a stub through its existing deps argument.
4. Keep the numbers so they may only fall: a new key queryBudget in src/server/ratchet.baseline.json, written by scripts/ratchet.mjs from a JSON file the int test leaves, and asserted by the int test itself (the unit ratchet has no database). Until the 1-and-20-stores counts are equal (DQ-1, DQ-5, DQ-6), record the difference as its own number that may only fall.
5. The routine: in CLAUDE.md, Database, after 'check the security and performance advisors', add: once a week read the 25 most-called and the 25 costliest statements and explain any newcomer; put the two queries (they are at the end of the statistics file of this review) in docs/ci-migrations.md.
6. Two scan tests that keep shapes out: the ratchet count of DQ-8 (no new 'store_id is not distinct from' with a parameter), and a scan over supabase/migrations/*.sql that fails on a new cron.schedule with '* * * * *' unless the job is listed with the one-statement due test its route starts with.

**Done when:** pnpm test:int runs query-budget.int.test.ts green with the three counts written in the baseline, and after DQ-1, DQ-5 and DQ-6 land the idle tick's count is the same for 1 and 20 seeded stores.

- CLAUDE.md (Workflow and Database) and docs/ci-migrations.md are the written routine that step 5 extends; the code review's Progress table has step 4.6 'Measure, then tune' (Open), which names no query count.
