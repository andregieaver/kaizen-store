- **Evidence:** Not in the verified report, which names only the invoice job's repeated per-store calls. invoiceJobs() runs every five minutes from the dispatcher. Its store finder (invoice-issue.ts:71-101) has no queue: it takes every order of every store placed in the last 120 days and proves for each that an invoice exists (an anti-join on invoices and a look in order_events), then every succeeded refund ever made (no time bound) against credit_notes and order_events, then every outside-refunded return. Invoicing is on unless switched off (coalesce(cfg.enabled, true), line 76), so every selling store's orders are in. My EXPLAIN on the local scratch database (PostgreSQL 16.15, read-only, enable_seqscan off): orders is entered through orders_invoice_candidates_idx, which is (store_id, placed_at), with placed_at as the only condition, so the whole index is walked; refunds through refunds_store_id_key with status as a Filter, so every refund is read. For each store found the job calls issue_waiting_invoices(), which itself ends with issue_missing_credit_notes() (baseline_1:10554), and then calls issue_missing_credit_notes() again (invoice-issue.ts:125): twice per store per tick (production: 9,909 calls each, 132 s and 35 s). In the same tick sendPendingDocumentNotices() (invoice-notices.ts:130-170) reads every invoice and credit note issued in 3 days, each with a look in order_events, document_deliveries and email_messages; invoices and credit_notes have no index that starts with a time (invoices_issued_idx is (store_id, issued_on), baseline_3:9222; credit_notes_issued_idx the same, :7654), and my EXPLAIN shows a walk of invoices_store_id_key with issued_at as a Filter: every invoice ever issued, every five minutes. runEinvoiceSending() (einvoice-sending.ts:57-97) reads every invoice, credit note, work invoice and work credit note of 2 days and opens each one's snapshot JSON to see whether the buyer is a business (my EXPLAIN: the snapshot test is a Filter after a bitmap scan on issued_on); a consumer's invoice is never recorded as looked at, so it is read again on every tick for two days. collectSupplierOrders() (supplier-orders.ts:58-73) does the same over 3 days of stock movements, but only at suppliers' locations, so its cost follows the stores that drop-ship.
- **Cost today:** Nothing measurable today (102 orders in all). After opening the work per tick is in proportion to all stores' orders, not to what waits. Estimate: at 1,000 stores with 10 orders a day, 1.2 million orders are re-proved every five minutes (two index probes each), every invoice ever issued is filtered for the email check, and 20,000 invoice snapshots are opened for the e-invoice check. The role's statement limit is 15 s; a store finder that passes it fails the whole invoice job, and then waiting invoices are not issued. Paid by: The database, every five minutes, for every store that sells; later store owners and their customers, if the job times out and invoices wait.
- **Saving:** Nothing at today's size. Estimate after opening: the tick's document work follows what waits, usually nothing, instead of all orders of 120 days and every invoice; and one of the two credit-note calls per store per tick goes (9,909 calls and 35 s so far).
- **Risk:** This is the path that issues legal documents. A fast path that misses a case leaves an invoice waiting up to an hour (the net) instead of five minutes; the owner's Check again on the Waiting tab is unchanged. Step 1 is indexes only and cannot change behaviour. Noticed by invoice-issue.int.test.ts, by the Home page's count of waiting documents and by the ledger row dispatcher.invoices.
- **Already tracked:** no. Code review step 3.15 (Open, FD7 and FD8) is about keeping the big tables lean, not about these reads; the verified report's DQ-5 named only the repeated per-store calls.

## The fix

1. Indexes that fit the two short windows, in one custom migration (pnpm exec drizzle-kit generate --custom --name document_job_indexes, then node scripts/prune-snapshots.mjs; none of these tables is on the hot-table list, so plain create index): invoices (issued_at); credit_notes (issued_at); invoices (issued_on) where (snapshot -> 'buyer' ->> 'type') = 'business'; the same partial index on credit_notes; work_invoices (issued_on) where status <> 'draft' and not imported and (buyer ->> 'business')::boolean is true; work_credit_notes (issued_on) where (buyer ->> 'business')::boolean is true. The statements at invoice-notices.ts:131-139 and :140-162 and einvoice-sending.ts:64-93 already carry these predicates, so no code changes: the email check reads 3 days of documents and the e-invoice check reads only business documents and never opens a consumer's snapshot.
2. The invoice job's finder, src/server/invoice-issue.ts:71-101: keep today's query as the net and run it once an hour (DQ-5's cadence; until then the minute-below-5 test of autopilot-effects.ts:44). Add to its refunds branch rf.created_at > now() - make_interval(days => LOOKBACK_DAYS), which refunds_store_created_idx can then help with per store, and an order by store_id before the limit so no store is starved when more than 50 have work.
3. A fast path for every tick that reads only what is marked as waiting: stores with an order_events row of type 'invoice.failed' in the last 120 days whose order still has no invoice (add a partial index order_events (created_at) where type = 'invoice.failed'; the event is written at baseline_1:10517), plus stores with an applied order change whose documents wait (add a partial index order_edits (store_id) where status = 'applied' and documents = 'waiting').
4. A try at once where the cause goes away: where the seller's details or the invoice settings are saved (find the writers with rg 'invoice_settings' src/server), call issueWaitingInvoices(storeId) in after(), so an owner who completes the details does not wait for the hourly net.
5. One credit-note call per store: issue_waiting_invoices() already ends with issue_missing_credit_notes(). In invoiceJobs() (invoice-issue.ts:123-126) call issueMissingCreditNotes(storeId) only when issueWaitingInvoices() failed; make it return that fact instead of swallowing it into a 0.
6. Write the pattern down in docs/wave-1b-invoices.md (the job's section) and docs/rules/admin/commerce.md: a document job reads a waiting mark or a window an index can serve, and keeps the full check as an hourly net.
