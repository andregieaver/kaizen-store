# DQ-12 ✓ Every server instance reads the interface translations before it serves and polls them each minute

How data is asked for (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P2. **Effort:** S. **Confidence:** high. **Step:** 0.7.
- **Second check:** corrected.
- **Where:** `src/instrumentation.ts:6-10`, `src/server/ui-text.ts:30-31`, `src/server/ui-text.ts:57-88`, `src/server/ui-text.ts:94-115`, `src/server/shopper-emails.ts:108`, `src/server/notifications.ts:367`
- **Evidence:** register() awaits startUi() before an instance takes requests (instrumentation.ts:6-10); that runs 'select lang, count(*), max(updated_at) from commerce.ui_translations group by lang' (ui-text.ts:60-62), then a timer repeats it every 60 s (107-110). Production: 278,393 calls, the second most-called statement. The verified report measured one statement per instance per minute on the local database. ensureUi() is called only from two email paths (shopper-emails.ts:108, notifications.ts:367); pages rely on the timer, so the timer is what keeps a long-lived instance current and cannot simply be dropped.
- **Cost today:** At least 3,569 round trips a day, each tiny. One round trip before a new instance serves (estimate, not measured). It grows with instances, not with stores. Once languages are translated the poll becomes a count over every translated text per instance per minute. Paid by: The first visitor served by a new instance; the database.
- **Saving:** Estimate: from 1,440 group-by polls per instance a day to 144, or the same count as single-row reads. Small either way.
- **Risk:** With the longer wait a language translated by AI would show up to 10 minutes late on other instances; with the stamp, none. Noticed as a page still in English after a language was made.

## The fix

1. Keep the read at start and the timer. In src/server/ui-text.ts make the poll cheap: a version stamp. Add ui_text_version bigint not null default 0 to commerce.platform_settings (one row), raised by one in the same statement by every writer of commerce.ui_translations (the AI translation, a person's edit, mark reviewed, the nightly run in ui-nightly.ts). refresh() first reads only the stamp and runs today's group-by only when it moved.
2. Or, with no migration: while the last answer had no translated language, let the timer wait 10 minutes instead of one (a setTimeout chain in startUi() in place of setInterval). reloadUi() already refreshes the instance that made a change.
3. Do not make t() wait on the database, and do not drop the timer.

**Done when:** On production the calls of the ui_translations group-by statement in pg_stat_statements grow by fewer than 200 a day per running instance with no translation edited (1,440 per instance a day today).

**Tests and rules that hold today's behaviour, and change with it:**

- src/server/ui-nightly.int.test.ts and src/server/languages.int.test.ts mention the interface text's loading; add a case that a second refresh with no change issues one single-row read.
- The module comment at ui-text.ts:22-27 is the written rule ('reads it when an instance starts and looks for changes each minute; the sync t() never waits on the database'): keep it true and name the stamp.
- A writer of ui_translations that forgets the stamp would leave other instances stale: hold the writers with a small scan test if step 1 is chosen.

**Notes:** Low priority: about 3,600 tiny reads a day that grow with instances, not stores. Do it when ui-text.ts is next opened, and before many languages are machine-translated, when the group-by starts to count thousands of rows a minute per instance.
