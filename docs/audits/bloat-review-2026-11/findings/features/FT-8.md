- **Evidence:** Order rules (D238): when an order is paid and conditions hold, then tag, notify staff, hold or ask the AI manager (order-rules.ts:46), with 13 kinds of condition (:29) and all-or-any matching. Workflows (D356): on any store event, order.paid among them, conditions on the event's fields (all must hold), then tag_order, note_order, tag_customer, email_staff, post_slack, send_request, ask_ai_manager (workflows.ts:133). Three of the four rule actions exist in Workflows; 'hold', 'any' matching and about nine order facts (first order, product, delivery, backorder, gift, source, tag, seller, risk) do not. The spec meant one engine: 'order rules become workflows of the trigger order.paid' (wave-9-platform.md:92); the build left them apart (:140). They run on two queues in the same every-minute route: workflows first, then the store events with the rules (integrations/route.ts:29-37; the rules are imported on demand, staff-alerts.ts:944). Size, measured: order rules are src/lib/order-rules.ts 294, order-rules-schema.ts 69, src/server/order-rules.ts 435, four settings pages with their files 558 lines, the editor in src/components/admin/automation, and 407 test lines in their own two test files (the skeptic's 1,910 code and 528 test lines by file name hold); 2 tables, 1 AI tool (order_rules). 40 other files name them (rg): the hold panel, staff alerts, follow-ups, the store copy, the export, the personal-data registers and five tests. Store workflows are 1,316 lines. Both are links under Settings (store-nav.ts:336-337).
- **Cost today:** Two editors, two logs and two links with near-identical words for the owner; every change to order automation made in the right one of two places; two queues to keep correct. Paid by: An owner's admin (a choice between two doors), CI, anyone changing automation
- **Saving:** Estimate: about 1,900 lines, 528 test lines, 4 pages, 1 link and 1 AI tool removed now, 2 tables a release later, less the 300 to 500 lines Workflows gains for the hold action, 'any' and the order facts.
- **Risk:** A hold is a safeguard, so three things must not change unseen: (1) the cap of 100 runs an hour per workflow would skip holds on a busy day unless order.paid is exempt; (2) the staff email says 'held' only if the hold lands before the alert, which the claim guard keeps; (3) a workflow is saved off and must be tested before it is on, so making a hold rule takes one more press than today. Order rules ran in a chosen order; workflows have none, which is harmless only because facts are read once. Each would show in workflows.int.test.ts and staff-alerts.int.test.ts if tested as listed. The editor grows by the pickers; if the owner finds the one editor too heavy for Homer, a 'When an order is paid' starting point keeps it simple.
- **Already tracked:** The page merge is audit phase 2 ('Workflows and Automation become one Automations', docs/audits/admin-usability-2026-11.md:199; code review step 2.4, Open). Merging the engines was the wave 9 spec's intent (docs/wave-9-platform.md:92), left undone at build (:140), and is on no open list.

## The fix

2. src/lib/workflows.ts: add the action `{ kind: "hold_order"; reason: string }` (at most 200 characters, as RULE_LIMITS.reason) to ACTION_KINDS, WorkflowAction and workflowActionSchema, offered by actionsFor() for the trigger order.paid only. Add `match: "all" | "any"` (default all) to WorkflowInput and workflowSchemaFor(), and make workflowMatches() honour it. Add the order facts as fields of order.paid only (a list fieldsFor("order.paid") appends): facts.total_main (number, the store's main currency), facts.buyer, facts.first_order (yes or no), facts.product_ids, facts.delivery, facts.backorder, facts.gift, facts.source, facts.tags, facts.seller, facts.risk.
