# What every AI call carries (AI)

Part of `docs/audits/bloat-review-2026-11.md`. One reviewer's reading of this area, 11 November 2026, commit 0bd814c. A tick (✓) marks a
finding checked a second time against the code, the build or production; the others were not (the second reviewers did not run: see
the review's section 6). "Step" is the step of the plan that closes the finding.

**In short.** The shopper chat is lean and well made: about 5,000 characters of prompt and tools a call. The AI manager is the bloated part: every model call carries about 160,000 characters (roughly 40,000 tokens, an estimate at 4 characters a token), 91% of it 124 tool definitions that do not depend on the question, and a turn makes up to 11 such calls; this is already step 3.18 of the code review, still Open, and nothing caches it. Around the AI, the helper that fetches the AI connection ran 237,563 times for 19,104 recorded AI calls, mostly to answer yes or no on pages, polls and five-minute jobs that call no model. The owner's browser also downloads the model's whole tool catalogue and admin map (half of a 496 KB script) to show 13 KB of labels.

## Well made, and should stay

- The shopper chat (src/server/chat-agent.ts, src/lib/chat.ts): 6 hand-written tools, a 2.5K-character prompt, history capped at 20 messages of 1,000 characters, results cut at 6,000, product tools dropped for a website, support tools chosen by desk mode, feature and channel. Its prompt and tools do not reach any browser chunk (checked in .next/static/chunks).
- Tools of store features that are off are already dropped (src/server/offered-tools.ts, src/lib/owner-tool-features.ts: 121 tools behind a feature), and tools a role may not use are never offered.
- The admin map in the prompt is one line a group (titles and ids only, 2.2K to 5.8K characters) and follows features and role (src/lib/admin-map.ts:1501-1513). The 58,402 characters of playbooks load only through use_skill.
- History: only the last 20 messages as text; earlier turns' tool results are never resent. Memories: at most 8 short lines a turn (src/server/assistant-memory.ts:44).
- The turn budget (src/lib/turn-budget.ts): 240 s, 400,000 tokens, the month's allowance checked between rounds, a daily cost ceiling for platform admins. Code review FA2 and FA5 are done.
- An autopilot step is offered only its own tools plus a few extras, not the 124 (src/server/owner-assistant.ts:714, 732).
- The launcher on every admin page loads the chat script and the AI's abilities only when the panel is first opened (src/components/admin/ai-manager-launcher.tsx:22-40, D444).
- One-shot prompts are small: tone 275 characters, support brief 334, rerank 962, Dream Factory brief 1,391, moderation 1,663 and 1,803, search understanding 2,211, rework 2,790, docs guide 4,776 (drawn in a scratch bundle). Change with AI sends the page's outline, not its JSON.
- Knowledge passages are short (246 to 1,176 characters in a test cut) and a search returns 5. Search vectors and understood searches are kept in the search cache.
- Prompt versions are hashed once per server instance (src/server/prompt-versions.ts:79-84).
- Built but unused with no running cost today, so not findings: the owner MCP (/api/mcp) would list up to 254 tools to an outside assistant, but oauth_clients, oauth_grants and oauth_tokens have never held a row; custom apps' tools (custom_apps empty).

## Findings

### AI-1 ✓ Every AI manager call sends 124 tool definitions, whatever the question or screen

- **Kind:** eager. **Effort:** M. **Confidence:** high. **Step:** 2.9. **The owner's decision.**
- **Where:** `src/lib/tool-budget.ts:15`, `src/lib/tool-budget.ts:88`, `src/server/owner-assistant.ts:731-741`, `src/server/owner-assistant.ts:793`, `src/server/ai.ts:693-702`, `docs/audits/code-review-2026-11.md:120`
- **Evidence:** chooseTools() fills the budget to the provider's cap: core tools, tools used before, the page's area, then every other area in a fixed order (tool-budget.ts:88). Run on a shop-only store it offers 234 store tools and sends 97 plus the manager's 26 and load_tools: 146,889 characters. The system prompt is 14,773. So a round is about 161,700 characters, 91% tools. The fixed order means orders, products, customers and marketing tools always go (products alone: 28 tools, 54,032 characters) and website and settings tools never do without an extra load_tools round. streamWithTools() gets the full list on every round but a forced last one, the answer round included. Measured with the app's own functions in a scratch bundle.
- **Cost today:** About 40,400 input tokens a call (estimate), up to 11 calls a turn; about 121,000 tokens for a turn with two tool rounds. At the seeded gpt-5-mini price (0.25 dollars a million input tokens, supabase/migrations/20261111172840_baseline_2_data.sql:106) that is about 3 cents a turn before any cache discount; more on a larger model. It also slows the first word of every answer and uses up a store's monthly AI allowance. Paid by: The server per AI manager call, the store's monthly AI allowance (or its own key), and the owner waiting for the answer.
- **Fix:** Keep D333's mechanism and lower the default. Send the 12 core tools, the manager's own, load_tools and the area of the page the person is on; stop filling with 'the other areas'. Let a cheap router in code add areas whose tool names or labels match words in the message, and keep 'tools used earlier'. Memoise toolDefinition() per tool (FA9). Run the agents' eval and commit a new recording, as the rules require.
- **Saving:** Estimate from measured sizes: a round falls from about 161,700 to 48,500 characters with no page area (minus 70%), or to about 77,000 on an orders page (minus 52%). A 3-call turn falls from about 121,000 to 36,000 to 58,000 tokens.
- **Risk:** The model may need one load_tools round more for questions outside the core and the page's area, or miss a tool; the eval and its recording must pass again. D333's reason (providers refuse more than 128) still holds and is kept.
- **Already tracked:** Yes: code review step 3.18 'Cheaper, faster AI rounds' (FA1, FA9), status Open; owner question 8 there asks about a default of about 40 tools.

### AI-2 The AI connection is fetched on pages, polls and jobs that call no model

- **Kind:** eager. **Effort:** M. **Confidence:** high. **Step:** 0.8.
- **Where:** `src/server/ai.ts:206-222`, `src/server/ai.ts:235-239`, `src/server/limits.ts:122-144`, `src/server/usage-sql.ts:48-56`, `src/server/support-inbox.ts:90-98`, `src/lib/support-rules.ts:74`, `src/app/admin/(gated)/[store]/pages/context.ts:165-168`, `src/server/chat-agent.ts:135-139`, `src/server/media-library.ts:860-870`, `src/server/alt-texts.ts:238`, `src/server/knowledge.ts:297-306`, `src/server/search.ts:333`, `src/server/products.ts:196`
- **Evidence:** aiFor() has no cache: each call runs 'select * from commerce.ai_providers', decrypts up to three API keys and, for a store on Kaizena Flow's key with a plan limit, sums the month's ai_usage with a price lookup per row (a 60-second memo per server instance, which short-lived functions and the 5-minute dispatcher rarely hit). rg finds 92 uses in 65 files. Many want only a yes or no: the staff's open conversation polls every 2 seconds and each poll calls aiFor() for the Translate button; opening a page in the builder calls it three times in a row (make pictures, edit pictures, change with AI); the product editor twice; the chat widget's profile on a site page render; every storefront search before it knows whether AI is used. The dispatcher calls it every 5 minutes for the platform, for each site with a chat agent, and for each site with media, before checking whether there is work. Production: 237,563 provider reads and 8,514 cost sums for 19,104 recorded AI calls. Next's own guide (node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-cache.md:245-259) says 'use cache' entries typically do not persist between serverless requests, which fits 48,492 reads of the platform's chat agent behind a cache of hours.

The sum grows with every row of ai_usage (19,104 today). Paid by: The database and the server per request: shoppers' searches and page renders, owners' editors, staff with a conversation open, and the dispatcher every five minutes.
- **Fix:** Add a small read for yes-or-no questions, for example aiAbilities(storeId): the model columns only, no key, no budget, tagged AI_TAG and memoised per instance for a minute; use it in the roughly 20 places that only draw a button, the conversation poll first. Keep aiFor() for code that is about to call a model. In jobs, ask 'is anything waiting?' before aiFor(). Replace the per-call sum with a running month counter per store, written by recordUsage(), so the limit check is one row. capacity.md's reason for the memo (no cache scope in jobs and actions) still holds: the gate stays inside aiFor().
- **Saving:** Estimate: provider reads fall by more than 80% (the dispatcher's idle runs, the poll and the editors go to zero) and the cost sum becomes a single-row read. An open support conversation goes from 30 provider reads a minute to none.
- **Risk:** Low. A cached yes-or-no can be a minute stale after an owner changes AI settings; saveAiSettings() should refresh the tag. The month counter must count the same as the usage pages (one shared SQL today, D106).
- **Already tracked:** no (docs/capacity.md:612 notes that aiFor() 'is called often' and adds the 60-second memo; no step covers the callers)

### AI-3 Prompts are not cacheable and cached tokens are never counted

- **Kind:** eager. **Effort:** M. **Confidence:** medium. **Step:** 2.9.
- **Where:** `src/server/owner-assistant.ts:409-415`, `src/server/owner-assistant.ts:743-750`, `src/server/ai.ts:693-702`, `src/lib/ai-usage.ts:92-101`, `docs/audits/code-review-2026-11.md:249`
- **Evidence:** The manager's prompt puts the time to the minute in its second line, 182 characters in (drawn: 'It is Wednesday, 11 November 2026 at 23:42 ...'), ahead of 14,500 characters that do not change. load_tools rebuilds the tool list in table order, so new tools land in the middle. The request body carries no cache marker for providers that need one (0 matches in src). readTokens() reads only prompt_tokens and completion_tokens, and commerce.ai_model_prices has no cached-input price, so even when a provider discounts a repeated prefix the store is charged the full price and nobody can see whether caching works.
- **Cost today:** The same 160,000 characters are paid in full on every round of every turn (see AI-1). Unknown share is already discounted by providers that cache by prefix on their own; the code cannot tell. Paid by: The server per AI manager call and the store's AI allowance.
- **Fix:** As FA1 says: fixed tool order with loaded tools appended at the end; the unchanging rules, skills and map first; the date (not the minute), page, waiting approvals and memories last; cache markers for models that need them. Add: read cached input tokens from the provider's usage, store them in ai_usage, price them, and show the cached share per round on Platform, AI. Step 3.18's own 'done when' needs that reading.
- **Saving:** Not measured. After AI-1 the stable prefix is about 48,000 characters a round; from the second round of a turn nearly all of it could be served from a cache where the provider offers one.
- **Risk:** Changing the prompt's order is a new prompt version: eval run and recording again. Cached-token fields differ by provider; read them defensively.
- **Already tracked:** Yes: code review step 3.18 (FA1), Open. Reading and pricing cached tokens is not written there.
