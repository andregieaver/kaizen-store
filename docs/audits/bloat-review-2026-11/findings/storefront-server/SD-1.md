# SD-1 ✓ The proxy and every storefront page load about half of the server's code at cold start

What the server does for a storefront request (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P1. **Effort:** M. **Confidence:** high. **Step:** 2.20.
- **Second check:** corrected.
- **Where:** `src/proxy.ts:3-16`, `src/server/holding.ts:9-10`, `src/server/house-switch.ts:8-17`, `src/server/not-found.ts:21-27`, `src/server/redirect-resolve.ts:19-23`, `src/server/experiments.ts:23-24`, `src/server/customers.ts:17`, `src/lib/two-step.ts:13`, `src/lib/admin-text.ts:2-60`, `src/db/client.ts:11`, `.next/server/middleware.js`
- **Evidence:** My walk of value imports from src/proxy.ts reaches 1,311 modules, 20.6 MB of source (483 server files, 813 lib files, the schema). Loading the built proxy in a fresh node process took 920 and 948 ms and added 167 to 168 MB (the verifier: 795 to 840 ms; the bare libraries 133 to 172 ms). What the proxy calls is small: five readers. They sit in files that also hold writers, so the imports of those writers come along. The proxy reaches auth.ts three ways (holding.ts:9 for audit(), house-switch.ts:8, not-found.ts:24 through permissions.ts), pages.ts, stores.ts and seo.ts through house-switch.ts:11-17, catalog.ts through redirect-resolve.ts:19 for one tag function, redirects.ts for countHit (redirect-resolve.ts:23, not-found.ts:26), and page-content.ts (197 KB) through experiments.ts. Cutting those 16 import edges leaves 97 modules and 1.95 MB (52 and 0.5 MB once db/client.ts:11 drops the schema). For the page functions: the store layout reaches 1,466 modules; 1,011 without customers.ts:17 -> privacy-erasure.ts. The third named cut is wider than reported: admin-text.ts (every admin catalogue, 147 files, 3.7 MB) is imported by 8 files on this path, not one. With only two-step.ts changed the layout still reaches 999 and the proxy 830; the verified 872 and 702 need all eight (two-step.ts and seven server modules, five of which want the staffEmails area alone).
- **Cost today:** About 0.8 to 0.95 s and 168 MB each time a proxy instance starts cold (this machine, not Vercel), before any page on any host, static pages included. Cold starts come with each new instance and each deploy (up to 52 on 11 Nov). A cold page function loads the same knot (the verifier: the store page's page.js alone 310 to 331 ms, a lower bound). The 12 proxy runs of one home view are warm and do not each pay this. Paid by: A shopper's first byte on a cold instance; the server's memory and compute. The same for every store, whatever it uses.
- **Saving:** By the walk: the proxy from 1,311 modules to about 50 to 100 (20.6 MB of source to 0.5 to 2 MB); the layout from 1,466 to about 880. Estimate from the local timings: proxy cold start from about 0.8 s to about 0.2 s and about 130 MB less. Page functions were not timed after the cuts. Not measured on Vercel.
- **Risk:** Low to medium. These are moves, not changes of behaviour. What can break: module load order. An import cycle can make a module fail only on a cold function (D440 was that), and a memo map that ends up in two files would stop forgetStoreFacts() or forgetRunning() from clearing what the proxy reads. Noticed by: the graph test, proxy.test.ts, redirect-writers.test.ts, the address, redirect and private-mode specs, and at deploy by the page checks of SD-3 step 1.
- **Already tracked:** Partly. Step 3.14 (FD5, Open) covers fix step 2. Steps 3.13 (domain folders) and 4.1 (lint boundaries), both Open, do not name the proxy or start-up weight.
