What the server does for a storefront request (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** duplicate. **Priority:** P0. **Effort:** S. **Confidence:** medium. **Step:** 0.20.
- **Second check:** confirmed.
- **Where:** `src/server/content-grid.ts:133`, `src/server/content-grid.ts:151-156`, `src/server/menus.ts:282-288`, `src/components/content-grid-section.tsx:70`, `src/components/store-part-section.tsx:84`, `src/components/search-section.tsx:53`, `src/components/instagram-section.tsx:28`, `src/server/recommend-grid.ts:58`, `src/server/stores.ts:190-193`
- **Evidence:** 'select slug from commerce.stores where id = ...' is written 27 times in 21 files of src (my rg), almost always followed by getStore(slug). A cached helper exists, storeSlugOf() (menus.ts:283-288, cached for days, 13 uses), but storeAndMarket() (content-grid.ts:151-156) runs its own uncached statement, and the per-request parts call it: each filterable grid (content-grid-section.tsx:70), each working page's part (store-part-section.tsx:84), the search part (search-section.tsx:53), the Instagram part and the recommending grid. In my warm search measurement commerce.stores was scanned 16 to 17 times in one view; the listing's SQL reads that table too, so this is not a count of the one statement, and I did not measure a page with a filterable grid. Production: 560,090 calls, the most called statement; the verifier tied most of it to the five-minute dispatcher by arithmetic (25 per run).
- **Cost today:** 1 statement per grid or part per view on the storefront; it grows with shopper traffic on pages built with such parts. The production count mostly measures jobs. Paid by: The database and the server per request; the scheduled jobs per run.
- **Saving:** Estimate: 1 to 3 statements per view on pages with grids, parts or search. The 7,181 calls a day in production fall only as the jobs move to the helper.
- **Risk:** Low. storeSlugOf() is cached for days with no tag, on the written ground that addresses do not change (menus.ts:282); it already has 13 users. If a store's slug can ever be changed, give it a tag in the same change.

## The fix

1. storeAndMarket() (src/server/content-grid.ts:151-156) and customWhere() (:133) take the slug from the cached storeSlugOf(). Move storeSlugOf() from src/server/menus.ts:282-288 to a leaf src/server/store-slug.ts (menus.ts re-exports), so content-grid.ts does not import the menus.
2. add the count of the written-out statement to src/server/ratchet.scan.test.ts and src/server/ratchet.baseline.json, so the other 25 copies only fall; each moves to storeSlugOf() when its file is touched. refreshStoreById() (stores.ts:190-193) keeps its own read: a writer must not trust a cache.
3. Later: the place a route hands to its parts (GridPlace) carries the slug the route already resolved, and the parts need no lookup.
