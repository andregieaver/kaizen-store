# SD-15 Every page load calls a function to learn that the wishlist is empty

What the server does for a storefront request (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P0. **Effort:** S. **Confidence:** high. **Step:** 0.15.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `src/components/wishlist-heart.tsx:21-30`, `src/components/wishlist-heart.tsx:37-40`, `src/components/wishlist-heart.tsx:113-114`, `src/components/store-layout.tsx:281-285`, `src/components/site-parts.tsx:172`, `src/app/s/[store]/[market]/wishlist/saved/route.ts:9-14`, `src/server/wishlists.ts:36-52`, `src/server/wishlists.ts:64-73`, `src/components/cart-link.tsx:15-28`, `src/app/s/[store]/[market]/layout.tsx:207-209`
- **Evidence:** The header's heart shows a count (WishlistCount, store-layout.tsx:283 and site-parts.tsx:172), and its hook fetches {market}/wishlist/saved with cache 'no-store' on every full page load (wishlist-heart.tsx:21-30, :37-40). routes.json: 12 of 12 store pages measured made the call (checkout twice), the store's text page, the cart and the account among them. The address looks like a page, so the proxy runs for it too (the matcher at src/proxy.ts:57-58); my first call after a pause read the proxy's store facts. For a visitor with no wishlist cookie and no session the handler reads nothing and answers {"products":[]} (wishlists.ts:36-42; measured: 0 statements of its own, 15 bytes). The cookie is httpOnly (wishlists.ts:45), so the browser cannot know it has no list. The same document already has a per-request part that reads cookies: the cart count beside the heart (cart-link.tsx:26, inside Suspense).
- **Cost today:** One extra function call and one extra proxy run per full page load, for every visitor of every store, to say 'nothing saved' to nearly all of them. No database read unless the visitor has a list. It grows one for one with page loads; on most pages it doubles the function calls a page load makes (the document, then this). Paid by: The server per page load; the shopper's browser (one request).
- **Saving:** One function call and one proxy run per full page load, for every visitor (measured: 1 per load on 12 of 12 store pages). A shopper with a list or a session pays the same 1 to 2 statements as today, inside the document's own request.
- **Risk:** Low. The seed runs getCustomer() for a visitor with a session cookie on every document, as the fetch did; SD-11 makes that one read per request. If the seed's boundary fails, hearts stay unfilled but still work.

## The fix

1. a server component WishlistSeed (new src/components/wishlist-seed.tsx) awaits savedProductIds(store.id) (src/server/wishlists.ts:64-73) and renders a small client component, SavedSeed, exported from src/components/wishlist-heart.tsx, which calls setSaved(products) once and marks the list as loaded.
2. draw it once in the market layout, in its own boundary beside the phone bar (src/app/s/[store]/[market]/layout.tsx:207-209), only while the online shop is on: <Suspense fallback={null}><WishlistSeed store={store} /></Suspense>. It reads cookies, so it is part of the per-request stream the cart count already uses; with no wishlist cookie and no session it reads nothing.
3. useSaved() (wishlist-heart.tsx:37-40) no longer fetches. Hearts are unfilled until the seed arrives, as they are today until the fetch answers. toggleWishlistAction() stays (it returns the new list).
4. delete src/app/s/[store]/[market]/wishlist/saved/route.ts once rg 'wishlist/saved' finds no caller (one today, wishlist-heart.tsx:24).
