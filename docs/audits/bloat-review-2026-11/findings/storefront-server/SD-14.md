# SD-14 Product tiles ask the server for stock on every page load, also in stores that show none

What the server does for a storefront request (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P0. **Effort:** S. **Confidence:** high. **Step:** 0.12.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `src/lib/shop-tiles.ts:21`, `src/lib/shop-tiles.ts:35-47`, `src/components/content-grid-section.tsx:37`, `src/components/content-grid-section.tsx:139`, `src/components/content-grid.tsx:81`, `src/components/tile-shop.tsx:21-41`, `src/components/tile-shop.tsx:48-60`, `src/app/api/shop/tiles/route.ts:14-28`, `src/server/shop-tiles.ts:23-52`, `src/server/product-settings.ts:13-24`, `docs/rules/admin/website.md:726-728`
- **Evidence:** The store's two switches (stock on tiles, Add to cart on tiles) are off until an owner turns them on (DEFAULT_PRODUCT_SETTINGS, shop-tiles.ts:21). A grid's own choice is absent by default and means 'follow the store', so tileAsk() returns an ask for every product grid (shop-tiles.ts:35-39) and each tile mounts an island that fetches /api/shop/tiles (tile-shop.tsx:33). Only when the answer arrives does the browser learn the store's settings and draw nothing (tileShows(), tile-shop.tsx:55). The route reads the settings, then every named product's variants, then their stock, whatever the settings say (src/server/shop-tiles.ts:27, :30-51, :52). Measured on the local build: the demo store has no product_settings row; its home page and All products each made the call (routes.json); one call for its 10 products read product_settings +1, products +33, product_variants +67, inventory_levels +32, inventory_locations +13, inventory_reservations +16 and bundle_components +240, and committed 4 statements over the idle floor (3 by the code). The answer began {"settings":{"tileStock":false,"tileQuantity":false}, so nothing was drawn.
- **Cost today:** Per load of a page with a product grid, in every store that has not switched the feature on: one function call, 3 statements (one of them the stock of every product on the page) and an answer nobody uses. It grows one for one with page loads of home and listing pages. Paid by: The server and the database per page load; the shopper's browser (one request and the island's script).
- **Saving:** Measured cost today: 1 function call and 3 statements per load of a page with a product grid. All of it goes for every store with the default settings; a store that shows tile stock pays as now.
- **Risk:** Low. A page drawn before the owner switched the feature on shows no tile stock until its tag is refreshed, so saveProductSettings() must refresh it; the e2e covers that path.

## The fix

1. Step 1, keeps D557 as written: tileFacts() (src/server/shop-tiles.ts:23-29) returns { settings, facts: {}, buttons } right after reading the settings when both are off and no grid of the page asks on its own. The island adds own=1 to its request when an ask holds 'show' (src/components/tile-shop.tsx:21-41; the batch keeps it if any tile says so) and the route passes it on (src/app/api/shop/tiles/route.ts:17-27). Saves 2 of the 3 statements.
2. Step 2, removes the call: src/server/product-settings.ts gains a cached tileSettings(storeId) ('use cache', cacheLife("hours"), cacheTag(productSettingsTag(storeId))), and saveProductSettings() (:27-37) refreshes that tag with refreshTag(). src/components/content-grid-section.tsx:37 and :139 resolve the ask on the server with a new pure tileAskFor(own, settings) in src/lib/shop-tiles.ts, which is null when tileShows() would be false for both; ContentGridView then draws no island (content-grid.tsx:81). The route still reads the settings and the stock per request, so stock is never cached and a switch turned off stops showing at once.
3. the rule's words. docs/rules/admin/website.md:728 and the header of src/lib/shop-tiles.ts:6-8 say that the store's settings decide whether the island is drawn (cached under their own tag) and that the route still answers them with the facts. The comment at product-settings.ts:13-16 ('never in a use cache function') gets its reason kept: a change must not refresh the catalogue, and a tag of its own keeps that.

**Done when:** On a store with both switches off, loading its home page and All products in a browser makes 0 requests to /api/shop/tiles (1 each today, routes.json), asserted in e2e/shop-components.spec.ts; with tile stock on, exactly 1.

**Tests and rules that hold today's behaviour, and change with it:**

- src/lib/shop-tiles.test.ts (tileAsk and tileShows; add tileAskFor).
- e2e/shop-components.spec.ts inserts a product_settings row directly (:63) and expects stock on tiles: after step 2 it must save through the admin's action or refresh the tag, because a direct insert no longer shows until the page is drawn again.
- src/server/content-grid.int.test.ts; docs/rules/admin/website.md:726-728 (D557).

**Notes:** Missed by the report because its statement counts were made with curl, which does not run the page's scripts. This is the plainest case in the dimension of cost that does not follow use: the feature is off by default and every store pays for it on its busiest pages.
