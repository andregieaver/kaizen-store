# DS-11 ✓ Ending one sandbox runs at least 800 deletes and holds about 2,100 locks, one pass per store table per round

The database's shape (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** oversize. **Priority:** P3. **Effort:** S. **Confidence:** medium. **Step:** 4.4.
- **Second check:** corrected.
- **Where:** `supabase/migrations/20261111172839_baseline_1_schema.sql:15374-15424`, `src/server/sandbox.ts:351-367`, `src/server/sandbox.ts:369-380`, `docs/builder-sandbox.md:214`
- **Evidence:** purge_sandbox() loops over every commerce table with a store_id column but two and runs a dynamic DELETE in its own exception block, and repeats the whole pass until a pass deletes nothing (baseline_1:15393-15417): at least two passes. On the real schema that is 400 tables. I ran the function's own loop in PGlite for a store id that owns nothing: one pass is 400 statements, took 64 to 293 ms (the first run, with cold caches, the longest), and left 2,129 relation locks held by the transaction, because planning each delete locks the table and all its indexes. It is the only function in the baseline that builds statements from the catalog. purgeSandboxes() takes up to 25 sandboxes a run, one after the other (sandbox.ts:369-380).
- **Cost today:** Estimate: 0.1 to 0.5 s of database time per ended sandbox. Measured: about 2,100 lock entries held until commit, which is a third of a default Postgres lock table (64 a connection, 100 connections). Both rise with every table and index added, not with what the sandbox held. The cost follows use, one visitor's try of the builder. Paid by: The database, per expired sandbox
- **Saving:** No time saved by step 1; it removes the case of two purges holding about 4,300 lock entries together. Step 3, if ever needed: from about 2,100 locks in one transaction to about 300.
- **Risk:** Low for step 1. Medium for step 3: the function is the guarantee that nothing of a sandbox is left, so the split must end with a pass that finds nothing.

## The fix

1. Small step, now: a custom migration that replaces commerce.purge_sandbox() with the same body and one new first statement, PERFORM pg_advisory_xact_lock(hashtext('commerce.purge_sandbox')), so two purges never hold their locks at the same time (two dispatcher runs can overlap).
2. Read production's limits once (show max_locks_per_transaction; show max_connections) and write them in docs/builder-sandbox.md beside the measured 2,129 locks a purge holds.
3. Only if those limits leave less than about four times a purge's locks, or sandboxes are purged by the hundred a day: split the work. A new function commerce.purge_sandbox_part(p_sandbox uuid, p_after text, p_tables integer default 50) deletes from the next 50 store tables and returns the last name; purgeSandbox() in src/server/sandbox.ts:365 calls it in a loop, each call its own transaction, in rounds until a full round deletes nothing; a last function then writes the tombstone and the sandbox's state as lines 15418-15422 do. No transaction then holds more than about 300 locks.
4. Whatever is done, keep the guarantee: the purge refuses any store that is not a closed sandbox whose row is expired, and ends only when a full pass deletes nothing.

**Done when:** src/server/sandbox.int.test.ts has a case where two purges started together both finish, and docs/builder-sandbox.md states production's max_locks_per_transaction and max_connections beside the 2,129 locks one purge holds.

**Tests and rules that hold today's behaviour, and change with it:**

- src/db/sandboxes.test.ts:313-327 and :406 (the purge refuses any other store; it returns the rows deleted) and src/server/sandbox.int.test.ts (files first, then rows): must pass unchanged after step 1.
- src/server/sandbox.int.test.ts runs on a real Postgres: add a case that two purges started together both finish, one after the other.
- Rule: docs/builder-sandbox.md:214-222 (what purge_sandbox() refuses and that it deletes every row of the store).

**Notes:** Not worth more than step 1 now: the cost follows use, is a fraction of a second, and one purge fits a default lock table. The verified report's fix (ask first which tables hold a row) would not lower the lock count: the asking locks the same tables and indexes. DS-12's count will show this cost growing with the schema.
