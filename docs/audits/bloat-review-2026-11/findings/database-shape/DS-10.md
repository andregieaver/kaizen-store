# DS-10 ✓ Where each picture is used is found by text-searching every page's JSON, again every day for every picture

The database's shape (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P1. **Effort:** S. **Confidence:** medium. **Step:** 0.21.
- **Second check:** corrected.
- **Where:** `src/server/media-library.ts:25-32`, `src/server/media-library.ts:317-322`, `src/server/media-library.ts:795-814`, `src/server/media-library.ts:825-830`, `src/server/media-library.ts:857-873`
- **Evidence:** mediaUses() casts each page's draft and published JSON to text and searches it for each picture's address and its small copy's (media-library.ts:321-322), and does the same for entries, menus, saved parts, the theme and navigation. embedMedia() treats a picture as stale when its vector is older than one day, 'so what uses an item is kept current' (:795-799, :810), and calls mediaUses for up to a run's worth of pictures; unchanged texts only have their date moved on (:825-830). The five-minute job loops over every site with media (:857-873). Production: the uses statement ran 3,053 times at 47 to 925 ms, about 380 s; media_embeddings took 13,414 updates on 468 rows. A written rule explains the search: uses are 'never stored, so it is always true' (:27-28).
- **Cost today:** About 380 s of database time per 78 days today, the second costliest app statement. It grows with pictures times pages per site, for every site with media, every day, whether or not anything changed. Paid by: The database and the server per cron tick; the owner's media library when it shows uses, which follows use
- **Saving:** Estimate: most of the 3,053 scans and of the 13,414 date-only updates per 78 days; at scale one small read per idle site per tick instead of a full search a day.
- **Risk:** Low. What could break: a place that shows pictures and is missing from the stamp, so its 'used in' words go stale; the new test case for each branch shows it. The words follow the next save of the site instead of the next day.

## The fix

1. Keep the rule: uses are looked up, never stored. In embedMedia() replace the one-day clause at :810 with a change test. Before the stale read, read one stamp for the site: the greatest of max(updated_at) over the site's rows in the tables mediaUses() reads (the branches from :321 on: pages, products and their media, content entries, menus, saved parts, the store's or platform's settings, theme looks). Pass it in: `or e.updated_at < ${changedAt}::timestamptz` in place of `or e.updated_at < now() - interval '1 day'`.
2. For a branch whose table has no updated_at column, keep the daily clause for that case only and say which in a comment. Check each table in src/db/schema.ts before writing the stamp query.
3. refreshMediaEmbeddings() (:857-873): ask the cheap question first and call aiFor() only for a site with stale rows: select exists (… e.media_id is null or e.updated_at < m.updated_at or e.updated_at < changedAt). A changed model (e.space <> space) is caught once a day: run the full check when now.getUTCHours() === 3 and now.getUTCMinutes() < 5, as autopilot-effects.ts:44 gates its hourly part.
4. Change the comment at :795-799 from 'or once a day' to 'or when something that can show a picture was saved since'.

**Done when:** On production n_tup_upd of commerce.media_embeddings in pg_stat_user_tables grows by fewer than 50 a day while no content changes (about 172 a day today: 13,414 in 78 days).
