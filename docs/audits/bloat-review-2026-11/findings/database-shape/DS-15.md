# DS-15 Indexes are declared in two places and nothing compares them, which is how duplicates reached orders and order_lines

The database's shape (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** no check. **Priority:** P1. **Effort:** S. **Confidence:** high. **Step:** 0.26.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `supabase/migrations/20261111172841_baseline_3_rules.sql:10328`, `supabase/migrations/20261111172841_baseline_3_rules.sql:10062`, `supabase/migrations/20261111172841_baseline_3_rules.sql:10076`, `src/db/schema.ts:4899`, `src/db/schema.ts:5092`, `docs/ci-migrations.md:60-62`, `src/db/migration-safety.scan.test.ts:20`, `package.json`
- **Evidence:** An index is made either in src/db/schema.ts (drizzle writes the migration) or by hand in a custom migration, as the rule for hot tables requires for a concurrent build (docs/ci-migrations.md:60-62). pnpm db:check compares schema.ts with drizzle's own snapshot, so a hand-written index is invisible to it. On the migrated test database 46 of the 1,059 non-unique indexes are named nowhere in schema.ts, 12 of them on hot tables. Two of those 12 are twins of a declared index: orders_invoice_candidates_idx (baseline_3:10328) has the key of orders_store_placed_idx (schema.ts:4899), and order_lines_analytics_idx (baseline_3:10062) has the key of order_lines_order_idx (schema.ts:5092, baseline_3:10076). No test looks for an index led by another: a catalog query I ran on the test database finds 11 such plain indexes today.
- **Cost today:** No direct cost. Each duplicate that slips in is one more index entry on every write of its table, and the hot tables are where hand-written indexes are made. Paid by: The database per write, later; CI
- **Saving:** No direct saving; it stops the next duplicate on a hot table at the commit that adds it.
- **Risk:** Low. A test only. What could break: a deliberate covering twin; the allowed list with a reason is the way through.
- **Already tracked:** Partly: code review FD7 proposes a standing unused-index check after traffic (step 3.15, Open). A duplicate check at commit time is new.

## The fix

1. Add src/db/index-duplicates.test.ts, using createTestDatabase() from src/db/testing.ts like the other src/db tests. It runs one catalog query: for btree indexes of schema commerce, list each plain (not unique) index A whose key columns, taken with pg_get_indexdef(indexrelid, k, true) for k in 1..indnkeyatts, equal the leading columns of another index B on the same table, where B is longer, or unique, or A's name sorts after B's. The working query is in the scratch file named in notes.
2. First case: A and B both without a WHERE clause. Expect no rows. Today it returns 11 distinct indexes (12 pairs); DS-9 removes them, so land this test with DS-9 or start with those 11 names in an allowed list that DS-9 empties.
3. Second case: A partial, B not partial, same leading columns. Expect only an allowed list, each with its reason in the test: ai_usage_autopilot_idx, order_events_restock_idx, price_lists_exclusive_idx, payments_captured_idx, orders_list_placed_idx and orders_list_archived_idx (selective conditions or different order). orders_retention_idx and orders_invoice_candidates_idx are on it only until DS-9 drops them.
4. Add one sentence to docs/ci-migrations.md after line 62: an index written by hand is checked against the table's other indexes by src/db/index-duplicates.test.ts; when it replaces a declared one, the declared line leaves schema.ts in the same change.

**Done when:** pnpm test runs src/db/index-duplicates.test.ts; its first case returns 0 rows (11 today) and it fails when a scratch migration adds create index on commerce.orders (store_id, placed_at).
