# The product's surface (FT)

Part of `docs/audits/bloat-review-2026-11.md`, on commit 0bd814c. One reviewer's reading of this area. A tick (✓) marks a finding the lead checked a second time; the others were not checked. "Step" is the step of the plan that closes the finding.

**In short.** The surface is far larger than its use: 560 pages, 110 store navigation links, 254 AI manager tools, 83 five-minute jobs and 481 tables serve 60 stores and 102 orders. About 100,000 lines of code (13% of src, a lower bound by file name), 42,000 lines of tests and 146 tables belong to 31 feature groups in which no store has ever written a row; most were built in the last weeks, so they are unused so far, not proven unneeded. The switch system (D178) is well made but covers 14 features only, and a switch hides links, pages and tools while the feature's scheduled work keeps running. Nothing limits growth: 158 decisions were recorded in the 13 days after feature waves were paused on 29 October, and the platform parity rule adds a twin to each.

## Well made, and should stay

- The switch system itself (D178): one registry with needs checked transitively, kept in step with the navigation, the admin map and the AI tools by tests; switching off deletes nothing and says what stops it (src/lib/store-features.ts, src/server/store-features.ts, src/components/admin/feature-off.tsx:43).
- A new store starts with the shop alone (src/lib/store-features.ts:202), and the navigation is filtered by features and permissions in one place (src/lib/store-nav.ts:388-401).
- The storefront reads a switched feature only while it is on: reviews (src/app/s/[store]/[market]/p/[handle]/page.tsx:132), subscriptions (account/account-section.tsx:72), and the referral capture script is drawn only while a programme is on (src/components/store-affiliate.tsx:10-14).
- Basic view has a budget that a test holds: at most 12 links a section and under half of all links (src/lib/store-nav.test.ts:250-253).
- The store Home streams its optional cards and draws the Deals card only when Deals is on (src/app/admin/(gated)/[store]/page.tsx:136-169).
- eBay's job returns before any query when the platform does not offer eBay (src/server/ebay.ts:478): 8 ms a run. It is the pattern the other jobs lack.
- Plan features only describe plans; they are not a second gating system (src/lib/plan-features.ts:4-6).
- One event intake feeds Zapier/Make/Slack, owners' endpoints and workflows (commerce.queue_integration_event, src/server/webhook-endpoints.ts:19-24, src/server/workflows.ts:41-47): not three pipelines.
- Work reuses the shop's e-invoice primitives and number series rather than copying them (src/lib/work-einvoice.ts:3, src/server/work-invoices.ts:803), and Work clients link to customers (work_clients_customer_idx, src/db/schema.ts:11498).
- Moving in from Wix, Squarespace, BigCommerce and Shopware exist as proposals in docs only (D447-D451); rg finds no importer code for them in src, so they cost nothing to keep.
- The AI manager already caps a round at 124 tools and loads the rest on request (src/lib/tool-budget.ts:15, 67-96).

Keep returns, privacy, invoices and accessibility always on: the law needs them. This parks; it retires nothing.
- **Saving:** Estimate: a new shop's Advanced navigation from 94 to about 75 links; AI tools offered from 234 to about 155; 35 of 83 five-minute jobs skippable. If the owner later retires groups outright, up to 100,406 code lines, 41,575 test lines and 146 tables (measured by file name and table name).
- **Risk:** An owner who needs a parked feature must find its switch: the Features page, the FeatureOff notice and the AI manager's set_feature tool already cover that. More switches make the Features page longer; group them. Addresses keep working because FeatureOff answers in place of the page.

### FT-3 A feature's scheduled work runs whether or not any store uses it; the switch does not reach it

- **Kind:** eager. **Effort:** M. **Confidence:** medium. **Step:** 0.4.
- **Where:** `src/app/api/cron/cart-reminders/route.ts:128`, `src/server/cron-runs.ts:117`, `src/server/bonus.ts:550`, `src/server/fiken-sync.ts:520`, `src/server/ebay.ts:478`, `src/app/api/cron/broadcasts/route.ts:26`, `src/app/api/cron/integrations/route.ts:27`, `src/app/api/cron/autopilot/route.ts:18`
- **Evidence:** The dispatcher starts 78 jobs at once every five minutes, then 5 more. I opened 20 of them: each begins with a query on its own table with no check that any store has the feature on (bonus.ts:550-576 runs four statements; fiken-sync.ts:525 selects from fiken_connections, which has never held a row). 35 jobs serve tables that have never held a row: plans, calendars, commissions, api-idempotency, oauth-tokens, content-moderation, activities, business-changes, pipedrive, fiken, store-copies, affiliates, recommendations, instagram, returns, invoices, low-stock, supplier-orders, ebay, sms, edit-expiry, support-actions, tracking, summaries, analytics-alerts, follow-ups, life-handoffs, three autopilot jobs, report-emails, schedules, ui-translations, two domain jobs. Their last durations sum to 4,012 ms of 12,111 ms. Three of the nine every-minute routes do the same for broadcasts, automations, review requests, gift cards, ad conversions, workflows, platform workflows and the autopilot, all with empty tables. Only eBay returns early (8 ms).
- **Cost today:** 35 x 288 = 10,080 job runs a day and as many cron_jobs upserts, about 4.0 s of database-bound job time per five-minute run, for nobody; plus 3 x 1,440 function calls a day whose work finds nothing. integration_deliveries alone took 66,533 updates and 66,533 deletes on a table that has never held a row. Paid by: The server (Vercel function time) and the database, every one and five minutes
- **Fix:** Give each job in the dispatcher a declared need: a feature id, or a table that must hold a row. Before the jobs, run one statement that answers all needs (which features any active store has on; exists() per named table), cache it for an hour, and skip jobs whose need is unmet, recording the run as skipped so cron-health does not call it late. Do the same inside the three every-minute routes.
- **Saving:** Estimate from last durations: about one third of the dispatcher's job time (4.0 of 12.1 s) and 10,080 job runs a day; more as FT-1 switches features off for new stores.
- **Risk:** A feature's first use must not wait for the hourly cache: clear it when a feature is switched on or the first row is written. The rule that every job is kept in commerce.cron_jobs (CLAUDE.md, Conventions) stays true if a skip is recorded as a run.
