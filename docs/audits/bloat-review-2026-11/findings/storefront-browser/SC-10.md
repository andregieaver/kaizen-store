# SC-10 ✓ Every document load asks the server for the wishlist, also for visitors who have none

What a shopper's browser loads (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P0. **Effort:** S. **Confidence:** high. **Step:** 0.15.
- **Second check:** corrected.
- **Where:** `src/components/wishlist-heart.tsx:21`, `src/components/wishlist-heart.tsx:37`, `src/components/wishlist-heart.tsx:113`, `src/components/store-layout.tsx:283`, `src/components/site-parts.tsx:172`, `src/app/s/[store]/[market]/wishlist/saved/route.ts:9`, `src/server/wishlists.ts:36`, `src/server/wishlists.ts:64`, `src/app/s/[store]/[market]/layout.tsx:207`
- **Evidence:** Re-tallied in this pass: all 12 measured storefront pages fire GET .../wishlist/saved once (1,743 bytes transferred for a 15-byte answer, private no-store), also pages with no heart on them, because the header's WishlistCount loads it (wishlist-heart.tsx:113-114, drawn at store-layout.tsx:283 and site-parts.tsx:172). The answer comes from a route handler (wishlist/saved/route.ts:9-14): a function call on top of the page's own. savedProductIds() answers an empty list without a query when the visitor has neither a customer session nor the wishlist cookie (wishlists.ts:36-42, 64-66). The module keeps the list for the life of the document (wishlist-heart.tsx:12-23), so client-side moves do not ask again; every full load does. The wishlist cookie is httpOnly, so the browser cannot know it has no list. Wishlists are not a feature a store can switch off. The document itself is already rendered per request (its response is private, no-store, and the layout streams the cart count per request, layout.tsx:207-212), so the same answer can ride in that stream.
- **Cost today:** One extra function call and 1.7 KB per document load for every visitor of every selling store. It is per visit, not per first visit, so it grows most directly with shoppers. Paid by: The server per request; a shopper's browser
- **Saving:** Measured: one function call and 1,743 bytes per document load, on 12 of 12 pages, for every visitor of every selling store. A visitor with saved products gets them in the page's own stream instead.
- **Risk:** Low. A list changed in another tab shows after the next full load or press, as today. The seed must stay a per-request part: if it were ever drawn inside a cached scope, one visitor's saved products would be sent to others; reading cookies keeps it per request, the same guard as the cart count, and the e2e test with two browsers' lists would show it.

## The fix

1. src/components/wishlist-heart.tsx: add a client component WishlistSeed({ products }: { products: string[] }) that calls setSaved(products) in an effect and draws nothing. Remove load() and the fetch (lines 21-30 and the effect at line 38): useSaved() only subscribes. The hearts stay unpressed until the seed arrives, as they did until the fetch answered.
2. New server component src/components/wishlist-saved.tsx: WishlistSaved({ storeId }) awaits savedProductIds(storeId) (src/server/wishlists.ts:64) and returns <WishlistSeed products={...} />. Run the read through perRequest('wishlist-saved:' + storeId, ...) while the layout is still drawn twice (SC-8).
3. src/app/s/[store]/[market]/layout.tsx: after the bottom bar's boundary (line 209) draw {selling && <Suspense fallback={null}><WishlistSaved storeId={store.id} /></Suspense>}. It reads cookies, so it is a per-request part of the page's own stream, as the cart count is; the prerendered shell does not change. Its own boundary keeps it out of React's 12.8 kB budget (the note at lines 201-206).
4. Delete src/app/s/[store]/[market]/wishlist/saved/route.ts. Take its address out of src/lib/visit-record.test.ts:125 and docs/store-features.md:290.
5. e2e/wishlist.spec.ts: add that a load of /s/demo/no makes no request to /wishlist/saved; and that after saving a product and a full reload the heart is pressed and the header's count shows 1.
6. Docs: where docs/rules/storefront.md or D34 say the saved products are fetched once per page, say they come with the page's per-request stream. Lower the after-load budgets (SC-6).
