# SC-13 A store in a language translated by AI sends its whole interface text in every page; the browser reads 114 of its 1,673 texts

What a shopper's browser loads (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** oversize. **Priority:** P1. **Effort:** S. **Confidence:** medium. **Step:** 0.8.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `src/app/s/[store]/[market]/layout.tsx:131`, `src/app/s/[store]/[market]/layout.tsx:160`, `src/server/ui-text.ts:47`, `src/server/ui-text.ts:127`, `src/components/ui-texts.tsx:17`, `src/lib/browser-text.ts:16`, `src/lib/returns-text.ts:15`, `src/app/s/[store]/[market]/withdraw/withdraw-flow.tsx:57`, `docs/performance.md:52`, `docs/audits/bloat-review-2026-11/scripts/sources/plan-sc/catalog-size.cjs.txt`
- **Evidence:** Read in code in this pass. The market layout hands the client component UiTexts whatever uiTextsFor(market.lang) returns (layout.tsx:131, 160). For a language without hand-written text that is every 'ui:' text of the language: loadLanguage() keeps all rows whose key does not start with 'email:' (ui-text.ts:48-53) and uiTextsFor() returns that map (ui-text.ts:127-129). A prop of a client component is written into the page's inline payload, so every page of such a store carries it. In the browser it is laid over browserText('en') only (ui-texts.tsx:21, browser-text.ts:16-18); the one other reader is the withdrawal page (returns-text.ts:19-20, withdraw-flow.tsx:57). Measured from the real catalogue with English as the stand-in (work/plan-sc/catalog-size.cjs runs catalogOf() of src/lib/ui-catalog.ts on the message files): the whole catalogue is 1,673 texts, 92,919 bytes of JSON, 99,613 bytes as written in the HTML, 25,416 gzip. The browser's texts are 114 texts, 5,862 bytes, 1,886 gzip. The withdrawal function's are 144 texts, 10,411 bytes. The home document is 138,410 bytes / 18,691 gzip today. docs/performance.md:52-60 (D212) states the rule this breaks: a visitor's browser gets only the texts its client components read. For nb, sv, da and en the prop is null and nothing is sent. Not run in a browser: the seed has no translated language, so the sizes are an estimate from the catalogue.
- **Cost today:** About 100 KB raw / 25 KB gzip more in every document of a store whose language is not nb, sv, da or en: the home document would be about 1.7 times its size raw and more than twice compressed. The same in every prefetch answer that carries the layout. Nothing for stores in the four hand-written languages. The cost falls only on stores that use the feature, but it is sixteen times what they need, on every page view, and Kaizena Flow sells EU-wide, where most languages go through this path. Paid by: A shopper's browser (download and parse on every page); the server per request (it serialises the map each time)
- **Saving:** Estimate from the real catalogue, English as the stand-in: about 93 KB raw (99.6 KB as written in the HTML) / 23.5 KB gzip per document in a store in an AI-translated language. Nothing changes for nb, sv, da and en.
- **Risk:** Low to medium. A text a client component reads that is not in the browser files would show in English: by D212's rule every such text is there, and the scan test keeps client components from the whole language. The withdrawal page must register its part before its flow renders; drawn above it, as the layout does, it is. No e2e spec runs a translated storefront language today, so step 5's hand check matters.

## The fix

1. src/server/ui-text.ts: compute once the key set of catalogOf('ui', enBrowser) (import enBrowser from src/lib/messages/en-browser.ts) and of catalogOf('ui', { returns: enReturns }). In loadLanguage() (lines 47-54) keep, beside the whole map the server's registry uses, a browser map with only the first set's keys. uiTextsFor(lang) returns the browser map. Add returnsTextsFor(lang) for the second set.
2. src/components/ui-texts.tsx: let registrations add to one another. Take a prop part ('browser' by default), remember the version per lang and part, merge texts into what the registry already holds for the language (registerMessages(lang, { texts: { ...registeredTexts(lang), ...texts } })), and build ui only for the browser part.
3. src/app/s/[store]/[market]/withdraw/page.tsx: draw <UiTexts lang={market.lang} texts={returnsTextsFor(market.lang)} part='returns' /> before the withdrawal flow, so returnsText() (returns-text.ts:19) still finds the function's words in a translated language.
4. Then look at ui-catalog in the first scripts (6,975 bytes, left open by SC-3): its CHOOSING table holds templates and prepare functions for 'email:' keys and for 'ui:' keys no client component reads. Split the table by reader if the measure shows more than 3 KB to gain; otherwise leave it.
5. Tests: a unit test (src/lib/ui-catalog.test.ts or a new src/server/ui-text.test.ts) that for a language with every key translated uiTextsFor() holds exactly the 114 browser keys. An integration test beside src/server/languages.int.test.ts: after generating 'de', the prop holds no server-only key (for instance 'ui:storeSummary'). By hand in a browser, in German: a client component's words (the gallery's labels, the cart's quantity words) and the withdrawal page read German.
6. docs/performance.md:52-60: add that a language translated by AI sends the same few texts, and the withdrawal page its own.

**Done when:** The new unit test passes: for a language with every key translated, uiTextsFor(lang) holds 114 keys and JSON.stringify of it is under 9,000 bytes (92,919 for the English stand-in today).
