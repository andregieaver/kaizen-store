# SF-7 ✓ Nothing counts what a server entry loads, so the cycle grew unseen

Server functions: size, cold start, per-request overhead (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** no check. **Priority:** P0. **Effort:** S. **Confidence:** high. **Step:** 1.5.
- **Second check:** confirmed.
- **Where:** `docs/performance.md:37`, `src/lib/storefront-bundle.scan.test.ts`, `src/lib/pay-routes.graph.test.ts:13-60`, `src/server/ratchet.scan.test.ts`, `next.config.ts:67-69`, `.github/workflows/ci.yml:152`, `docs/audits/code-review-2026-11.md:129`, `docs/audits/code-review-2026-11.md:532`
- **Evidence:** The browser's scripts have a budget test (storefront-bundle.scan.test.ts) and unchecked reads have a ratchet. One import-graph test exists, src/lib/pay-routes.graph.test.ts, and it checks only that the pay routes reach no forbidden module, not how much anything loads. I searched the 44 scan tests of src/lib and src/server and ci.yml for nft, cycle, circular and .next/server: nothing counts a server entry's imports, its cycle, its trace or its cold load. So the cycle reached 229 files, one re-export put the beacon in it (SF-4), and a comment in next.config.ts:67-69 accepts that every route carries the taxonomy. A file-level graph is a sound basis for a test: the verified report matched it against the build's chunk source maps (1,294 against 1,306 files for the beacon, 54 against 54 for /api/health), and in this pass the files six handlers import only lazily were all absent from their start chunks. Rebuilding the graph of 4,136 files takes about 5 s.
- **Cost today:** No direct cost. Without it, SF-1 to SF-6 grow back with the next features, as they grew in. Paid by: Everyone who pays SF-1 to SF-6, later.
- **Saving:** No direct saving. It keeps the other findings' savings and makes each later cut a visible number.
- **Risk:** Low. A regex walk counts a few files more than the build loads (it cannot see an import used only as a type without the type keyword; 8 such imports today), which the baseline absorbs. The numbers in this review come from a TypeScript-parser walk, so the first baseline will differ by a few files (the storefront-data plan's regex walk gives 1,311 for the proxy where the parser gives 1,309).
- **Already tracked:** partly: code review step 4.1 (FH7, FH8; Open) plans lint rules for boundaries, but lists no cycle or reach rule.

## The fix

1. One test file, one baseline and one script, shared with DP-6 and SD-13 step 1 of this review (SD-1 step 5 calls the same test src/proxy.graph.test.ts): make one.
2. scripts/lib/route-load.mjs: move the import walk (IMPORT, typesOnly(), importsOf(), resolve(), reach()) out of src/lib/pay-routes.graph.test.ts into it, as ratchet.scan.test.ts shares scripts/lib/ratchet-count.mjs; the pay-routes test imports it and must pass unchanged. Add an option that follows static value imports only (import type and import() are not followed; a "use client" file is a leaf), Tarjan's strongly connected components over src/server, and entryReach(entry), the count of files an entry reaches. scripts/route-load.mjs prints the largest cycle and each named entry's count and, with --write, lowers src/server/route-load.baseline.json (the pattern of scripts/ratchet.mjs).
3. src/server/route-load.graph.test.ts: (a) the largest cycle in src/server is no larger than the baseline (229 at the start), and the test also fails when it is smaller until the baseline is lowered; (b) the same for the file count of each named entry: src/proxy.ts, src/instrumentation.ts, src/app/api/health/route.ts, the four /api/visit routes, src/app/api/fonts/css/[slug]/route.ts, src/app/api/shop/tiles/route.ts, src/app/robots.txt/route.ts, src/app/api/cron/page-jobs/route.ts, src/app/s/[store]/[market]/layout.tsx, page.tsx and p/[handle]/page.tsx, src/app/admin/(gated)/[store]/orders/page.tsx; (c) what each may not reach (the lists SF-2, SF-4 and SF-5 give), with a named exception list that may only shrink.
4. scripts/route-budget.mjs, run after pnpm build in CI's e2e job (.github/workflows/ci.yml:152). For the proxy, /api/visit, /api/health, /api/shop/tiles and the storefront home it sums the chunks the built entry lists for loading at start and the files of its .nft.json, and fails over today's figure plus 4%. It prints, without failing: the ten largest traces; the bytes of chunk files with identical content (SF-11); the counts in .next/routes-manifest.json (SF-13); and a fresh-process cold load of the proxy, the beacon and the start hook (require the built entry with NODE_ENV=production and NEXT_RUNTIME=nodejs, then routeModule.ensureUserland(); time, heap after gc, files in require.cache), since timings are too noisy in CI to gate on.
5. docs/performance.md: a section 'What a function loads' with the measured figures, two rules (import a helper from the file that defines it, never through a feature's module; a module or package most requests do not need is loaded with import() where it is used) and the names of the guards.
