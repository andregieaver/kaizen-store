# Server functions: size, cold start, per-request overhead (SF)

Part of `docs/audits/bloat-review-2026-11.md`, on commit 0bd814c. Read by one reviewer, challenged by a second (who re-opened every citation, re-measured every number and applied the owner's note that the platform is not open yet) and planned by a third. A tick (✓) marks a finding the second reviewer confirmed or corrected; one the planner added has none. Each finding has a file of its own beside this one.

**In short.** One import cycle of 229 server modules makes 559 of 562 pages, 181 of 268 route handlers and the proxy load the same 11 MB of server code: re-measured in this pass, such an entry needs 0.84 to 1.09 s and 71 to 83 MB to start where a route outside the cycle needs 0.16 s and 14 MB, and a start hook adds 0.33 s before any request. None of this rests on a feature being unused; every store pays it after each deploy (90 commits to main on 11 November), on scale-out and after idle, and it grows at opening as many quiet stores meet cold instances. Thirteen findings stand (eleven verified, two added) and seven of them are import changes with no data moved: on the import graph they take the visit beacon from 1,306 source files to about 100, the proxy from 1,309 to about 95 and a storefront page from about 1,420 to about 600, where the page renderer is the floor. Added by this pass: every store's own domain is compiled into each deployment (4 to 8 routing rules a store against Vercel's 2,048 a deployment, of which this app's own dynamic routes already take 685, and a full redeploy per domain change), and the list of those domains is parsed again for every link a page draws.

## Well made, and should stay

- Nothing in this dimension argues from 'no store uses it'. Every finding is a cost paid per cold start, per request, per build or per store, whatever a store uses. The two that lean on production's counts (the start hook's query, the nine every-minute routes) are read as idle cost, and SF-10 is ranked last for that reason.
- The routes outside the cycle show the floor and are well made: /api/health loads 17 chunks (1.14 MB) and starts in 159 to 163 ms with 14.4 MB; /api/ab/assign 1.56 MB, 240 ms, 22.2 MB; /api/consent and /api/csp-report reach 55 and 54 source files.
- A server-side await import() does give a chunk that loads on demand in this build: the files six light handlers import only lazily are absent from their start chunks, and the start hook's own entry file is 169 bytes: its 2.33 MB of chunks load only when register() runs. 58 such imports already exist in 30 files of src/server. The rule about import() in docs/performance.md:39 is about a visitor's client scripts, not server chunks.
- Chromium is traced only into the routes that launch it (three cron routes, the replicator's tick, two admin PDF routes, the shopper's document PDF, the PDF job); Playwright, @sparticuz/chromium, unpdf and mammoth are imported on demand (src/server/browser.ts:11-15). playwright-core's JS is also traced into four replicator entries that start no browser: small.
- The proxy's per-request work is light when warm: no fetch, pure decisions in src/lib, one store-facts read per store per instance per 10 s (src/server/redirect-resolve.ts:203-232), A/B tests read only with the kaizen_ab cookie, held-domain lookups only for hosts that are no store's, the 404 count after the response. The 10-second bound serves private mode, so it is not a finding. The one per-request cost that grows is the hosts list (SF-12).
- No client component imports a server-only module, directly or through src/lib: 0 of 495 client files on the graph; 787 modules carry import "server-only".
- Environment variables are validated when used, not at import. The database pool is created on the first db() call, 5 connections, 5 s idle (src/db/client.ts:14, 63-71, 95-98). Keeping an instance running until its idle connections close (attachDatabasePool, line 77) is by design and is weighed in the scheduled-work plan (CR-1), not here.
- No route sets a runtime; nothing is on the edge runtime, which fits cacheComponents. All 13 cron routes have a maxDuration; eleven run through trackedRoute(), the five-minute dispatcher runs its jobs through runJobs(), and /api/cron/document-pdfs is left out on purpose (src/server/cron-routes.scan.test.ts). The shopper chat route sets no maxDuration; what bounds it is the project's default, which was not visible, and its AI calls time out at 30 s by themselves.
- Next loads a handler's own code lazily (userland behind a require), and source maps (about 672 MB of the build) are in no function trace.
- JSON imported as modules is small (google-fonts.json 71 KB, no-saft.json 88 KB). The 13 MB taxonomy is read from disk on first use, not at import, and the product page reads it inside a cached function.
- src/lib/page-content.ts (4,319 lines) costs little at import: it is not among the costliest files of the cold-load profile. The zod cost at start comes mostly from the AI manager's tool definitions (src/lib/owner-tools.ts, about 44 ms in the profile), which SF-1 takes out of every entry but the AI's own.
- The docs' Markdown (0.8 MB) and HarfBuzz's wasm (0.7 MB) are traced only into the 22 and 1 entries that read them.
- One import-graph test already exists and is sound: src/lib/pay-routes.graph.test.ts keeps forbidden modules off the pay routes and follows import() too, so the lazy imports planned here cannot hide a module from it.
- The list of every store's hosts does not reach the browser (the verified client-bundles report: no client chunk parses NEXT_PUBLIC_STORE_HOSTS).
