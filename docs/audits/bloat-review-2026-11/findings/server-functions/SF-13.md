# SF-13 Every store's own domain is compiled into each deployment: routing rules against a cap of 2,048, and a full redeploy per change

Server functions: size, cold start, per-request overhead (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P1. **Effort:** L. **Confidence:** medium. **Step:** 2.20. **The owner's choice.**
- **Second check:** added by the planner, not checked a second time.
- **Where:** `next.config.ts:95-103`, `next.config.ts:113-114`, `src/lib/store-hosts.ts:60-103`, `src/lib/store-hosts-build.ts:11-36`, `src/server/domains.ts:82-101`, `src/server/domains.ts:189`, `src/server/domains.ts:265`, `src/server/domains.ts:304`, `src/server/domains.ts:324`, `src/server/domains.ts:361`, `src/server/domains.ts:398`, `src/server/vercel.ts:125-130`, `src/app/admin/(gated)/[store]/settings/domains/page.tsx:66`, `docs/platform.md:17`, `docs/platform.md:19`, `docs/cells.md:57`, `src/db/schema.ts:9872`, `.next/routes-manifest.json`
- **Evidence:** A store's active domains are read from the database when a deployment is built (next.config.ts:95, src/lib/store-hosts-build.ts) and become routing rules and a constant in the code (decision P8, docs/platform.md:19). Counted here by running storeHostRoutes() on sample input: 4 rules with no store domain at all, then 4 more for each store with a primary domain, 5 with its www alias, 8 with two country domains; 300 stores with www and apex make 1,504 rules. This build's routes manifest already holds 685 dynamic routes, 9 redirects, 8 header rules and 3 rewrites. Vercel's limits page (fetched in this pass, last updated 2026-09-16) caps 'Routes created per Deployment' at 2,048 on Hobby and Pro, counts each rewrite, redirect and header, and says Next's dynamic routes create routes too; deploy hooks may fire 60 times an hour. If each dynamic route counts once, about 270 stores with a domain and its www alias fill the cap; how Vercel's builder counts this app's 685 dynamic routes was not visible, and it may be more than once each. Every change of a domain asks for a new deployment: requestDeploy() is called from six places in src/server/domains.ts (lines 189, 265, 304, 324, 361, 398) and the Domains page asks again while the running deployment lags (page.tsx:66, held to once in 15 minutes). A deployment is a full build (263 s and a 7.26 GiB peak in this review's build; Vercel's build machine has 8 GB) that empties every instance's caches and makes every function start cold (SF-1). The reason decision P6 gives for routing in configuration (docs/platform.md:17: it adds no function call to a page view) no longer holds for pages: the proxy is a Node function in front of every store page (SF-2) and already reads each store's facts every 10 s. Looking a host up at run time is one read through an existing unique index (store_domains_active_hostname_idx, src/db/schema.ts:9872).
- **Cost today:** Little today: few stores have a domain. At opening, each store that connects or changes a domain costs one full production deployment for everyone (build minutes, all caches emptied, all functions cold) and 4 to 8 routing rules for the life of the store. The cap is a documented limit; what Vercel does with a deployment past it was not observed, and at that point it would concern every deploy, not one store. Paid by: The build and CI per domain change; every store's shoppers through the cold starts after each such deploy; the owner, who waits for a build before a new domain answers.
- **Saving:** Estimate: one production deployment fewer per domain change (each a full build that empties the caches and restarts every function cold), 4 to 8 routing rules fewer per store with a domain, and no ceiling near 270 such stores. No per-request gain: a remembered read replaces a rule match.
- **Risk:** This is every store's front door on its own domain: a mistake takes those stores off the air, where today a mistake is caught at build. A lookup must fail open to the answer the platform gives today for an unknown host, never to another store. The 60 s memory means a removed domain answers for up to a minute. The proxy would run on more requests (a store's files with an extension on own domains). It would be noticed by CI's hosts job and e2e/store-hosts.spec.ts; step 2 comes first because the ceiling may be nearer or further than estimated.
- **Already tracked:** no. docs/platform.md P8 records the design as decided (2026-09-26) and docs/cells.md:57 notes that a domain change needs a deploy; neither names the routes cap or the growth with stores.

## The fix

1. For the owner to decide: let a store's domain answer without a deployment, by looking the host up when the request arrives. This replaces decision P8's 'routed as configuration built into each deployment' for own domains; the generic {store}.{store domain} rules stay configuration. Steps 1 and 2 need no decision.
2. Now, small: make the number visible. src/server/usage.ts gains storeDomainRules(): the active rows of commerce.store_domains by store, passed through storeHostRoutes() (src/lib/store-hosts.ts) to count the rules. The platform's Usage and limits page (src/app/admin/(gated)/platform/capacity/page.tsx) shows the count beside what is left under 2,048, in the page's warning style from half of what is left. scripts/route-budget.mjs (SF-7 step 3) prints the app's own count from .next/routes-manifest.json so that figure stays true. docs/capacity.md gains the cap, the rule cost per store and the redeploy per change.
3. On a preview deployment, read the number of routes Vercel made for this app (the routes array of the build output's config.json) with 0 and with 3 store domains. That fixes how the 685 dynamic routes are counted, and so the real ceiling. Record it in docs/capacity.md.
4. If the owner decides for the lookup: (a) a new leaf src/server/host-store.ts (the database client and short-memory.ts of SF-2 only): storeOfOwnHost(host) reads one row of commerce.store_domains joined to commerce.stores by hostname where status = 'active' (the slug, whether it is the primary, its language and market, the store's primary host), remembered per host and instance for 60 s, a miss included, with the memory capped as src/server/holding.ts caps its own.
5. (b) src/proxy.ts: for a host that is not Kaizena Flow's own and not {slug}.{store domain}, ask storeOfOwnHost() before mayBeHeld(), and do in code what the per-store rules did: a store's other hosts and its {slug}.{domain} host go to its primary (307, as today's non-permanent redirects), /s/{slug}/… on the platform's host goes to the store's primary, and a served host's request is rewritten to /s/{slug}/… (the proxy already rewrites this way for D484, houseServedPath()). A lookup that fails leaves the request alone, as the proxy's other reads do.
6. (c) The matcher gains an entry for hosts that are not the platform's, so that a store's files with an extension on its own domain (robots.txt, the sitemap, favicon.ico, llms.txt, the feeds) pass too: source "/((?!_next/|api/|demo/|kaizen/).*)" with missing: a host condition that matches the platform's own hosts and the store domain's pattern. A matcher is static, and those hosts are known at build. Extend the matcher test in src/server/redirect-writers.test.ts.
7. (d) Links: getStore() (src/server/stores.ts) reads the store's active domains with the store and remembers them per process as it does the address shape (rememberStoreAddress(), src/lib/store-address.ts:194); storeOrigin(), languageHosts(), countryHosts() and storeOrigins() in src/lib/paths.ts read that memory instead of NEXT_PUBLIC_STORE_HOSTS; the email loader does as it does for the address.
8. (e) next.config.ts keeps the four generic rules; readStoreHosts(), src/lib/store-hosts-build.ts, the env entry (line 103) and the per-store parts of storeHostRoutes() go. (f) src/server/domains.ts: requestDeploy(), deployIfBehind() and routedAsSaved() (lines 68-101) go with their six callers' lines and the Domains page's waiting state; activating, removing or re-pointing a domain forgets the host in this instance and refreshes the store's tag (refreshTag(storeTag(slug))); other instances follow within the 60 s. platform_settings.domains_deploy_requested_at is dropped in a later migration (add, never drop in the same change).
9. (g) CI's hosts job (.github/workflows/ci.yml:170) and e2e/store-hosts.spec.ts seed a store on a domain of its own before the build; add a case that activates a second domain after the build and expects it to answer. docs/platform.md: P6 and P8 get a dated line saying what replaced them; docs/cells.md:53-57 is corrected.

**Done when:** In CI's hosts job a domain activated after the build serves its store's front page, and .next/routes-manifest.json holds the same number of redirects and rewrites whether the database has 0 or 300 active store domains.
