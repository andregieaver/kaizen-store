# PF-1 ✓ Next's route guessing and the cart drawer's catch-all slot make an endless prefetch on the local build and in CI: about 165 requests a second reach the server per open page

Prefetching: what the router asks for unasked (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P0. **Effort:** S. **Confidence:** high. **Step:** 0.11.
- **Second check:** corrected.
- **Where:** `src/app/s/[store]/[market]/@drawer/[...rest]/page.tsx:1-4`, `src/app/s/[store]/[market]/layout.tsx:104-105,214`, `node_modules/next/dist/client/components/segment-cache/optimistic-routes.js:174-182,222-232,578-594`, `node_modules/next/dist/client/components/segment-cache/cache.js:335-348`, `node_modules/next/dist/server/config-shared.js:212`, `node_modules/next/dist/server/config-schema.js:246`, `node_modules/next/dist/build/define-env.js:206`, `next.config.ts:79-88`, `playwright.config.ts:11-15,36`, `.github/workflows/ci.yml:116-157,170-191,215-251`, `src/lib/store-hosts.ts:89-104`, `e2e/a11y.ts:51`
- **Evidence:** Cause, as the skeptic proved and re-run here. Next 16.4.3 guesses a link's route tree from a route of the same shape it already learned (experimental.optimisticRouting, on by default at config-shared.js:212; cache.js:344 reads the flag that define-env.js:206 sets). The guess fills params from the address along the main branch only, so the rest param of the @drawer/[...rest] slot is never filled, and the code keeps the old value under its own comment "TODO: This should never happen. Bail out with null" (optimistic-routes.js:590-594). The slot's segment is written under one key and read under another, reads Empty, and is asked for again without end. Planner's runs: work/pf/probe.mjs on /s/demo/no/search?q=lampe at 1440x900, 4 s each: 624 router requests as built, 55 with guessing off, 47 with a two-line bail-out (the skeptic on a phone: 495, 23, 21). watch.mjs on /s/demo/no/category/hjem at 1440x900: 2,040 router requests in 5 s, 1,994 of them one address and segment. The skeptic's corrections stand: about 165 a second reach the server (the other half of the request events are answered by the browser's cache); 9 of 11 demo pages never go idle at CI's 1280x720; the trigger is any link whose route shape was learned before its prefetch starts. Behind a rewrite the address does not spell the route, no shape is learned and nothing loops; with the store domain set every /s/ address redirects to the store's host (store-hosts.ts:89-104), so production cannot loop today.
- **Cost today:** Per looping page (the skeptic's measures): 4.7 s of server CPU per 9 s (0.16 s when quiet), 2.8 s of browser main-thread time per 8 s (0.08 s when quiet), a heap that grows from 3 to 13 MB in 8 s. waitForLoadState('networkidle') never resolves on such a page (e2e/a11y.ts:51 swallows that; 13 spec files wait for it). In production nothing today. Paid by: CI's e2e job: 25 spec files open /s/demo addresses in 101 goto calls at 1280x720. CI's signed-in job runs without the store domain too, and 12 of its spec files open /s/ addresses (exposed where the store has a country in its address). Anyone running the production build at /s/ addresses. Shoppers would pay only if a later Next release learns shapes through rewrites while the TODO stands: a risk, not a cost.
- **Saving:** Measured: 624 to 55 router requests in 4 s on the search results page at 1440x900 (the skeptic: 495 to 23 on a phone); per the skeptic, server CPU for an open store page from 4.7 s to 0.16 s per 9 s. 101 goto calls in 25 e2e spec files run on a page that goes idle again. Removes a latent production failure before opening.
- **Risk:** Low. With guessing off a link of a known shape asks for its route tree again (0.4 to 1 KB each): 8 more requests on the search results page in my run (55 against 47 with the bail-out), as every link on production's store hosts already does. The flag is experimental and undocumented: if a later Next renames it the line is ignored silently, and the new e2e test fails on the loop, which is how it would be noticed. Not built in this session.
- **Already tracked:** no (not in the code review's Progress table, the PSI follow-ups, docs/performance.md or the rules)

## The fix

1. next.config.ts:79-88: add optimisticRouting: false to the experimental block, with a comment that says why (the @drawer/[...rest] slot and the TODO at next/dist/client/components/segment-cache/optimistic-routes.js:590-594) and when it may go. The NextConfig type (config-shared.d.ts:437) and config-schema.js:246 accept it; define-env.js:206 turns it into the flag cache.js:344 reads.
2. Create e2e/prefetch.spec.ts with one helper that records every request whose headers carry rsc: 1 and next-router-prefetch (its path and its next-router-segment-prefetch header). First test, 'a store page goes quiet': for /s/demo/no/search?q=lampe, /s/demo/no/category/hjem and /s/demo/no/cart at the project's 1280x720, load, wait 3 s, expect fewer than 60 such requests; wait 2 s more, expect no new one.
3. Add src/lib/next-config-prefetch.test.ts in the style of src/lib/chromium-trace.test.ts (it reads next.config.ts as text): expect the line optimisticRouting: false, with a comment naming the e2e test that says when it may be removed.
4. Build once as CI does and run the new spec (pnpm build, then pnpm exec playwright test e2e/prefetch.spec.ts): in this review the flag was switched off by rewriting the router chunk in flight, not by a build.
5. Record it: a new row in docs/decisions.md (the next number after D573), a clause in CLAUDE.md's Stack line beside the Next patch, a line in docs/performance.md. Report the bug upstream with the two-line bail-out (a guessed tree that leaves a param unresolved is not used).
6. At each Next upgrade read optimistic-routes.js for the TODO. When it is fixed, remove the flag and the unit test and keep the e2e test.
