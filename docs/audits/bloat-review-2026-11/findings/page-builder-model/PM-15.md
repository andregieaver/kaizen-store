# PM-15 One cache tag covers all of a store's pages: publishing one page, or describing one picture, makes every built page of the store render again

The page builder's model and a built page's render (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P1. **Effort:** M. **Confidence:** medium. **Step:** 2.14.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `src/server/pages.ts:69`, `src/server/pages.ts:690`, `src/server/site-layouts.ts:31`, `src/server/product-layouts.ts:30`, `src/server/experiments.ts:217`, `src/app/admin/(gated)/[store]/pages/actions.ts:60`, `src/app/admin/(gated)/[store]/pages/actions.ts:107`, `src/app/admin/(gated)/[store]/media/actions.ts:31`, `src/app/api/cron/cart-reminders/route.ts:262`, `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/updateTag.md:16`, `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cacheTag.md:171`, `.next/server/app/s/demo/no/om-oss.meta:1`, `docs/audits/code-review-2026-11.md:112`
- **Evidence:** Every cached read of a store's pages carries one tag, pages:{storeId} (pagesTag, pages.ts:69; 17 cacheTag places in 13 files, among them the header and footer at site-layouts.ts:31, the menus' names at pages.ts:722 and the product layout at product-layouts.ts:30). Because the layout draws the header, the footer and the menus, every route of the store uses a read with that tag. Measured on the build: all 261 prerendered entries of the demo store carry it in their x-next-cache-tags (read from the .meta files under .next/server/app/s/demo), the 30 product page entries included; only 45 carry the catalogue's tag. My rg finds 55 places in 31 files that refresh it: a publish (pages/actions.ts:107), an unpublish, a delete, a changed alt text in the media library (media/actions.ts:29-32, which refreshes the catalogue's tag too), a translation, a scheduled publish in the five-minute job (cart-reminders/route.ts:262), the AI manager's page tools. A draft save does not (actions.ts:107 asks `publish`). Next's guide: updateTag expires the cached data for the tag at once and the next request waits for fresh data (updateTag.md:16); a cached function may add a tag from the row it has read (cacheTag.md:171). The code review plans the same for products only (step 3.10, cache tags per product, Open).
- **Cost today:** Per publish: every built page of the store is stale and renders again on its next visit: its pages, articles, product and category pages, in each country, language and currency view (261 entries for the demo's 3 pages and 9 products). Each of those renders finds every tagged read cold: the page list, the names, the header, the footer, the modal check, the blogs, the grids. A store with 2,000 products that publishes an article a week renders its whole site again each week, and crawlers see to it that every stale page is asked for. Not timed here. Paid by: The server per render; the database (the cold reads); the first visitor to each page after a publish
- **Saving:** Estimate: a publish that changes only a page's body makes that page's own entries render again (one per market view) where today it makes every built page of the store do so: 261 entries on the demo, measured as carrying the tag.
- **Risk:** Medium. A fact shown on another page and missed by listFacts() would stay stale there until the hourly expiry (the reads have cacheLife('hours')), so the harm is bounded and the list in step 3 is the thing to review. Headers, footers and product layouts are safe, because every page that draws one carries its tag. Noticed by the e2e cases above.
- **Already tracked:** no (code review step 3.10, cache tags per product, FF3, Open, is the catalogue's twin and does not name pages)

## The fix

1. After PM-2, so that no page draws another page's content out of the whole list.
2. Beside pagesTag: export const pageTag = (id: string) => 'page:' + id. Reads that return one page's document add cacheTag(pageTag(id)) once the row is read, and keep pagesTag(owner): findPublishedPage() and publishedPageById() in src/server/pages.ts, siteLayoutFor() (site-layouts.ts:28), the product layout's read (product-layouts.ts:27, see PM-16) and siteVersionContent() (experiments.ts:214, for the version's and the original's id). A header's or footer's change then reaches every page through the header's own tag.
3. New pure module src/lib/page-list-facts.ts: listFacts(content) is what other pages show of a page: its title and the translations' titles, slug, thumbnail, excerpt, seo.description and, where both are empty, pageExcerpt(content), categories, tags, markets, blogId, authorId and author, searchEngines, aiAssistants, and whether it holds a modal that remembers (the rule at page-modals.ts:24, written as a function and tested against the same samples). Unit-test it.
4. src/server/pages.ts savePage(): on a publish, return scope 'site' when the page is new, was not live, changes its address, a global part spread to other pages (result.pages), or listFacts(before.livePublished) differs from listFacts(content); else 'page'. Unpublishing and deleting are 'site'.
5. The callers: the store's and the platform's save actions (pages/actions.ts:107, platform/pages/actions.ts:70) always refresh pageTag(id) on a publish and refresh pagesTag only for scope 'site'. The same in src/server/page-text-edit.ts:169 and page-css-edit.ts:155 (words and CSS changed on the site: 'page' unless listFacts changed), the AI manager's tools (owner-tools.ts:1040, site-tools.ts:425, :678, :987) and the schedule runner behind cart-reminders/route.ts:262, which returns each published page's id and scope.
6. Leave the media library's refresh (media/actions.ts:31) store-wide for now: finding the pages that hold a picture needs the index DQ-3 and DS-10 plan; note it there.
7. docs/rules/storefront.md, beside the catalogue's caching rule: the two tags, what refreshes each, and that a new reader of one page's document carries pageTag. Add a decision row; set the code review's Progress table forward if this is done with step 3.10.

**Done when:** A unit test of the store's save action with next/cache stubbed sees a body-only publish call updateTag with page:{id} and not with pages:{store} (today every publish calls it with pages:{store}), and the new cases in src/server/pages.int.test.ts pass (a body-only publish is scope 'page'; a changed title is 'site').

Where `next start` sends it, a new case can also read the x-nextjs-cache header of another page after a body-only publish and expect HIT (the header is described in Next's incremental-static-regeneration guide, line 584).
- Rules: CLAUDE.md, Storefront (catalogue reads are cached by tag; a writer refreshes the tag itself) and src/server/store-writers.scan.test.ts for stores; CA-10 plans a scan that every writer of pages refreshes the pages tag: the new pageTag must be an accepted answer there.
