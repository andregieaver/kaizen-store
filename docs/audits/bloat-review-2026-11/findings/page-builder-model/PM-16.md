# PM-16 A product's layout is cached once per product, whole

The page builder's model and a built page's render (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** duplicate. **Priority:** P2. **Effort:** S. **Confidence:** high. **Step:** 2.14.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `src/server/product-layouts.ts:27`, `src/server/product-layouts.ts:30`, `src/server/product-layouts.ts:59`, `src/app/s/[store]/[market]/p/[handle]/page.tsx:127`, `src/lib/signature/orbit.ts:452`, `src/lib/signature/orbit.ts:611`, `node_modules/next/dist/server/config-shared.js:102`
- **Evidence:** productLayoutFor(storeId, productId) is a `use cache` function, so its entry is keyed by the store and the product, and it returns the chosen layout's whole parsed content (product-layouts.ts:27-63). A store with one standard layout and K products therefore gets K entries holding the same document, K statements that each return it, K runs of the page schema and K picture lookups on a cold instance; and each product page's resume state keeps its own copy (in the build, demo-bordlampe.meta holds the entry: 15 bytes, null, because the demo store has no built layout). Each of the six signature themes ships a product layout (orbit.ts:452, :611). Measured here by bundling the themes (the review's working files (not kept), layouts2.mjs): 1,362 to 1,504 bytes as written, 13 blocks in 2 rows; Orbit's is 1,485 bytes as stored and takes 0.2 ms to parse. So a store started from a launch theme has one from its first day.
- **Cost today:** About 1.5 KB per product of the instance's 50 MB cache (config-shared.js:102) and of each built product page's resume state, for a theme's layout; an owner's own layout of 10 KB makes it 10 KB a product (estimate). 2,000 products: 3 to 20 MB of one instance's 50 MB for copies of one document, plus 0.2 ms of parsing and one picture lookup per product page on a cold instance. Paid by: The server per cold instance (cache memory, parsing); the database (the same document sent once per product); the build
- **Saving:** Estimate: one cached copy and one parse of a layout per store where there is one per product: 1.5 KB (a theme's layout) to about 10 KB (an owner's own) less per product in cache and in each built product page's resume state.
- **Risk:** Low: the choice of layout is the same statement; a cold product page makes two small reads where it made one. Noticed by the integration test.

## The fix

1. src/server/product-layouts.ts: split the read in two. productLayoutIdFor(storeId, productId): today's statement with `select p.id` only, same tags. productLayoutById(storeId, layoutId): 'use cache', cacheLife('hours'), cacheTag(pagesTag(storeId)) (and pageTag(layoutId) with PM-15): one row where id = the id, store_id = the store, type = 'product_layout' and published_at is not null; parsePageContent(); withPageAlts(). productLayoutFor() awaits the first, then the second, and keeps its signature, so productLayoutForVisitor() and the product page do not change.
2. src/server/product-layouts.int.test.ts: a case with two products on one standard layout that sees the layout's document read once (count the statements, or spy on the second function), and the cases it has today for a product's own layout, a category's and a tag's.

**Done when:** rg -n 'select p.id, p.published' src/server/product-layouts.ts prints nothing, and the new case in src/server/product-layouts.int.test.ts shows one read of the layout's document for two products.
