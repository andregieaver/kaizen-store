Scheduled and background work (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P0. **Effort:** M. **Confidence:** high. **Step:** 0.21.
- **Second check:** confirmed.
- **Where:** `src/server/knowledge.ts:153-160`, `src/server/knowledge.ts:167-192`, `src/server/knowledge.ts:233-258`, `src/server/knowledge.ts:297-312`, `src/server/embeddings.ts:31-49`, `src/server/embeddings.ts:110-122`, `src/server/media-library.ts:798-830`, `src/server/media-library.ts:860-876`, `src/server/alt-texts.ts:224-246`, `src/server/ai.ts:206-222`, `src/server/ai.ts:235-239`, `src/app/admin/(gated)/[store]/products/actions.ts:118`, `src/app/admin/(gated)/[store]/chat/actions.ts:26`
- **Evidence:** knowledge: for each site with a chat agent on, every run reads the site's locales (2 queries), every published page with its whole 'published' JSON, its blogs and its content entries, compares versions in JavaScript, runs a delete, resolves the AI and reads stale passages. A page that yields no passages gets no version (replacePassages deletes and inserts nothing), so it is cut again on every run: 91,200 'delete from knowledge_chunks where page_id' calls removed 782 rows in all. Nothing kicks it when a page is published: refreshSiteKnowledge() is called only when the agent's settings or a document are saved (chat/actions.ts:26, 44). embeddings: each run joins every active product translation of every store on Kaizena Flow's AI to its terms and hashes title, terms and description in SQL to find stale ones (10,201 calls, 148 s), though a product save already kicks the same work with after(). media: a loop over every store that has media: aiFor, a delete, a select each, and every item goes stale again after a day by design, which is the 13,414 updates on 468 rows. altTexts: its first query lists every site with a picture the AI may still describe, then per site resolves the AI and reads the site's languages and due pictures until five sites with work are found. Each aiFor() reads ai_providers (237,563 calls in the stats) and, for a store on the platform's key with a plan limit, sums the month's AI cost.
- **Cost today:** The dispatcher's four slowest database jobs after the status probes: alt-texts 604 ms, media 555, knowledge 542, embeddings 241. Database time is small today because there are 60 stores. It is the part of scheduled work that grows with stores times pages, products and pictures. Estimate: the embeddings statement takes 14.5 ms for today's few hundred translations; it cannot use an index for 'hash differs', so at a few hundred thousand translations it nears the 15 s statement limit and the job fails each run. Paid by: The database and the dispatcher every five minutes; it scales with every store that has a chat agent, media or products, used or not.
- **Saving:** Estimate: the four jobs fall from about 1.9 s of recorded time to a few statements per run; the 91,200 empty transactions and the daily re-touch of every picture stop; cost per store becomes cost per change.
- **Risk:** A grouped 'what is stale' statement that misses a case leaves a vector or the chat's knowledge out of date until the hourly pass: search by meaning and the chat agent are affected, so the pass stays. It would be noticed as a chat agent that does not know a page published in the last hour. The media change replaces a written reason (the daily re-check keeps uses current); the weekly check or the marker must cover it.
- **Already tracked:** no (docs/audits/psi-2026-10-24.md:146 judged these 'incremental'; the code and the stats show the knowledge loop and the media re-touch are not)

## The fix

1. Ship the four parts apart, smallest first. The aim for each job: an idle run is one statement over all stores, so the job can stay at five minutes and nothing gets slower.
2. knowledge, the empty page (smallest): keep what was cut per source even when it has no passages. Migration: commerce.knowledge_cuts (store_id, page_id, entry_id, published_at timestamptz, type_version text, path text, cut_at), with row-level security enabled and its lines in COPY_RULES (derived) and NOT_PERSONAL. replacePassages() (knowledge.ts:233-258) upserts the row in its transaction. syncPageKnowledge() (knowledge.ts:167-192) compares in SQL and reads the 'published' JSON only for the pages and entries to cut.
3. knowledge, the loop: refreshKnowledge() (knowledge.ts:297-312) starts with one grouped statement that returns only the agents' sites with a page or entry whose published_at (or type version) differs from its cut, a cut whose page is no longer published, or a passage whose space is null. Resolve siteLocales() and aiFor() only for those. A changed model (space differs) is found when the AI provider is saved (call refreshSiteKnowledge() there, as chat/actions.ts:26 does for the agent) and by one full pass an hour.
4. No kick on publish is needed: after step 2 the five-minute job costs one statement when nothing changed, so a published page reaches the chat as fast as today. (Ten server files write commerce.pages, so a kick at each would be easy to forget.)
5. embeddings: keep the kick on save (products/actions.ts:118, product-import.ts:629, bulk-edit.ts:456, translate/actions.ts:68). Give the dispatcher's platform-wide hash sweep an hourly cadence (CR-2): 24 passes a day instead of 288. For scale, add products.text_changed_at, moved by a trigger on product_translations and product_terms (no trigger moves products.updated_at today), and filter on it before hashing, so the sweep hashes only what changed. products is a hot table: add the column with a default in a plain migration, and build any index on it concurrently in a file that starts with -- kaizen:no-transaction (D569). CR-15 uses the same marker.
6. media: refreshMediaEmbeddings() (media-library.ts:860-876) starts with one grouped statement that returns only the owners with a stale item; run the 'not described' delete only for them. Replace the daily re-check (media-library.ts:810, 'so what uses an item is kept current') with a weekly one, or move the picture's media.updated_at when a page or product that uses it is saved. The reason stays met; the daily re-touch of every picture goes.
7. alt texts: the first query (alt-texts.ts:225-232) returns only sites with a picture that has no alt text and is due (alt_source is null), which is exact in SQL. The second case, a language added since, is queued when the store's languages are saved and found by one pass an hour that runs today's full list.
8. After steps 2, 5 and 6 aiFor() is resolved once per store with work, not once per store per run.

**Done when:** In pg_stat_statements the calls of 'delete from commerce.knowledge_chunks where page_id = $1' rise by no more than the pages published that day (about 1,170 a day on average now), n_tup_upd on media_embeddings rises by fewer than 100 a day at today's size, and the new knowledge.int.test.ts shows an idle refreshKnowledge() sends the same number of statements for 1 site and for 20.
