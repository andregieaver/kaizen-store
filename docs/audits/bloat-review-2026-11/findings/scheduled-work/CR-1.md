- **Evidence:** pg_cron posts to nine routes every minute: 12,960 calls a day. The ledger says they last took 0 to 72 ms; seven answer before working. Idle paths as read: autopilot 13 statements, broadcasts about 15, integrations about 14, theme-shots 8, cookie-scan 3, dream-factory 2, page-jobs, page-looks and pack-pictures 1 each, plus one ledger upsert per route and one for dream-factory.advance: about 68 a minute. Most queues are also kicked by the request that fills them (site-tools.ts:245, broadcasts/actions.ts:93, support-inbound.ts:148, triggerLook in page-looks.ts:126-139), so the minute poll is mostly a safety net. Six routes have a true queue (a row waits or it does not): page-jobs, page-looks, pack-pictures, dream-factory, theme-shots, cookie-scan. I read each claim statement and wrote its predicate into the fix. The other three (broadcasts, autopilot, integrations) carry several features with time-derived work. Built sizes re-measured in this session from .next: 11 of the 13 scheduled routes require 118 to 145 chunks at start (10.9 to 11.7 MiB of JavaScript); document-pdfs needs 30 chunks (1.5 MiB) and usage 48 (5.0 MiB).
- **Cost today:** 12,960 invocations a day of functions that are already warm, and about 97,900 idle statements a day. Each call opens fresh connections to the pooler, because idle ones close after 5 s (db/client.ts:14). In database time it is small: net.http_post totals 3,974 s in 78 days, 51 s a day on average and about 150 s a day at today's schedule (estimate). The function size (47 to 125 MiB traced) is paid at deploy and on a cold start, not per call. Estimate: the pool rule keeps an instance running about 5 s per call, about 18 instance-hours a day across the nine routes; what Vercel bills for that was not checked. The floor is flat: it does not grow with stores. Its largest measured consequence is the scheduler's log (CR-5). Paid by: The server per invocation (Vercel) and the Supabase pooler; the database a little.
- **Saving:** Estimate. Lasting, whatever the store count: the six queue routes fall from 8,640 calls a day to the sweep's 576 plus the minutes with real work, and about 33,000 idle statements a day go. pg_cron's own runs, and so its log rows (CR-5), fall from 13,250 to about 1,730 a day. The three feature routes stay at one call a minute (4,320 a day); their saving is CR-3.
- **Risk:** A predicate that forgets a kind of due work delays it to the 15-minute sweep; it is never lost. It would show as a queue that only moves at :00, :15, :30 and :45 (the ledger's last_started_at). A gated route is cold on its first call after a quiet spell: triggerLook(), where a person waits, then pays a cold start on the page-looks function (125 MiB traced, about 11 MiB of JavaScript at start; today the minute ping keeps it warm). Scheduling logic moves into SQL: D263 records that every scheduled call once failed for hours unnoticed, so the predicate needs its test and the tick its ledger row; a dead tick shows as 'late' on the platform home and fails the status page's 'jobs' probe.

## The fix

1. Write one custom migration (pnpm exec drizzle-kit generate --custom --name cron_tick, then node scripts/prune-snapshots.mjs). In it create commerce.cron_due(p_now timestamptz default now()) returns setof text, language sql, stable, search_path ''. It returns 'autopilot', 'broadcasts' and 'integrations' always (their own gate is CR-3). It returns each queue route when its predicate holds, or when extract(minute from p_now)::int % 15 = 0 (the sweep). The predicates, copied from the claim statements: page-jobs = a row of commerce.page_ai_jobs with status 'waiting' and (claimed_until is null or claimed_until < p_now) (site-tools.ts:463); page-looks = commerce.page_looks with status in ('queued','running') (page-looks.ts:241); pack-pictures = commerce.store_starters with pictures_wanted_by is not null (content-packs.ts:747); dream-factory = commerce.dream_runs with status in ('running','asking','ready') and finished_at is null (dream-factory.ts:465); theme-shots = commerce.theme_shots with status 'running', or 'waiting' with (claimed_until is null or claimed_until < p_now) (theme-shots.ts:176-180); cookie-scan = commerce.cookie_scans with status 'queued' (cookie-scans.ts:81).
2. Same migration: commerce.cron_claim_tick() returns setof text, plpgsql, volatile. It upserts the row 'tick' in commerce.cron_jobs (every_seconds 60, last_started_at, last_finished_at and last_ok_at = now(), runs + 1, failures 0) and returns commerce.cron_due(). The tick then has a ledger row, so a stopped scheduler reads as late (D263 is the reason).
3. Same migration, inside the same guard as baseline_4 lines 82-84 (pg_cron, pg_net and vault present): cron.schedule('kaizen-tick', '* * * * *', a statement that selects net.http_post(url := 'https://kaizenaflow.com/api/cron/' || r, the same headers and 30 s timeout as the baseline's call) from commerce.cron_claim_tick() as r). Then cron.unschedule(jobid) the nine every-minute jobs, each looked up in cron.job by its jobname (kaizen-autopilot, -broadcasts, -cookie-scan, -dream-factory, -integrations, -pack-pictures, -page-jobs, -page-looks, -theme-shots) and skipped if it is not there. Leave kaizen-cart-reminders, kaizen-subscription-reminders, kaizen-usage and the two retention jobs. The migration is applied before the deploy; the routes are the same in old and new code, so the rule 'keep the running code working' holds.
4. In the six queue routes (src/app/api/cron/{page-jobs,page-looks,pack-pictures,dream-factory,theme-shots,cookie-scan}/route.ts) change trackedRoute(..., 60, run) to 900, so cron-health allows 45 minutes between calls (allowanceSeconds(900) = 2,700 s). Keep 60 on autopilot, broadcasts and integrations.
5. Do REL-06's open item in the same change: in the seven routes that work inside after(), make the runner return how many units it took (runPageJobs, runPageLooks, runPackPictures, runThemeShots, runAutopilot with runGoalReviews and runEvents, runBroadcasts and its followers, advanceDreamRuns) and wrap the work in tracked('<route>.work', <same seconds>, ...) only when it took something. The ledger then shows real work and its real duration, and an idle call writes one row, not two.
6. src/server/status.ts:168-169: count a late 'tick' as a late dispatcher is counted (j.job === 'tick' || j.job.startsWith('dispatcher')).
