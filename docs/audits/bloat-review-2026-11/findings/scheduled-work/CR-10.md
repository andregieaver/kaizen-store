# CR-10 ✓ The docs search index is rewritten row by row on every docs change

Scheduled and background work (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** oversize. **Priority:** P2. **Effort:** S. **Confidence:** high. **Step:** 3.5.
- **Second check:** confirmed.
- **Where:** `src/server/docs-search.ts:76-81`, `src/server/docs-search.ts:94-127`, `src/server/docs-search.ts:174-186`, `supabase/migrations/20261111172841_baseline_3_rules.sql:8326-8354`
- **Evidence:** When the deployment's docs fingerprint differs, writeDocsIndex() upserts all rows with 'on conflict (key) do update' and no condition (docs-search.ts:109), then deletes rows whose updated_at is older than the transaction (line 120). Every row is rewritten even when one article changed; each rewrite recomputes two generated tsvector columns and a trigram text and touches three GIN indexes. The vector is kept when the text hash is the same. Stats: docs_index has 1,845 rows, 49,347 updates, and is the largest table in the schema at 33 MB.
- **Cost today:** About 1,845 row versions written per docs-changing deploy, with GIN upkeep. How much of the 33 MB is dead space was not measured. Paid by: The database on each deploy that changes content/docs or the contracts. It is deploy churn; it does not grow with stores or shoppers.
- **Saving:** Estimate: writes per docs deploy from 1,845 rows to the rows that changed. The table file shrinks only with a 'vacuum full'; a plain vacuum makes the space reusable.
- **Risk:** Low. The two edits must go together or the delete removes every unchanged row; the integration test would fail at once (the index would be nearly empty after a second write).

## The fix

1. src/server/docs-search.ts:109-117: add a where to the upsert: the stored text_hash is distinct from excluded.text_hash, or the row of the other written columns (doc, item, track, kind, lang, areas, features, plans, section, section_title, path, url, title, headings, code, summary, position, reading, checked) is distinct from the excluded row's.
2. In the same edit replace the delete by time (line 120) with a delete by key: delete from commerce.docs_index where key <> all(the keys just written, as one text[] parameter). Unchanged rows now keep their old updated_at, so the old delete would remove them all.

**Done when:** After a deploy that changes one docs article, n_tup_upd for commerce.docs_index in pg_stat_user_tables rises by fewer than 50 (1,845 before).

**Tests and rules that hold today's behaviour, and change with it:**

- src/server/docs-search.int.test.ts (a rewrite keeps a row's vector while its words are the same; rows no longer made are removed): add 'an unchanged row is not written again' (its xmin or updated_at stays) and 'a row whose only change is its section title is updated'.
- src/lib/docs-search-rules.test.ts stays. Rule: the docs portal's entry (D442, D443) in docs/rules/admin.

**Notes:** A fixed, platform-level cost. Worth doing because it is two lines, not because it is large.
