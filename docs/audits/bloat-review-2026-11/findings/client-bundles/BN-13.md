# BN-13 ✓ 40% of the built client JavaScript is second copies of modules; a browser meets about 14% of it while moving around

The built client bundles, by page (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** duplicate. **Priority:** P3. **Effort:** M. **Confidence:** medium. **Step:** tolerated.
- **Second check:** corrected.
- **Where:** `next.config.ts:79`, `src/lib/store-features.ts:14`, `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/turbopackChunking.md:103`, `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/turbopackChunking.md:137`, `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/turbopackChunking.md:151`
- **Evidence:** The skeptic split .next/static/chunks by Turbopack's module ids: 550 of 1,079 modules sit in more than one file and the extra copies are 7,222,830 bytes of 17.1 MB; the feature registry is in 90 files, blocks.en in 7. Seen again here in a small way: the loader of the recommended grid's view exists in eight copies with five different chunk lists. Next's doc says this is the chunker's trade (merging helps a first page load at the cost of moves between pages; lines 95 to 99) and documents experimental.turbopackChunking with generateComponentChunks, which lets the runtime skip what it already has, and clusters (lines 103 to 151); next.config.ts sets nothing under it (line 79). What a browser pays is smaller than 40%: within one route's own first-load list 7.5 KB is loaded twice, and a tour of all 59 top-level store admin screens downloads 3.70 MB of which 0.51 MB (14%) is second copies (the skeptic's measures, not re-run).
- **Cost today:** About 14% of what an owner downloads while moving around the admin, and 17 MB of static files per deploy of which 6.9 MB is repeats. Paid by: An owner's browser while moving between admin screens; the upload of each deploy. Not a shopper's first page.
- **Saving:** Not measured: the option is experimental and was not built here. The catalogues and tables the other findings remove are about 1.5 MB of the 6.89 MB (the skeptic's sum of the largest items).
- **Risk:** Medium. An experimental option on a build at its memory limit; expect no gain for a shopper's first page.
- **Already tracked:** No.

## The fix

1. Do the cuts above first: they take the largest repeated modules out of client code (catalogues, the cookie table, the registry's catalogue import), about 1.5 MB of the 6.89 MB.
2. Then, as an experiment on a branch that is never pushed to main: build once locally with experimental.turbopackChunking { generateComponentChunks: true } and once more with clusters for /admin and /s, each under the 8 GB cap.
3. Compare with the same scripts: copies (the module split), per-route bytes (scripts/bundle-budget.mjs), the 59-screen tour, the number of chunk files and the build's peak memory.
4. Write the result into docs/performance.md whichever way it goes, so it is not tried blind again.

**Done when:** docs/performance.md holds a table of the two builds: second copies (6.89 MB today), the 59-screen tour (3.70 MB, 14% repeats), first-load bytes of the 15 budgeted routes and the build's peak; the option is adopted only if the tour falls by at least 10% with no budget raised and the peak within about 150 MB.

**Tests and rules that hold today's behaviour, and change with it:**

- docs/build-memory.md: the build's margin is about 0.8 GB; an experimental chunker option is measured under the cap before it is considered.
- e2e/performance.spec.ts and e2e/signed-in/admin-scripts.spec.ts: first-load budgets must not rise with the option on.
- CLAUDE.md, Workflow: main deploys to production, so the experiment stays local.
