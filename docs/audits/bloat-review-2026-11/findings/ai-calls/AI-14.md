# AI-14 The agents' eval cannot tell whether the model finds a tool, so the default tool set cannot be lowered safely

What every AI call carries (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** no check. **Priority:** P1. **Effort:** S. **Confidence:** high. **Step:** 1.11.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `src/server/agent-eval.ts:78-81`, `src/server/agent-eval.ts:141-153`, `src/server/agent-eval.ts:188-192`, `src/lib/agent-eval.ts:25-57`, `src/lib/agent-eval.ts:149-340`, `docs/audits/code-review-2026-11.md:549`
- **Evidence:** Owner question 8 of the code review says a new eval run 'has to show it still finds the right tool'. The eval has 9 AI manager cases (rg counts them). Seven test that text planted in a tool's answer is not obeyed: they pass when no gated tool is called. Two require a tool: run_report, which is a core tool, and refund_order. For every case the harness loads the areas of all the tools the case scripts, forbids or requires before the first step (managerTools(), agent-eval.ts:146-153: 'so the tools a case tests are offered'). load_tools is handled if the model calls it (lines 188-192) but no case needs it, and rg finds the word nowhere in src/lib/agent-eval.ts. toolsVersion() hashes each tool's name, description and parameters (lines 78-81), not which tools a round sends, so a recording stays 'valid' when the default set changes. So today nothing would fail if a lean default left the model unable to find a tool, and nothing measures how well it finds one among 124 either.
- **Cost today:** No running cost. It is why the default sits at the provider's cap: the one change that would cut the AI manager's input by a third to two thirds (AI-1) has no check to pass. Every round of every turn pays for that until the check exists. Paid by: Every AI manager call, through AI-1 staying open; the team, who would otherwise learn of a missed tool from owners.
- **Saving:** None by itself. It unlocks AI-1 (a round down by 36% to 70%), AI-6 (15,384 characters a round) and AI-8, and keeps them from being undone unnoticed.
- **Risk:** A handful of scripted cases is a smoke test, not proof: a model can pass them and still miss a real request. Keep the round log of AI-10 (load_tools calls, 'no tool' answers) as the check in production. Each eval run costs real model calls, a few cents with today's 9 cases and a lean tool set.
- **Already tracked:** No. Owner question 8 of the code review assumes the eval can show this; step 3.18's 'done when' asks for 'a new eval run' without saying what it must contain.

## The fix

1. src/lib/agent-eval.ts: add `lean?: boolean` to AgentEvalCase and `loadsTools?: boolean` to its `expect` (the case passes only if load_tools was called before the required tool). Add six to eight manager cases marked lean, each a plain owner request whose tool is outside the core 12, with a scripted answer for that tool and `requiredTools`: a discount code (create_discount), a newsletter (a broadcast tool), free shipping over an amount (set_flat_shipping or save_shipping_method), a change to a page's text (get_page then edit_page), inviting staff (invite_staff), the plan and its price (billing_overview), a product's stock (set_stock), and one in Norwegian ('Lag en rabattkode på 10 %'). Add two that must not load anything: 'How many orders last week?' (run_report or list_orders) and a greeting. Check each tool name exists (src/lib/agent-eval.test.ts does).
2. src/server/agent-eval.ts, managerTools() (lines 146-153): for a lean case, do not preload: start from what a real turn on Home would send (core tools, the manager's own, load_tools, and the router's area once AI-1 is in), and add areas only as the model's load_tools calls ask (the loop at lines 188-192 already records them in `wanted`).
3. Same file, scoreAgentCase's caller: count a lean case as failed when the model answers that it cannot do the task without having called load_tools. Report, beside passed and total, how many lean cases needed a load_tools round: that number is the router's score.
4. toolsVersion() (lines 78-81): include what decides a round's tools (CORE_TOOLS, the load_tools definition for a fixed held-back set, TOOL_CHOICE_VERSION), so a recording made with one default set is refused for another.
5. Run the eval once on today's code with the new cases and keep the result as the 'before' (with 124 tools sent the lean cases should pass without load_tools; record how many do). Then AI-1 has something to be compared with.
6. Platform, AI: show the lean cases' result as its own line ('Finds its tools: 8 of 8, 3 with a load'). CLAUDE.md's Conventions paragraph on the eval: add that a change to which tools a round sends needs a new run, as a prompt change does.
