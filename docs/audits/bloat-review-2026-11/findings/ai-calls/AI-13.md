# AI-13 The alt-text job walks every site that has an AI-written alt text, every five minutes, and retries a failed picture every day with no end

What every AI call carries (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P1. **Effort:** S. **Confidence:** high. **Step:** 0.21.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `src/server/alt-texts.ts:224-241`, `src/server/alt-texts.ts:201-214`, `src/server/alt-texts.ts:104-107`, `src/server/alt-texts.ts:119-136`, `src/server/alt-texts.ts:146`, `src/app/api/cron/cart-reminders/route.ts:153`
- **Evidence:** refreshAltTexts() lists the sites to look at with '(m.alt_source is null or m.alt_source = 'ai') and (m.alt_tried_at is null or m.alt_tried_at < now() - interval '1 day')' (alt-texts.ts:225-232). A picture the AI described completely has alt_source 'ai' and alt_tried_at null (line 146 sets it to null on a complete answer), so it matches: once the job has done its work for a site, that site is on the list on every run for good. For each listed site, one after another, the loop fetches the AI connection (aiFor(), line 238), reads the site's languages (altSite()) and runs the exact due check (dueForAltText(), lines 201-214), and goes on until it has found five sites with work (line 236). When everything is up to date it walks them all, every five minutes. The verified report called this list 'already narrowed'; it is narrow only before the first alt text is written. Second, a picture whose alt text fails is marked tried (lines 104-107, 129, 136) and is due again after a day, each time fetching the picture and, for a provider error or an answer that could not be used, sending it to the vision model again (lines 119-136). There is no count of tries anywhere (rg finds only alt_tried_at). A text rejected because it made a claim the site does not allow can be rejected the same way every day.
- **Cost today:** Per run and per site with pictures: one AI connection read (with the limit and cost checks for a store on a plan with an AI limit), the due check on media, and the store read when it is not cached, in sequence, plus the list query itself. commerce.media shows 43,240 sequential scans in 78 days, about two a dispatcher run, which fits this list and the picture job each scanning it once a run; I cannot split them. Small today with a handful of sites. It grows with every store that has pictures: at 1,000 such stores, 2,000 or more round trips in sequence every five minutes to find nothing. The retries: one vision call a day on the store's allowance (or Kaizena Flow's bill for its own site) for every picture that cannot be described, for as long as the picture exists; capped only by the job's 4 pictures a site and 5 sites a run. Paid by: The database and the dispatcher's function every five minutes; the store's AI allowance for the daily retries.
- **Saving:** Estimate: on an idle run the job falls from three or more round trips per site with pictures to one query in all; the daily language pass keeps the per-site walk at once a day (288 times fewer). The retries stop after five days instead of never; how many pictures fail is not known before real catalogues arrive.
- **Risk:** A language added to a store waits up to a day for the alt texts of pictures the AI described earlier (minutes today): noticed in the media library's count of missing texts; the owner's own run fills them at once. A picture that fails five times for a passing reason (the provider was down for five days) stays without an alt text until someone asks: the count resets on any success and on the owner's run.
- **Already tracked:** No.

## The fix

1. src/server/alt-texts.ts, refreshAltTexts() (lines 224-232): list a site on the five-minute run only for a picture with no alt text that is due: `m.alt_source is null and (m.alt_tried_at is null or m.alt_tried_at < now() - interval '1 day')`. Drop `or m.alt_source = 'ai'` from this query.
2. The other reason a site is listed today, an AI-written text that lacks a language the site has added since (dueForAltText(), line 210), moves to a pass of its own, `refreshAltTextLanguages()`, with today's list query, run once a day: on DQ-5's job cadences, or until then a guard in src/app/api/cron/cart-reminders/route.ts:153 on the hour and minute. A language added to a store then gets its alt texts within a day; the owner's own *Write alt texts* run is unchanged and immediate.
3. Move the list query into an exported `sitesDueForAltText()` so a test can call it, and in the loop (lines 235-240) run dueForAltText() before aiFor(), so a site with nothing due costs no connection read.
4. Retries: src/db/schema.ts, the media table: `altTries` (smallint, not null, default 0); `pnpm db:generate` (media is not on the hot list; add-only). In writeAltText() the `tried()` update (line 104) adds one; the successful update (line 146) sets it to 0. dueForAltText() and the list query take a picture only while `alt_tries < 5`, unless the run is the owner's own with `rewrite` or a single picture asked for in the library (writeAltText() called directly), which try regardless and reset the count on success.
5. Media library: a picture that reached five tries shows 'Could not be described' with the last reason only if that is cheap to add; otherwise it simply shows as having no alt text, as today.
6. docs/rules/admin/website.md:683 (Alt texts, D89: 'a picture that could not be described waits a day') and the comment at src/server/alt-texts.ts:217-223: say five tries, then only on request, and that a new language is picked up daily.
