# The server code every route loads (SG)

Part of `docs/audits/bloat-review-2026-11.md`, on commit 0bd814c. Read by one reviewer, challenged by a second (who re-opened every citation, re-measured every number and applied the owner's note that the platform is not open yet) and planned by a third. A tick (✓) marks a finding the second reviewer confirmed or corrected; one the planner added has none. Each finding has a file of its own beside this one.

**In short.** One import cycle of 229 files in src/server makes 181 of 268 route handlers, 559 of 562 pages and the proxy each load about 10 MB of server code (the AI manager's tools, the admin's whole text in two languages, the schema, Stripe, sharp): a fat route takes 0.9 to 1.3 s and 97 MB of heap to load cold on this machine against 0.16 to 0.24 s and 26 MB for /api/health, and every instance first pays 0.27 to 0.30 s for a start hook and about 0.09 s to read a 10.4 MB list of server references. None of it depends on what a store uses, so it grows with stores, traffic and the deploy on every push once the platform opens. The cure is a few dozen small import changes, not removed features: one import path takes the visit beacon from 10.4 to 1.9 MB (0.96 MB with the schema and Stripe cuts), the rest take a storefront page from 11.3 to about 3.5 MB, the proxy from 9.2 to 2.4 MB (0.8 MB with its readers split) and 2.2 MB off 384 admin pages (all simulated on the build's own module graph). A scan test and a byte budget must land with them or the next convenient import undoes the work; before opening is the cheapest time, with no live traffic and every cut checkable on the next build.

## Well made, and should stay

- A lean route is possible today: /api/health loads 16 chunks and 1.1 MB, and 24 handlers reach under 500 modules (/admin/sw.js 93, /api/ucp/catalogue.json 103, /api/gravatar/[hash] 139). The fat graph is a tangle of imports, not a property of the stack.
- Turbopack runs a module's body only when it is first imported: a chunk's factories are registered on load and the route's own code is loaded on the first request. /api/visit's chunks hold 1,879 source modules; 1,332 factories run.
- A lazy server import is safe in a prerendered page: the server runtime loads an async chunk with a synchronous require and returns an already resolved promise (.next/server/chunks/[turbopack]_runtime.js:945-970), so import() adds no I/O task. What it does not do is shrink the function's package: code behind import() is still traced.
- Modules are instantiated once per process, so a second fat route in a warm instance costs almost nothing when it names the same chunk files (/api/shop/tiles after /api/visit: 1 ms). The exception is SG-11's copies.
- Heavy third-party parsers are already behind import(): unpdf, mammoth, playwright-core, @sparticuz/chromium (58 await import() in 30 server files). They cost package size, not cold-start time.
- sameSite() already lives in a leaf with no imports (src/lib/same-site.ts), OwnerToolError in its own leaf (src/server/owner-tool-error.ts), visitorKey in chat-turns.ts, and 66 src/lib modules already import their own area's admin catalogue directly: several of the moves are only import-path changes with a pattern in the repo.
- The taxonomy (12.7 MiB of JSON) is read from disk on first use and kept per instance (src/server/product-taxonomy.ts:27-43); catalog.ts reads it only for a product with a standard category.
- Chromium, the PDF files, the docs' Markdown and HarfBuzz are traced only into the routes that use them (next.config.ts:50-78); only the taxonomy uses '/**'.
- The database pool is made on first use (src/db/client.ts:94-97); importing the client opens nothing.
- Source maps are not traced into any function checked, and the edge runtime carries nothing heavy (.next/server/edge is 116 KB).
- The browser's copy of the admin catalogue is already split per area (D540, docs/performance.md:167-185); what is whole is the server's registry (SG-4).
- After the planned cuts no second hub hides behind the first on an admin page: removing any one file of src/server or src/app from /admin/[store]/orders takes off at most 238 modules and 0.64 MB. An admin page's floor of about 2,000 modules is what it uses (auth, orders, checkout), plus the text registry.
- The three-minute type check is not paid on Vercel (next.config.ts:45, D378) and CI runs it in its own job: it is no cost of the server graph.
- Test coupling to the present import paths is small for the P0 and P1 cuts: one mock of the chat module, one proxy test with five mocks, nothing for the cycle's edges, the key reader or the theme store section. Only SG-9 meets many tests (113 files).
- No finding in this dimension asks to retire, hide or merge a feature, and none argues from a feature being unused. Each is a running cost that every store pays whatever it uses, so the owner's clarification changes wording (SG-5), not substance.
