# SG-17 The page renderer imports the theme store's server code for every page of every store

The server code every route loads (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P1. **Effort:** S. **Confidence:** high. **Step:** 0.6.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `src/components/page-article.tsx:33-35`, `src/components/page-article.tsx:356-363`, `src/components/theme-store-section.tsx:7-12`, `src/components/theme-store-section.tsx:21-24`, `src/server/theme-store.ts:33-36`, `src/server/theme-shots.ts:34-39`, `src/server/theme-prices.ts:21-26`, `.next/server/chunks/[turbopack]_runtime.js:945-970`
- **Evidence:** page-article.tsx draws every page of every store and of Kaizena Flow's own site. It statically imports each block's server component, among them ThemeStoreSection (line 35), which draws only on Kaizena Flow's pages and its own store's: the component's first line returns null for any other owner (theme-store-section.tsx:24, D285 and D469). That component imports theme-store.ts (line 9), which imports theme-shots.ts (the job that makes theme photographs: media, theme-highlights and theme-shot-files, all three with sharp), design-presets.ts, store-starters.ts and theme-prices.ts (which imports billing.ts, connect.ts and stripe.ts, lines 21-26). page-article.tsx is the component's only importer (rg). On the build's graph, with the other cuts of this plan in: removing the one edge page-article.tsx -> theme-store-section.tsx takes 67 modules and 464 KB off the storefront home page (1,661 -> 1,594 module paths, 4,349 -> 3,885 KB) and the same 67 modules off 96 routes; storefront pages that still reach sharp fall from 58 to 2 (the two account privacy pages), other public pages from 42 to 10. It is the last path from a store's page to sharp. PlansSection (line 33, Kaizena Flow's plans, D142) is the same pattern at 8 modules and 41 KB; DomainSearchSection is 2 KB. A lazy server import is safe in a prerendered page: the server runtime loads an async chunk with a synchronous require and returns an already resolved promise (runtime.js:945-970), so no I/O task is added.
- **Cost today:** 67 modules and 464 KB of server code on every storefront page and on about 40 other public pages, and the only reason those pages load sharp (44 to 54 ms and 26 to 29 MB of RSS per cold instance until SG-7) and carry its 18.9 MiB in their package. Paid by: The server per cold instance of every store's pages; a store pays for a component only Kaizena Flow's own site can draw.
- **Saving:** Simulated on the build's graph after the other cuts: 67 modules and 464 KB off each storefront page and about 40 other public pages (96 routes); sharp no longer loaded at cold start by 56 of 58 storefront pages even before SG-7. The package keeps sharp until the later step.
- **Risk:** Low. The first theme store part drawn in an instance loads the chunk then. A prerendered page with a theme store part must still prerender: the runtime's loader is synchronous, and the build's route list and the two e2e specs show it. Alone, before SG-1, the cut shows nothing, because the cycle brings the same files another way.

## The fix

1. src/components/page-article.tsx: delete the static import at line 35 and add a small async wrapper beside the other helpers: async function ThemeStorePart(props: { block: ThemeStoreBlock; place: GridPlace }) { const { ThemeStoreSection } = await import('./theme-store-section'); return <ThemeStoreSection {...props} />; } with a comment giving the reason (the theme store's parts are Kaizena Flow's own, D285: loaded where one is drawn). Use it at line 363. Keep themePartDraws and themePartLeftOut (pure, src/lib/theme-store-parts.ts) as they are.
2. The same wrapper for PlansSection (line 33, used at 357) if the build shows its 41 KB leaves; leave DomainSearchSection.
3. Add to the guard of SG-14: src/app/s/[store]/[market]/layout.tsx and page.tsx may not reach src/server/theme-store.ts, src/server/theme-shots.ts or sharp by static value import.
4. Build. Check in the build's route list that Kaizena Flow's theme pages (/themes and /themes/[slug]) and its store's pages are prerendered as before, and run e2e/theme-store.spec.ts and e2e/theme-host.spec.ts.
5. Later, for the package only (with SG-8, inside code review step 3.13): split the theme library's readers from its photograph job so that no import, lazy or not, leads from a store's page to sharp. Four chains must go: theme-store.ts:35 (lookOf and themeShotsFor to a reader file), theme-store.ts:33-34 (DESIGNS_TAG and STARTERS_TAG from the tag leaf of SG-2, publishedContents to a reader file), and theme-page-parts.tsx -> demo-stores.ts -> design-presets.ts -> theme-shots.ts.

**Done when:** A new next analyze export shows /s/[store]/[market] with no src/server/theme-store.ts and no [externals]/sharp among its sync modules, and at or under about 1,600 modules and 4.2 MB of server code with SG-1, SG-4 and SG-6 also in (today 2,419 modules and 11,944 KB).
