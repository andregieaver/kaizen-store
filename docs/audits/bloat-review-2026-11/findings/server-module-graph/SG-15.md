I also looked for a second hub behind it and found none: with those cuts in, removing any single file of src/server or src/app from the page's graph takes off at most 238 modules and 0.64 MB (the store layout itself). - **Cost today:** About 2.2 MB and 400 modules on every admin page of a store, loaded whether or not the owner opens the assistant; the admin orders page takes about 0.9 s to load cold on this machine (measured by the skeptic). Paid by: An owner's admin: the server per cold instance of any admin page. It grows with the number of owners working at once after opening.
- **Saving:** Simulated: /admin/[store]/orders 2,425 -> 2,030 module paths, 11.0 -> 8.8 MB; with SG-6 8.2 MB; admin pages that reach the AI tools 384 -> 55 to 65; median admin page 2,443 -> about 2,000. An estimated 0.15 to 0.2 s of an admin page's cold load.

## The fix

1. src/app/admin/(gated)/[store]/assistant/actions.ts: turn the value import of @/server/owner-assistant (lines 8-17) into a type-only import (import type { Approval, Conversation }) and add an unexported loader: const assistant = () => import('@/server/owner-assistant'); In the five actions that call it (startAssistantAction, loadConversationAction, decideApprovalAction, deleteConversationAction, rateAnswerAction) take the functions first: const { assistantAbilities, listConversations } = await assistant(); Every export stays an async function, as 'use server' requires.
2. src/app/admin/(gated)/platform/assistant/actions.ts: the same change (the platform gets what stores get).
3. Keep the launcher on every page (D103): nothing a person sees changes.
4. Add both admin layouts to the guard of SG-14: they may not reach src/server/owner-assistant.ts, src/server/owner-tools.ts or src/lib/owner-tools.ts by static value import.
5. Run src/server/owner-assistant.int.test.ts and e2e/signed-in/ai-manager-panel.spec.ts; build and read the done-when.
