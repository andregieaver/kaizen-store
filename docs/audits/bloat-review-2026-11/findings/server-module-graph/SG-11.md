# SG-11 ✓ The build writes the same server chunks many times: 124 MiB of 196 MiB is repeats

The server code every route loads (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** duplicate. **Priority:** P2. **Effort:** S. **Confidence:** medium. **Step:** 4.5.
- **Second check:** confirmed.
- **Where:** `.next/server/chunks/_030vf3oprhjaf._.js`, `.next/server/chunks/src_lib_05q7dyrt2q-qx._.js`, `.next/server/chunks/ssr/_0_w2fqt8kybui._.js`, `next.config.ts:79-82`, `docs/build-memory.md:20-26`, `docs/build-memory.md:43-45`
- **Evidence:** Hashing every server chunk without its last line (the skeptic's script): 512 of 5,174 files repeat another's bytes; one 4.0 MiB blob exists 18 times, the 2.7 MiB admin catalogue chunk 10 times, a 3.9 MiB SSR chunk 5 times. Each copy has its own source map: 431 of 672 MiB. Routes name different copies: /api/visit and /api/cron/page-jobs share 105 chunk files by name but 113 by content, and loading both in one process the second spent 116 to 142 ms and 15 MB of heap on 7.4 MB it already had. du gives 1.4 GB for .next/server (re-run here). The build took 263 s: compile 36.5 s, the type check 3.0 min, 1,426 static pages after that (m/build.log lines 20-27); peak machine memory 7.6 GB against a 0.8 GB baseline (m/build-summary.txt). docs/build-memory.md says each page-data worker holds 1.3 to 1.9 GB.
- **Cost today:** About 550 MiB of the 1.4 GB under .next/server; build time and memory writing it; and at run time roughly 0.1 to 0.25 s and 15 to 19 MB of heap each time a warm instance first serves a route whose chunk list names other copies. Paid by: The build and CI; the server when one instance serves routes from different copy sets. How Vercel groups routes into functions was not checked, so the run-time share on Vercel is unknown.
- **Saving:** Estimate, not measured: 80 to 100 MiB of chunk JS and about 300 MiB of maps off the build output once the blob is cut. The build-memory gain is unknown until tried.
- **Risk:** Without server source maps, production stack traces name minified positions; hence only on Vercel and only if memory needs it. I found no Turbopack option that shares server chunks by content.
- **Already tracked:** Partly: code review FH10, step 1.8 'Give the build room', Open; docs/build-memory.md Watch. The duplicate chunks are new. In this review: tests-ci TC-8 step 5 and functions SF-11.

## The fix

1. Do nothing to the bundler first: the copies shrink with the blob. SG-1, SG-4 and SG-6 take most of the 4 MiB and 2.7 MiB chunks apart.
2. Add the duplicate count to scripts/route-budget.mjs (SG-14): md5 of every file under .next/server/chunks without its sourceMappingURL line; report files and bytes that repeat another's.
3. After those cuts, measure again and write the table into docs/build-memory.md.
4. Then one experiment, on Vercel's build only and measured under an 8 GB cap as docs/build-memory.md did: add serverSourceMaps: false to the ON_VERCEL spread at next.config.ts:79-82 (Next's memory-usage guide, line 126), then enablePrerenderSourceMaps: false. Keep a switch only if the capped peak falls by 0.3 GB or more; CI's builds keep their maps. This is step 5 of tests-ci TC-8: run it once.

**Done when:** The duplicate-chunk count in scripts/route-budget.mjs reports under 40 MiB of repeated bytes (today 123.6 MiB), and docs/build-memory.md holds the measured peak with and without server source maps.
