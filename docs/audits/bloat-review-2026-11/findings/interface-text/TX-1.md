# TX-1 ✓ Every server instance, and the proxy, evaluates all 134 admin catalogue files and all four storefront languages when it starts

Interface text (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P1. **Effort:** M. **Confidence:** high. **Step:** 0.7.
- **Second check:** corrected.
- **Where:** `src/lib/admin-text.ts:2-135`, `src/lib/admin-text.ts:232-310`, `src/lib/i18n.ts:9-17`, `src/lib/two-step.ts:13`, `src/lib/work-text.ts:4`, `src/server/store-action.ts:6`, `src/server/auth.ts:18`, `src/proxy.ts:10`, `src/server/holding.ts:9`, `src/lib/store-features.ts:14`, `src/lib/admin-map.ts:9`, `.next/server/chunks/[turbopack]_runtime.js:885-886`, `evidence/chunks.md:21`, `a scratch script`
- **Evidence:** admin-text.ts imports all 134 area files statically into one table; adminText(lang, area) reads one entry. In the build, 802 of 830 route entries and the proxy load a chunk with 100 or more of the 134 area-languages, and a heap probe finds 132 of them evaluated in /api/visit and in the proxy (verified report). My own count: 35 files outside the admin import the registry by value (32 in src/server, src/lib/two-step.ts, src/lib/work-text.ts, src/app/api/platform/editor/route.ts). Between them they read 18 areas, each by a literal name; 12 of the 35 read only staffEmails. The proxy reaches the registry through holding.ts, auth.ts and two-step.ts, which needs the signIn area. The static closure of src/proxy.ts is 1,311 source modules and holds 135 of the 136 catalogue files. If the 35 files read their own areas, the closure holds 37 catalogue files, 33% of the catalogues' source bytes: 16 files are the areas those files name, the others come through 37 lib and server modules that import an English catalogue directly, 21 of the 68 such modules only for a default argument.
- **Cost today:** Per cold start of a server instance and of the proxy: about 2.9 MB of catalogue code read and about 80 to 105 ms and 13 MB of heap to evaluate it (this machine, not Vercel), for words a storefront, API or cron request never shows. That is about a tenth of the measured cold start. The build writes the set out 12 times (35.6 MB). Each further admin language adds about 1.5 MB to every function. It will be felt more after opening: more stores mean more instances and more cold starts in front of shoppers. Paid by: The server at every cold start and in every instance's memory; a shopper whose request starts a new proxy or page instance; the build.
- **Saving:** Estimate, this machine. Steps 1-4 take about 99 of the 134 area-languages (two thirds of the bytes) out of the proxy and the storefront, API and cron code: about 55 to 75 ms and 9 MB per cold start, about 2 MB less code in each. With step 5 about 85%: 70 to 90 ms and 11 MB. That is 6 to 9% of a cold start. Step 6 gives admin functions the same and makes a new admin language free for everything that does not show it.
- **Risk:** Low for steps 1-4: a file that reads a word its reader lacks does not compile. What the compiler does not catch is an index module that pairs a language with the wrong file; the Norwegian email and sign-in tests show that. Step 5 changes signatures (words become required): callers that leaned on the English default fail to compile, which is how they are found. Step 6 touches about 690 files and should be its own push. The saving is from esbuild bundles on this machine, not from Vercel, and how Vercel groups route entries into functions was not measured.
- **Already tracked:** no (PSI PERF-01 and admin-catalogues.scan.test.ts cover the browser only)

## The fix

1. An index module per area that code outside the admin reads. For each of the 18 areas (staffEmails, screens, work, website, signIn, platform, customers, platformSite, invoices, customReports, assistant, sandbox, reports, order, oauth, experiments, common, books) add src/lib/admin-words/{stem}.ts, with the catalogue file's own stem (staff-emails, sign-in, custom-reports, platform-site). It imports the area's two files and exports the pair and a reader, for example: export const staffEmailsWords: Record<AdminLang, StaffEmailsMessages> = { en: staffEmailsEn, nb: staffEmailsNb }; export const staffEmailsText = (lang: AdminLang) => staffEmailsWords[lang]. Record<AdminLang, ...> keeps a missing language a compile error.
2. In src/lib/admin-text.ts, lines 232-300, the entry of each of those 18 areas becomes the imported pair (staffEmails: staffEmailsWords) and the area's two direct imports at the top go. A language is then still added in one place per area. Types stay as they are (the type imports of each .en file remain).
3. Change the 35 files to call their area's reader and drop the import of lib/admin-text: src/lib/two-step.ts (signIn, lines 59 and 92), src/lib/work-text.ts (work, screens), src/app/api/platform/editor/route.ts (website), and in src/server: store-action.ts (common), two-step.ts (signIn), assistant-route.ts (assistant), analytics-say.ts (screens), control-center.ts (books), developer-apps.ts (oauth), sandbox-ai.ts (sandbox), platform-briefing.ts (platform), platform-site-words.ts (platformSite), page-duplicate.ts (website), work-words.ts (work), customer-tiers.ts, company-locations.ts and price-lists.ts (customers), report-labels.ts (reports, customReports), report-schedules.ts (customReports), einvoices.ts and einvoice-sending.ts (invoices, screens), experiment-emails.ts (experiments, staffEmails), staff-alerts.ts (order, staffEmails), and the 12 that read only staffEmails: autopilot-reports.ts, cron-alerts.ts, endpoint-emails.ts, follow-up-runner.ts, kaizen-life-emails.ts, plan-reminders.ts, push.ts, security-emails.ts, shopper-emails.ts, stock-alerts.ts, store-closure.ts, support-email.ts.
