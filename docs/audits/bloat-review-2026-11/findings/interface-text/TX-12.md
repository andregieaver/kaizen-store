# TX-12 Every instance start reads every AI-translated language whole, one after another, and builds it before the first request

Interface text (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P2. **Effort:** S. **Confidence:** medium. **Step:** 0.8.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `src/server/ui-text.ts:47-54`, `src/server/ui-text.ts:57-72`, `src/server/ui-text.ts:106-108`, `src/instrumentation.ts:6-10`, `src/lib/ui-registry.ts:21-28`, `src/lib/ui-catalog.ts`, `src/lib/i18n.ts:23-25`, `src/server/ui-nightly.ts:53-63`, `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/instrumentation.md:18`, `docs/audits/bloat-review-2026-11/scripts/sources/tx-plan/overlay-time.mjs.txt`, `docs/audits/bloat-review-2026-11/scripts/sources/tx-plan/overlay-heap.mjs.txt`
- **Evidence:** refresh() loops over the languages in the table and awaits loadLanguage() for each in turn (ui-text.ts:63-70). loadLanguage() reads every key of the language, interface and email (line 48), and at once builds two full message objects with overlayMessages() and a third copy for the browser (lines 52-53). startUi() awaits all of it (line 108) and Next holds requests until register() returns. So with L translated languages every new instance runs L + 1 statements one after another and builds L languages, whatever it will serve: a health check, a cron run, a store that sells only in Norwegian. Measured with the real overlayMessages() on a stand-in language of English length: 1,863 rows (1,673 interface, 190 email), 134,820 bytes as JSON; 13 ms for the first language and 5.6 ms on average; 443 KB of heap kept per language, of which the rows alone are 229 KB. The languages are the platform's (commerce.platform_languages), not a store's, so L is the number of languages anyone has had translated.
- **Cost today:** Nothing today: no language is translated before opening. Per translated language afterwards, at every cold start of every instance: one more round trip to the database before the first request (its time was not measured), about 135 KB of rows, 6 to 13 ms of CPU and 0.44 MB of heap. With 20 languages (the EU's other official languages) that is 21 statements in a row, about 2.7 MB of rows, 0.1 to 0.26 s of CPU and about 9 MB of heap per cold start (estimate: the one-language measurement times 20). The cost follows the platform's number of languages, not what the instance serves. Paid by: The server at every cold start; a shopper whose request starts an instance; the database.
- **Saving:** Per translated language that an instance does not serve: one round trip fewer before the first request, about 4 to 11 ms of CPU and about 0.2 MB of heap (measured here: 5.6 to 13 ms and 443 KB today against 1.5 ms and 229 KB when only the rows are kept). At 20 languages: 19 round trips, roughly 0.1 to 0.2 s and 4 MB per cold start (estimate by multiplication). Nothing today.
- **Risk:** Low. The first page in a language pays its 6 to 13 ms of building once per instance, during the render, as pure CPU. A maker that throws would throw inside t(): build inside try and fall back to English, as a failed read does today. The grouped read returns all changed languages in one answer (about 135 KB each); at start that is every language, which is the same data as today in one statement.

## The fix

1. One statement for the languages that changed. In refresh() (ui-text.ts:57-72) collect the languages whose version differs, then read them together: select lang, key, text from commerce.ui_translations where lang = any(...) (textList() from src/server/sql-arrays.ts), and group the rows by language in code. Two statements at start instead of L + 1.
2. Build a language when it is first read. src/lib/ui-registry.ts: an entry may hold makers beside values (makeUi and makeEmail, each a function); registeredUi(lang) and registeredEmail(lang) call the maker on first read, keep the result and drop the maker. loadLanguage() registers makers that close over the two maps and call overlayMessages("ui", t("en"), ui, lang) and overlayMessages("email", emailText("en"), email, lang). t() stays synchronous and never waits on the database: the rows are already in memory. The browser's UiTexts keeps registering values as today.
3. Keep for the browser only what TX-3 hands (the 114 browser keys and the withdrawal page's 144), not a third copy of every text (line 53).
4. forgetMessages() and reloadUi() work as before: a reload registers fresh makers. Update the module comment (ui-text.ts:19-27).
5. Not now, and only if cold starts show it once there are many languages: load a language's rows on first need instead of at start, awaited where a store is read (getStore() in src/server/stores.ts:199 already notes per-store facts on each call) and before emails (ensureUi()). 124 files call t() with a language taken from data, so one missed path would show English and a cached page could keep it; that risk is why this step waits.

**Done when:** The new unit test passes: with three translated languages startUi() issues 2 statements (4 as written today) and overlayMessages() is not called until t() is first read for a language.
