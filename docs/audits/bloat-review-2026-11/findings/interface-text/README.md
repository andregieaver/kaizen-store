# Interface text (TX)

Part of `docs/audits/bloat-review-2026-11.md`, on commit 0bd814c. Read by one reviewer, challenged by a second (who re-opened every citation, re-measured every number and applied the owner's note that the platform is not open yet) and planned by a third. A tick (✓) marks a finding the second reviewer confirmed or corrected; one the planner added has none. Each finding has a file of its own beside this one.

**In short.** The words themselves are in good order: 2,003 storefront keys in four languages and 29,040 admin texts in two, none missing, and only 34 keys nothing reads (0.1%). The bloat is in how they are loaded. 802 of 830 server entries and the proxy evaluate all 134 admin catalogue files and all four storefront languages at each cold start (about 80 to 105 ms and 13 MB here, a tenth of the start); admin pages hand whole areas to the browser (the product editor hands 204 KB where its parts name at most 65 KB); and 97 of 111 visitor routes load about 25 KB of cookie purposes and admin words no shopper reads. The empty commerce.ui_translations table is what one expects before opening and is no finding; its loader is: it asks every minute per instance today, and as written every cold start will read each translated language whole, one after another (about 135 KB, 6 to 13 ms and 0.4 MB a language). Four fixes are small and safe now (TX-4, TX-5, TX-8, TX-11), and the two structural ones (TX-1, TX-2) are cheapest before opening and before a third admin language adds about 1.5 MB to every function.

## Refuted by the second reviewer

These were in the first reading and did not hold. They are in no step.

- **Typing the admin's catalogues is why the type check needs a 5 GB heap (the brief's premise and the comment in .github/workflows/ci.yml:35).** Measured alone the catalogues and the registry take about 125 MB and under a second. The tests-and-CI dimension found no single type to blame (TC-4). No retyping is proposed; only the comment is corrected (TX-9).
- **42 dead keys, 8 of them in marketing.problems and payments.problems.** Those 8 are live: the server builds their English sentences from parts (src/lib/broadcasts.ts:40-45, src/server/settings.ts:70, src/server/automations.ts:119) and the tables match them. Deleting them would turn Norwegian refusals into English. 34 are dead.
- **Move the whole cookie table to the server.** The browser reads it when consent is withdrawn (src/components/consent/consent-manager.tsx:230). The fix is a split: patterns and categories stay, purposes go (TX-5).
- **Pass three message groups as props and the page builder loads no storefront language.** The grid preview reads functions from the store's language (page-builder-fields.tsx:1537, content-grid.tsx:63), which cannot cross as props. The builder needs one language module loaded on demand (TX-7).

## Well made, and should stay

- The languages are complete and held by the compiler. Re-checked here key by key: nb, sv and da each have all 2,003 storefront keys and all 316 email keys, none missing, none extra; the admin's Norwegian has every one of the 29,040 English keys.
- A shopper's document carries only what it shows: 7 to 32 catalogue texts in one language on the 12 measured pages (verified report). Storefront client components are typed with small label groups of BrowserMessages, not with Messages (my rg of the 'use client' files under src/app/s and src/components).
- Choosing a language does not make pages dynamic. The language is in the address (resolveShop, src/server/shop.ts:42-49). Only the front door is decided per visitor, by a 307 in the proxy with Vary and no-store (src/proxy.ts:110-116). The admin reads the account's choice.
- The catalogues' typing is the cheap kind: plain object literals, one Widen<typeof en> per area, each Norwegian file annotated with it. Measured alone it is about 125 MB and under a second. Retyping the catalogues would not move the 5 GB heap, so no cheaper typing is proposed; a missing key stays a compile error as it is.
- Dead text is about 0.1% of keys and no catalogue is an orphan: every one of the 67 areas is in the registry and has readers.
- Repeated labels (Save, Name, Cancel) are 24% of the admin's keys but 7% of its characters, and they let one area be handed to a page alone. Leave them.
- The admin's English fallback is fetched per area only when needed (D540, src/components/admin/admin-text-later.ts) and a signed-in test fails on any screen that needs it. Only common and sign-in English are compiled into the admin's first scripts.
- The AI-translated interface (commerce.ui_translations, D111) costs no AI call at night for a language nobody asked for (src/server/ui-nightly.ts:53-63). Its table being empty is expected before opening and is no reason to change the feature. Nothing else in src reads the table on a request path (rg ui_translations: the loader, the platform admin's tools and the nightly job).
- The glossary (src/lib/i18n-glossary.ts, 852 lines) is imported by tests only (rg: no non-test importer). It costs nothing at run time.
- Kaizena Flow's own chrome words (messages/platform-en.ts and platform-nb.ts, 32 and 33 KB) reach no visitor client code: client parts take typed slices such as PlatformMessages["docs"]["guide"] as props (my client import graph).
- The four small browser-text files loading together with a page's first scripts is a written, tested decision (D212, docs/performance.md:52-60: loading one language on its own once lost a press). It costs a shopper about 4.6 KB gzip. Leave it until a fifth hand-written language is added.
- Norwegian-only files nav.nb.ts (42.8 KB) and pages.nb.ts (61.2 KB) are a second way of translating (by English sentence and by page id), held by admin-nav-words.test.ts. They are server-side cost only and are counted in TX-1; not worth a change of their own.
