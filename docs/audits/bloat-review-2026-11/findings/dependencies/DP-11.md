A server component that imports a 'use server' file imports the module itself, so every admin screen under either layout evaluates all of it. Walked: the root, gated and store layouts plus the orders page reach 1,396 source files and 5,498 zod calls. With the storefront review's first cut alone (customers.ts:17 no longer imports privacy-erasure.ts) the count stays 1,396, because this door is still open. With these two imports made lazy alone it stays 1,396, because the other door is open. With both: 986 files and 3,034 zod calls, and no path to owner-tools.ts, owner-assistant.ts or opentype.js. The platform layout: 1,365 files, 925 with both. Measured: the tool catalogue and the 177 source files it imports, bundled and loaded in a fresh process, take 109-123 ms, 19.7 MB heap and 52 MB RSS (zod alone 18-19 ms, 2.2 MB, 9 MB). The built admin routes list src/lib/owner-tools.ts (156 KB) among their largest server modules (m/chunks.md).
- **Cost today:** About 90-105 ms and 17 MB of heap per cold start of an admin function for the tool schemas alone (this sandbox), plus the tools' own server code, which was not timed. - **Saving:** Estimate from the bundles: about 90-105 ms and 17 MB heap less per admin function cold start for the tool schemas, and 410 fewer source files (1,396 to 986) with their own compile and memory. Not measured on a built admin route.
- **Risk:** Low. The first press on the AI manager in an instance loads its code then (about 0.1 s) instead of every screen loading it. A slip in an action shows at once in the signed-in e2e run. The files that stay on the hub through other chains are not harmed.
- **Already tracked:** no. SD-1 of the storefront review names the customers.ts chain and the proxy; it does not name this door, and its measured saving (the store layout from 1,466 to 1,011 files) does not carry to any admin layout without it.

## The fix

1. src/app/admin/(gated)/[store]/assistant/actions.ts: turn the value import of @/server/owner-assistant (lines 8-17) into a type-only import (import type { Approval, Conversation } ...) and add an unexported loader: const assistant = () => import('@/server/owner-assistant'); In the five actions that call it (startAssistantAction, loadConversationAction, decideApprovalAction, deleteConversationAction, rateAnswerAction) take the function first: const { listConversations, assistantAbilities } = await assistant(); and so on. Every export of the file stays an async function, as 'use server' requires.
2. src/app/admin/(gated)/platform/assistant/actions.ts: the same change (the platform gets what stores get).
3. src/server/follow-ups.ts:14: import OwnerToolError from './owner-tool-error', where it is defined and where 54 other files already take it. One line; it removes a second, pointless edge into owner-tools.ts.
4. Do the storefront review's first cut (SD-1 step 1: src/server/customers.ts stops importing eraseSubject at the top). Either order; neither pays for the admin without the other.
5. Add to the graph test of DP-6 (src/server/route-load.graph.test.ts): src/app/admin/(gated)/[store]/layout.tsx and platform/layout.tsx may not reach src/server/owner-assistant.ts, src/server/owner-tools.ts or src/lib/owner-tools.ts by static value import. Until SD-1's cut lands, assert only that the two actions files do not import owner-assistant as a value.
6. Run the AI manager's suites and open its panel signed in; then build and check that an admin route's chunks no longer hold lib/owner-tools.ts.
