# PL-6 ✓ A listing sends its product grid twice, and a category asks the database again for the list it already drew

What a page sends: document, payload and requests (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** duplicate. **Priority:** P2. **Effort:** M. **Confidence:** high. **Step:** 2.12.
- **Second check:** confirmed.
- **Where:** `src/components/content-grid-section.tsx:42`, `src/components/content-grid-section.tsx:86`, `src/components/content-grid-section.tsx:97`, `src/app/s/[store]/[market]/term-listing.tsx:185`, `src/app/s/[store]/[market]/term-listing.tsx:190`, `src/app/s/[store]/[market]/products/page.tsx:103`, `src/components/product-listing.tsx:78`, `src/components/product-listing.tsx:135`, `src/server/listing.ts:220`, `src/server/listing.ts:74`, `docs/rules/storefront.md:355`
- **Evidence:** A filterable product grid is a Suspense whose fallback is the whole grid as built and whose content is the same grid drawn again per request with the controls; with no filter chosen the items are literally the same (content-grid-section.tsx:42-44, 97). Recounted in the saved /products document: every data-item-id is there 18 times in the markup and 18 in the payload for 9 products; the verified report found the two grids byte-identical (7,559 bytes each) and the stand-in's payload copy 15.3 KB. The standard category, tag and products pages do the same with ProductGrid (term-listing.tsx:185-198, products/page.tsx:97-104), and there is more: ProductListingFor is given no products there (term-listing.tsx:190, products/page.tsx:103), so ProductListing takes the branch that calls listingPage() even with no filter (product-listing.tsx:78-83). listingPage() is not cached (listing.ts:220-268: an id query with a window count, then a cached read keyed by those ids). The built grid already skips that read when nothing is chosen (content-grid-section.tsx:86). The written rule (docs/rules/storefront.md:355) says listing pages keep their unfiltered grid prerendered as the Suspense fallback: that is why the stand-in exists. The waste is drawing it, and on standard pages reading it, a second time when nothing was asked for.
- **Cost today:** 24.7 KB raw (14.5%) of the demo's listing with 9 products, about 2.7 KB raw per product; a full page of 48 would be about 130 KB (estimate). Small on the wire (about 2 thousand bytes gzipped: the copies compress). The server renders the grid a second time per request, and on standard category, tag and products pages runs one uncached list query per unfiltered view. The browser builds the first grid, then swaps in an identical one. Paid by: The server and the database per listing view (the second render; on standard pages the second read); a shopper's browser on every category, tag and products page.
- **Saving:** Measured: 24.7 KB raw (14.5%) of the demo's listing; about 2.7 KB raw per product shown; about 2 thousand bytes gzipped. One grid render per unfiltered view instead of two. By code: one uncached list query less per unfiltered view of a standard category, tag or products page (step 1 alone). Filtered views stay as they are.
- **Risk:** Medium for steps 2 to 4: a filtered view shows the unfiltered grid until its own arrives, as today, but now by a style rule, so a missed marker would show two grids (e2e/listing.spec.ts counts cards). The hidden built grid stays mounted on filtered views, so its hearts and tile parts wake unseen there. Low for step 1: the given list and the read list are the same query in the same order; a store selling to both kinds of buyer keeps the read.

## The fix

1. The quick part (S), standard pages only: src/components/product-listing.tsx: add a prop firstPage (boolean). When products are given with firstPage, no filter is chosen, the sort is featured, page is 1 and the store does not sell to both kinds of buyer (store.audience is not 'both': the list's scope then does not depend on the viewer, listing.ts:74), skip listingPage() and use the given products with total = Math.max(facets.total, given.length), as the built grid does (content-grid-section.tsx:99). Pass products={products} firstPage from src/app/s/[store]/[market]/term-listing.tsx:190 and src/app/s/[store]/[market]/products/page.tsx:103. Search keeps its own meaning of given products.
2. The built grid: src/components/content-grid-section.tsx:40-46. Draw the grid as built outside the boundary. Inside one wrapper (class listing, a column with the same gap) in this order: a Suspense with no fallback that streams the controls; the grid as built in a div marked data-grid-built; a second Suspense with no fallback that streams, only when the address asks for something else (a filter, a sort, a page above 1, or a store that sells to both kinds of buyer), the chosen grid in a div marked data-grid-chosen, and after it Show more. Both boundaries get their facts (filters, facets, the listed products, the terms) from one function run through perRequest (src/server/request-memo.ts) keyed by the block and the listing's path, so nothing is read twice.
3. src/app/globals.css: one rule: inside .listing, when a [data-grid-chosen] child is present, the [data-grid-built] child is not displayed. The built grid then shows until the chosen one arrives, exactly as the fallback does today.
4. The standard pages the same way: term-listing.tsx:185-198 and products/page.tsx:97-104 draw ProductGrid as built outside the boundary; split ProductListing (product-listing.tsx:38-132) into the controls with TrackOnView (first boundary) and the chosen grid with Show more (second boundary). The search page keeps its single boundary: its results depend on the query.
5. Tests: e2e/listing.spec.ts must pass unchanged (filtering, sorting, taking a filter away, a category and search). Add to it: an unfiltered /s/demo/no/products holds each product once (count of li[data-item-id] equals the number of products), and with scripts off the grid shows. e2e/wishlist.spec.ts:7 says the streamed list's hearts are the ones to use: with one grid, correct the comment and the locator.
6. Reword the rule in docs/rules/storefront.md:355: 'Listing pages draw their unfiltered grid once, prerendered; the controls, and a grid only when the address asks for another, stream in per request.' A decision line beside D78.
