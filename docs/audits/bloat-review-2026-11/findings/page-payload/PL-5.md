# PL-5 ✓ Prefetching runs per link because partialPrefetching is unset: 11 to 50 requests after a storefront load, 23 to 46 in the admin

What a page sends: document, payload and requests (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P1. **Effort:** M. **Confidence:** medium. **Step:** 2.8.
- **Second check:** corrected.
- **Where:** `next.config.ts:42`, `docs/plan.md:120`, `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/partialPrefetching.md:44`, `node_modules/next/dist/docs/01-app/02-guides/adopting-partial-prefetching.md:72`, `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/02-route-segment-config/prefetch.md:44`, `src/proxy.ts:54`, `src/components/product-card.tsx:73`, `src/components/content-grid.tsx:147`, `src/components/content-grid.tsx:310`, `src/components/store-layout.tsx:443`, `src/components/store-layout.tsx:498`, `src/components/store-layout.tsx:511`, `src/components/admin/store-admin-nav.tsx:94`, `evidence/start.log`
- **Evidence:** The build and the server both warn that cacheComponents is on without a partialPrefetching value (evidence/build.log:6, start.log). Next's docs: unset behaves like false, 'a page with N links to N routes produced ~N route prefetches'; with true there is one reusable App Shell per route. docs/plan.md:120 names partialPrefetching as part of the chosen stack; next.config.ts does not set it. Recounted from routes.json (docs/audits/bloat-review-2026-11/scripts/sources/plpl/after.mjs.txt and a per-page tally): a visitor who does nothing causes 11 to 50 prefetch requests per storefront page and 23 to 46 per admin screen; in the store admin 18 to 40 of them carry no shared-cache header (26 of 32 on Orders), so no shared cache may keep them; whether production answers those from prerendered segments or with a render was not measured. The local server adds 1,718 bytes of headers to each answer, so bodies are about 14 to 112 KB per storefront page and 37 to 81 KB per admin screen. Product tiles in content grids are plain anchors (content-grid.tsx:147, 310): never prefetched, and a press is a document load. Measured in a headless browser (docs/audits/bloat-review-2026-11/scripts/sources/plpl/nav.mjs.txt): a press on a home page tile loaded a 131,228-byte document (19,694 gzipped), read the stylesheet and 24 scripts again (811 KB, from the cache), repeated the wishlist call and made 12 new prefetches; a press on the bottom bar's next/link made one navigation request, fetched 7 new scripts and 13 prefetches. Next also offers a per-segment switch, export const prefetch = 'partial' or 'force-disabled' on a page or layout (route-segment-config/prefetch.md), so the change can be tried one route at a time.
- **Cost today:** 11 to 50 requests per storefront document load, each through the proxy, and 23 to 46 per admin load, most of which no shared cache may keep. The request count is the cost, and it grows one for one with page views. On the main path of a store built with content grids, every press on a product tile is a whole document load. Paid by: The server per request (proxy.ts on every storefront prefetch; an uncached answer per admin prefetch); a shopper's and an owner's browser and data.
- **Saving:** Sure and measured: step 2 saves 4 requests and about 12 KB per view of any store page whose footer is in view. Not known before the trial: one shell per route instead of two or three requests per link is the ceiling. If tiles become links: a press costs one navigation request instead of a 131 KB document, 24 scripts and a stylesheet read again, the wishlist call and 12 prefetches (measured for one press each way; the two destinations differ, so read it as the shape, not a like-for-like figure).
- **Risk:** Medium. With shells, a pressed link shows the shell first and its page after a fetch, which shoppers will feel on links that were instant. Tiles as links change the main path from document loads to client navigations: back and forward, scroll position and the Safari patch need their e2e runs. Next's next major turns the flag on for everyone, so the trial is due either way and is cheapest before opening.
- **Already tracked:** Partly: docs/plan.md:120 lists partialPrefetching in the chosen stack; no step or rule tracks that it is not set, and the build's warning fails nothing.

## The fix

1. next.config.ts:42: beside cacheComponents, write partialPrefetching: false. It records today's behaviour, and the warning leaves the build and the server start (so PL-13's 'no new warning' check has a clean start).
2. Links few people press, on every store: add prefetch={false} to the footer's cookies link (src/components/store-layout.tsx:498), WithdrawalLink (443) and the legal pages' links (511), and to the built footer's and the platform footer's twins (src/components/site-parts.tsx:224, 283, 287). Measured on the cart: cookies and withdraw are 4 requests and 12,125 bytes per view where the footer is in view.
3. A trial, one destination at a time, each in its own build: add export const prefetch = 'partial' to the product page (src/app/s/[store]/[market]/p/[handle]/page.tsx, under (shop)/ once PL-2 has moved it) and to the admin's orders page (src/app/admin/(gated)/[store]/orders/page.tsx), run node docs/audits/bloat-review-2026-11/scripts/measure-routes.mjs, and write down requests and bytes per page beside today's. The root layout awaits params above any Suspense (layout.tsx:105), so a store route's shared shell may hold little; the trial says how little.
4. Decide with those numbers, and write the decision in docs/decisions.md: (a) the storefront keeps per-link prefetching for the header's four tools and the menus, or moves to shells; (b) product tiles in content grids become next/link for internal addresses (keep the anchor for external links and for tracked search results), with prefetch={false} until shells are per route; (c) the admin's sidebar links below the first level (store-admin-nav.tsx:131, 195) get prefetch={false}, or the admin's segments get prefetch = 'partial'.
5. Hold the result: PL-13's after-load request budgets per page, set at what step 4 leaves.
6. Docs: docs/performance.md gets a section 'Prefetching' with the rule of step 2, the trial's table and the decision; docs/plan.md:120 is corrected to what is set.

**Done when:** next build and next start print no partialPrefetching warning, docs/performance.md holds the trial's table (requests and bytes per page, before and after, for the product page and the orders page) with the decision, and the after-load request budget of PL-13 passes at the decided figures.
