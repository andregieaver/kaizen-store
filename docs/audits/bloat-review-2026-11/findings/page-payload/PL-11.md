# PL-11 ✓ Every open admin tab asks for AI manager notices each minute, with three queries for one number

What a page sends: document, payload and requests (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P0. **Effort:** S. **Confidence:** medium. **Step:** 0.14.
- **Second check:** confirmed.
- **Where:** `src/components/admin/ai-notices.tsx:29`, `src/lib/assistant-notices.ts:13`, `src/app/admin/(gated)/(owner)/account/notices/feed/route.ts:22`, `src/app/admin/(gated)/(owner)/account/notices/feed/route.ts:32`, `src/server/assistant-notices.ts:146`, `src/server/assistant-notices.ts:173`, `src/components/admin/ai-manager-launcher.tsx:102`
- **Evidence:** useNoticeCount() fetches /admin/account/notices/feed?place=...&count=1 when the admin opens, every 60 seconds while the tab is shown (NOTICE_POLL_MS, assistant-notices.ts:13) and when it is shown again (ai-notices.tsx:29-55). In routes.json every store and platform admin page made the call after load: no-store, a 12-byte answer. Per call the route checks the session, looks the store up by its slug (route.ts:22, one query), then calls listNotices with a limit of 1 (route.ts:32), which runs the list query (assistant-notices.ts:146-157) and the unread count (173-179): three queries for one number. The poll runs whether or not anything that writes notices is on for the account.
- **Cost today:** One function call and three queries plus the session check, per minute per visible admin tab and once per page load: 60 calls and 180 queries an hour per open tab. It grows with the number of owners at work. Paid by: The server and the database, per open admin tab.
- **Saving:** By code: two of three queries per call at once. Estimate: about three quarters of the calls per open tab for owners with nothing unread.
- **Risk:** Low: a notice may show up to five minutes later for an owner whose tab has sat idle with nothing unread; it shows at once when they come back to the tab.

## The fix

1. src/app/admin/(gated)/(owner)/account/notices/feed/route.ts:31-33: when count=1, answer { unread: await unreadNotices(account.id, place) } (src/server/assistant-notices.ts:173) and do not call listNotices().
2. Skip the slug lookup: src/app/admin/(gated)/[store]/layout.tsx (the launcher at line 114-116) passes the store's id, useNoticeCount() sends it as place, and placeOf() (route.ts:18-24) returns a uuid as it is. Notices are filtered by the account's own id, so another store's id returns nothing of anyone else's. The poll is then the session check and one count.
3. src/components/admin/ai-notices.tsx:39-45: lengthen the wait while the answers are 0: 60 seconds, then 120, then 300; back to 60 when the tab is shown again, after a press on the launcher, or after an answer above 0.
4. Add a case to src/server/assistant-notices.int.test.ts: the count for a place equals listNotices().unread for the same place (so step 1 cannot drift).

**Done when:** The count=1 answer of the feed runs one statement besides the session check (three today: route.ts:22 and assistant-notices.ts:146 and 173), shown by AD-12's statement counter or by reading the route, and a visible tab with no notices asks at most 14 times in its first hour (60 today).
