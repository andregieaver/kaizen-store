# AC-11 ✓ The import guard that keeps zod and whole catalogues out of shoppers' scripts leaves the admin out

What an owner's browser loads in the admin (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** no check. **Priority:** P0. **Effort:** S. **Confidence:** high. **Step:** 1.4.
- **Second check:** confirmed.
- **Where:** `src/lib/storefront-bundle.scan.test.ts:14`, `src/lib/storefront-bundle.scan.test.ts:16`, `src/components/admin/admin-catalogues.scan.test.ts:44`, `src/components/admin/pages-table.tsx:5`, `src/lib/page-roles.ts:1`, `src/lib/custom-fields.ts:5`, `src/lib/page-modal.ts:1`, `src/lib/work-calc.ts:2`, `src/components/admin/product-editor.tsx:38`
- **Evidence:** storefront-bundle.scan.test.ts walks every visitor component's static imports and fails on zod, lib/page-content, lib/i18n and whole language modules; its header (line 14) says the admin is left out. The admin's only bundle guard matches a direct .en import in a "use client" file. Every large finding here is one small import of a helper from a large module, which a walk catches: typingIn from responsive-edit (AC-1), ROLE_COPY from page-roles (AC-2), two helpers from page-content in custom-fields.ts (AC-3), TOOL_WORDS (AC-8), work-text (AC-7), t() (AC-6). My own walk (a 30-line script, under a second over 4,156 files) found each of them, and three more of the same kind that no finding lists: page-modal.ts takes two cookie helpers from cookie-consent.ts, which also holds the cookie list in four languages (a 37,916-byte chunk on 83 admin routes); work-calc.ts takes parsePrice from product-input.ts (40 KB of schemas, reachable from client code on 85 routes); product-editor.tsx takes addressChangeWords from redirect-admin.ts (119 KB of source, a 22 KB chunk on the product editor).
- **Cost today:** Nothing at run time; each miss costs 20 KB to 1.7 MB per screen until someone measures by hand. Paid by: CI (a unit test of under a second); an owner's browser pays for each miss.
- **Saving:** Prevents the return of AC-1, AC-3, AC-6, AC-7 and AC-8 (about 0.5 MB on every screen and up to 1.7 MB on one); the three helpers named in step 3 are worth about 38 KB on 83 routes, 18 KB on 71 and 22 KB on the product editor.
- **Risk:** Low. A static walk does not follow import(), which is what is wanted (a lazy part is allowed to be large). A false alarm would be a legitimate new editor module, which is added to zone (c)'s list with a reason in the same change.
- **Already tracked:** No.

## The fix

1. Lift the walk of src/lib/storefront-bundle.scan.test.ts (resolve, typesOnly, the import pattern) into a shared helper, src/test/import-walk.ts, and keep that test's behaviour as it is.
2. Write src/components/admin/admin-bundle.scan.test.ts with four zones. (a) The shell: the client modules reached from src/app/admin/(gated)/layout.tsx, [store]/layout.tsx, platform/layout.tsx, the owner's layouts and admin-frame.tsx may not reach zod, @supabase, lib/page-content, lib/i18n, a whole language module, @tiptap, lib/admin-map, lib/owner-tools, or any file of lib/admin-messages but common and sign-in. (b) Everywhere: no module reachable from a "use client" module may import lib/admin-text, lib/work-text or lib/i18n as a value. (c) lib/page-content and @tiptap only from a named list of editor modules that may only shrink. (d) Catalogue files: the indirect import sites of AC-9 as a list that may only shrink, in place of the matcher at admin-catalogues.scan.test.ts lines 44-53.
3. Start each list with today's offenders so the test passes the day it lands; AC-1, AC-3, AC-6, AC-7, AC-8 and AC-9 each delete their entries. Put page-modal.ts to cookie-consent.ts, work-calc.ts to product-input.ts and product-editor.tsx to redirect-admin.ts on a fifth list of helpers to move out of large modules (consentCookieName and decodeConsent, parsePrice, addressChangeWords each into a small file).
