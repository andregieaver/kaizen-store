# AC-13 The notice badge asks the server every minute from every open admin tab: four database statements a time, one of them thrown away

What an owner's browser loads in the admin (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P2. **Effort:** S. **Confidence:** high. **Step:** 0.14.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `src/components/admin/ai-notices.tsx:29`, `src/components/admin/ai-notices.tsx:41`, `src/lib/assistant-notices.ts:13`, `src/components/admin/ai-manager-launcher.tsx:102`, `src/app/admin/(gated)/(owner)/account/notices/feed/route.ts:22`, `src/app/admin/(gated)/(owner)/account/notices/feed/route.ts:32`, `src/server/assistant-notices.ts:146`, `src/server/assistant-notices.ts:173`, `src/server/auth.ts:138`, `src/server/auth.ts:148`, `docs/rules/admin/ai.md:99`
- **Evidence:** useNoticeCount() asks /admin/account/notices/feed?place=...&count=1 when the admin opens, every NOTICE_POLL_MS (60,000) while the tab is visible, and when the tab is shown again. It runs in the AI manager's launcher, which is in the store's and the platform's layout, so every screen of a signed-in owner has it. The browser run shows it on all 13 store screens sampled: one GET after load, 1,731 bytes on the wire for a 12-byte answer. What one answer costs, read from the route: getAccount() verifies the token and selects the account (auth.ts line 138), and for a session without a second step calls Supabase Auth once (getUser, line 148); placeOf() selects the store by its slug (route.ts line 22); then listNotices(account.id, place, 1) (line 32) selects the newest notice joined to its store, whose rows the count answer does not use, and unreadNotices() counts. Four statements, one discarded, and up to one Auth round trip. Notices are written only by the AI manager's background work (page builds, follow-ups, plans, approvals, reports, hand-offs).
- **Cost today:** Per visible admin tab: 60 requests and 240 statements an hour, whether or not the AI manager has ever left that person a notice. Arithmetic, not a measurement: 1,000 owners with the admin visible are 1,000 function calls and 4,000 statements a minute. Paid by: The server per request and the database, and Supabase Auth for sessions without a second step; the owner's browser a little. It grows with the number of open admin tabs, not with use of notices.
- **Saving:** Estimate: about 85 to 90% fewer poll requests from an idle open tab (6 an hour, not 60) and half the statements in each.
- **Risk:** Low. A notice from scheduled work reaches the badge up to ten minutes late in a tab nobody is touching; it still shows at once on the next click or when the tab is shown again. It would be noticed as a badge that lags in the ai-manager-panel spec.
- **Already tracked:** No. The verified report listed the poll under clean because it follows open tabs; it does not follow use of notices, and its cost per answer was not counted.

## The fix

1. src/app/admin/(gated)/(owner)/account/notices/feed/route.ts line 32: in count mode call unreadNotices(account.id, place) and answer { unread }; keep listNotices() for the list. Four statements become three.
2. Let the count take the store's slug and join commerce.stores in the same statement (a second form of placeWhere in src/server/assistant-notices.ts), so a count is one statement after the account read. Three become two.
3. src/components/admin/ai-notices.tsx lines 39-51: ask on mount, when the tab is shown, and when the path changes (at most once a minute). Keep the one-minute timer only for ten minutes after recount() was called or while the count is above zero (the person is using the AI manager); otherwise ask every ten minutes. Put the two intervals beside NOTICE_POLL_MS in src/lib/assistant-notices.ts and the schedule in a pure function with a unit test.
4. docs/rules/admin/ai.md line 99: still polling, never a socket; say the cadence.

**Done when:** With the store home left open and visible for ten minutes and the AI manager untouched, the browser makes at most 2 requests to /admin/account/notices/feed (10 today), checked in a signed-in spec with a clock; and a count request runs at most 2 statements after the account read (asserted in assistant-notices.int.test.ts).
