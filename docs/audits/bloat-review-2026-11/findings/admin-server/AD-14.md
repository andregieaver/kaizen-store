- **Where:** `src/server/pages.ts:135-156`, `src/server/pages.ts:112-115`, `src/lib/page-content.ts:4305-4308`, `src/lib/page-content.ts:4317-4319`, `src/app/admin/(gated)/[store]/pages/views.tsx:66-79`, `src/app/admin/(gated)/[store]/pages/context.ts:79-110`, `src/app/admin/(gated)/[store]/pages/views.tsx:124`, `src/app/admin/(gated)/[store]/pages/views.tsx:138-139`, `src/app/admin/(gated)/[store]/pages/views.tsx:145`, `src/app/admin/(gated)/[store]/pages/views.tsx:162`, `src/app/admin/(gated)/[store]/pages/views.tsx:179-180`, `src/app/admin/(gated)/platform/pages/views.tsx:57`, `src/app/admin/(gated)/[store]/pages/actions.ts:408`, `src/app/admin/(gated)/platform/pages/actions.ts:332`, `src/app/admin/(gated)/[store]/articles/blogs/page.tsx:32`, `src/server/shopify-copy.ts:555`, `src/server/admin-api-content.ts:222`
- **Evidence:** listPages() selects draft and published, the two whole JSON documents of a page, for every page of a type, with no limit (pages.ts:136-140). In code each row is parsed twice with the full page schema (parsePageContent, a zod parse of a 4,300-line schema file) and the two results are compared with JSON.stringify to tell 'published' from 'changed' (pages.ts:112-115, page-content.ts:4317-4319). The list then shows a title, an address, a state, two dates, two flags and a thumbnail. Timed in this pass on ten real page documents from the themes (average 8.3 KB of JSON): 0.64 ms of blocking CPU per row, so 19 ms for 30 pages and 128 ms for 200 articles, with about 16.6 KB per row read from the database (3.3 MB for 200). The same view serves pages, articles, headers, footers and product layouts (views.tsx:66) and the platform's own pages (platform/pages/views.tsx:57). Five callers want only an id, a title or an address (pages/actions.ts:408, platform/pages/actions.ts:332, try/[sandbox]/actions.ts:219, shopify-copy.ts:555, articles/blogs/page.tsx:32), and the Admin API's list filters by date after reading everything (admin-api-content.ts:222). The view then awaits its other reads one after another with no Suspense, 4 to 6 by type (views.tsx:68, 76, 79, 124, then 138-139, or 145 and 162, or 179-180), and siteLayoutChoice() is read twice for headers and footers (145, 162). The first of them, storePageContext() (pages/context.ts:79-110), builds the page builder's whole context, with menu previews, every field group and their lookups in sequence, and the list uses two things from it: siteBase and the duplicate action (views.tsx:150 and 155).
- **Cost today:** Per list view: two documents per page from the database and 0.64 ms of CPU per page, growing without bound with a store's pages and above all its articles. A blog moved in from Shopify or WordPress has hundreds of posts on day one. Today's pages are the team's demo content (1,389 rows, 9.1 MB in production), so nothing shows yet. Paid by: The database (rows and bytes), the server (a synchronous parse that holds the instance), and the owner, who waits for the list.
- **Saving:** Measured per-row cost times rows: for 30 pages about 19 ms of CPU and about 500 KB of JSON less per view; for 200 articles about 128 ms and 3.3 MB. Five or more sequential waits become one, and the builder's context is no longer built for a list.
- **Risk:** Low to medium. What could break: a page shown as 'changed' when it is not, or the reverse, if the SQL comparison replaced the parsed one outright (step 2 keeps the parsed compare for the rows that differ); a title that differs for a draft that does not parse (step 3). The new integration case and blogs.spec.ts are the checks.
- **Already tracked:** no (code review FS2 and step 1.13 name customers, products, invoices and returns; pages and articles are not there)

## The fix

1. src/server/pages.ts:135-156: read the list's columns in SQL instead of the documents: id, slug, draft->>'title', draft->'thumbnail'->>'url', the two flags from coalesce(published, draft) with the schema's defaults (page-content.ts:4296-4297: true), published is not null, (published is not null and draft = published) as same, published_at, updated_at. Describe the row with col and read it through typedRows() (the rule for new reads).
2. Keep the state's exact meaning: no published document is 'draft'; same is 'published'; for the rows that differ as stored, read draft and published for those ids only (one more statement, bounded to the changed pages) and decide with stateOf() as today, because two documents can differ as stored and be equal after the schema's defaults.
3. Keep the fallback for a draft that cannot be parsed (pages.ts:117-128: the address is the title): coalesce(nullif(draft->>'title', ''), slug).
4. Add pageTitles(owner, type) returning id, slug and title only, and use it in the five callers that want no more (listed under where).
5. src/app/admin/(gated)/[store]/pages/context.ts and views.tsx:68: give the list what it uses without the builder's context: the site's base address and the duplicate action (both need only the store and the type). storePageContext() stays for the editor.
6. src/app/admin/(gated)/[store]/pages/views.tsx:66-79: run commentCounts(), scheduleChips(), runningPageJobs(), layoutUses(), listTerms(), siteLayoutChoice() (once) and the home offers in one Promise.all with the list, each only for the types that use it. The platform's view (platform/pages/views.tsx) the same.
7. Give articles a page size and the pager of code review step 1.13 (50 by updated_at desc, id), and src/server/admin-api-content.ts:222 a since filter in SQL. Add the pages and articles lists to step 1.13's list of unbounded lists in the code review, with a change-log line.
