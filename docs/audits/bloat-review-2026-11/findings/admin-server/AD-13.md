What the server does for an admin navigation (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Second check:** added by the planner, not checked a second time.
- **Where:** `src/components/admin/inventory/locations-view.tsx:92`, `src/components/admin/inventory/locations-view.tsx:115`, `src/components/admin/inventory/locations-view.tsx:128`, `src/app/admin/(gated)/[store]/inventory/locations/actions.ts:27-68`, `src/components/admin/inventory/inventory-table.tsx:139`, `src/components/admin/inventory/inventory-table.tsx:151`, `src/app/admin/(gated)/[store]/inventory/actions.ts:23`, `src/app/admin/(gated)/[store]/inventory/actions.ts:31`, `src/components/admin/passport-editor.tsx:32`, `src/app/admin/(gated)/[store]/products/[productId]/passport/actions.ts:15`, `src/components/admin/automation/rule-editor.tsx:208-209`, `src/app/admin/(gated)/[store]/settings/automation/actions.ts:30`, `src/components/admin/discount-editor.tsx:126-127`, `src/app/admin/(gated)/[store]/discounts/actions.ts:31`, `src/components/admin/campaign-editor.tsx:169-170`, `src/app/admin/(gated)/[store]/campaigns/actions.ts:30`, `src/components/admin/reminder-editor.tsx:116-117`, `node_modules/next/dist/server/web/spec-extension/revalidate.js:67-77`, `node_modules/next/dist/server/app-render/action-handler.js:926-935`
- **Evidence:** A server action that calls refresh() answers with the route already drawn again: refresh() sets pathWasRevalidated (revalidate.js:67-77), so the action handler does not skip page rendering (action-handler.js:926-935). In many client parts the code then calls router.refresh() as well, which sends a second request that renders every layout and the page once more. Counted in this pass: 90 router.refresh() calls in 50 files of src/components/admin and src/app/admin. A static pass (script in the scratch folder) resolved the action awaited just before each call and read its body: at 36 sites every candidate action already calls refresh(); 6 are mixed; at 11 the action does not refresh, so the client call is needed; 37 were not resolved (polls, fetches to route handlers, helpers), and 3 of those are doubles by hand, which makes 39. Reading both sides by hand confirmed nine: stock adjust and policy (inventory-table.tsx:139 and 151 with inventory/actions.ts:23 and 31), locations (locations-view.tsx:92, 115, 128: all 6 actions of locations/actions.ts refresh), the product passport (passport-editor.tsx:32 with passport/actions.ts:15), an automation rule, a discount and a campaign. The last three and the cart reminder do router.push(back) and then router.refresh(): three renders for one save (the editor being left, the list, the list again). No written rule or scan test says which side refreshes (rg over docs/rules and the scan tests).
- **Cost today:** One whole-route render more than needed on each of these saves, two more where an editor pushes and refreshes: the guard's 2 statements (and an Auth call for a session without two-step, AD-3), the shell (100 to 125 ms of CPU until AD-1, 6 statements until AD-4, 51 to 66 KB until AD-5) and all of the page's own reads. Stock adjustments, redirects, suppliers, imports and moving in from another shop are among them: things an owner does many times in a row. Paid by: The server and the database per save; the owner's browser, which parses the route twice; the owner, who sees the page settle twice.
- **Saving:** One whole-route render fewer per save at 39 or more save sites, two fewer on four editors. Per render saved, from the measured parts: 100 to 125 ms of CPU (until AD-1), 8 or more statements plus the page's own, and 51 to 66 KB of JSON (until AD-5). After the other fixes it is still the page's reads and the guard, once per save.
- **Risk:** Low. What could break: a screen whose action returns before its write is visible, or a list reached by router.push() that the client still holds, would show the old rows without the second fetch. Each such screen has a signed-in spec that waits for the saved value; run it per file. The static pass can be wrong where one prop name is bound to several actions (that is why 6 are 'mixed'): read those by hand.
- **Already tracked:** no (rg router.refresh over docs/rules, docs/performance.md and the scan tests: no rule, no check)

## The fix

1. Run node docs/audits/bloat-review-2026-11/scripts/sources/planner-ad/double.mjs.txt and take its 'double' lines as the work list (36 today). At each, delete the client's router.refresh() and, where nothing else uses it, the useRouter() import. The action's refresh() has already brought the new page.
2. The four editors that push and refresh (discount-editor.tsx:126-127, campaign-editor.tsx:169-170, automation/rule-editor.tsx:208-209, reminder-editor.tsx:116-117): keep router.push(back) and drop router.refresh(). The list is dynamic and is fetched when it is opened (next.config.ts sets no staleTimes). Better where the action knows the way back: let the action redirect() after saving, as deleteDiscountAction already does (discounts/actions.ts:44), which is one render in all.
3. Read the 6 'mixed' and the 37 unresolved sites by hand (the script prints them; 3 of the 37 are already known doubles: discount-editor.tsx:127, campaign-editor.tsx:170, locations-view.tsx:92). Where the awaited call is a server action that calls refresh(), delete the client call; where it is a fetch() to a route handler or an action without refresh() (the 11 'single' lines), keep it.
4. Write the rule once, in docs/rules/admin/platform.md beside the storeAction rule (line 89): the action refreshes; a client part does not call router.refresh() after a server action.
5. Hold it with a scan test, src/components/admin/router-refresh.scan.test.ts: it counts router.refresh() in src/components/admin and src/app/admin against a baseline that only falls, with a short named list of the calls that are not after an action (refresh-while.tsx, analytics/live-refresh.tsx, pack-pictures.tsx's watch, session.tsx's recovery, admin-text.tsx's language change, data/job-tracker.tsx).
6. Go file by file with the screen's spec, not by a codemod: a few screens may lean on the second fetch without meaning to.
