- **Where:** `src/server/products.ts:305-348`, `src/app/admin/(gated)/[store]/products/page.tsx:168`, `src/components/admin/products-bulk.tsx:1`, `src/server/customer-admin.ts:131-177`, `src/app/admin/(gated)/platform/stores/page.tsx:25`, `docs/audits/code-review-2026-11.md:70`, `docs/audits/code-review-2026-11.md:91`
- **Evidence:** listAdminProducts() has no limit and runs correlated sub-selects per product (picture, two variant counts, stock, title fallback, price range, and a vat_rate() call); every row is serialised to a client component. The platform's Stores list reads every store with billing. listCustomers() builds its rows from a CTE over every order of the store, grouped by email, and only then keeps 100 (line 177), so paging the result will not bound the work. (The skeptic's reading; this pass read the products page and the code review's rows.)
- **Cost today:** Per view: 6 sub-selects and a function call per product, and one pass over all of a store's orders. Today's catalogues and orders are the team's demo data, so nothing shows; the cost grows with each real store's catalogue and order history from the day it sells. Paid by: The database, and the owner's browser for the products table.
- **Saving:** Bounds the three views at a fixed page as stores grow (estimate; nothing to measure on demo data).
- **Risk:** Low. A bulk action that silently applied to the visible page only, where it used to apply to everything, would be the fault: the bulk panel must say how many it will change, as the orders list does.
- **Already tracked:** code review step 1.13 (FS2): Open; step 2.10 (FS9): Open. The customers aggregate over all orders is not written there.
