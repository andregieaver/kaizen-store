# What the server does for an admin navigation (AD)

Part of `docs/audits/bloat-review-2026-11.md`, on commit 0bd814c. Read by one reviewer, challenged by a second (who re-opened every citation, re-measured every number and applied the owner's note that the platform is not open yet) and planned by a third. A tick (✓) marks a finding the second reviewer confirmed or corrected; one the planner added has none. Each finding has a file of its own beside this one.

**In short.** All 12 findings of the audit stand (8 confirmed, 4 corrected) and this pass added three; none argues for removing, hiding or merging a feature, and none rests on a table being empty. The admin's lists, streaming and cache tags are well made: the waste is in the shell and the home screens, and it is paid per owner tab and per save, so it grows with stores and owners, not with data. Three numbers tell it: building the store menu costs 125 ms of blocking CPU on every shell render (220 permission lookups; 0.1 ms once memoised), the shell is rendered again after every save and at least 39 save sites render the whole route twice because the browser asks again, and a store Home view runs 29 to 46 statements before its first content. Before opening is the cheap time: do the menu memo (AD-1), the double redraws (AD-13), the hidden-tab polls (AD-9), the products list's unused reads (AD-7) and a statement counter so this cannot grow unseen again (AD-12) first.

## Well made, and should stay

- Orders list: keyset paging at 50 rows, a count capped at 10,000, named columns, the list behind Suspense, and a server-drawn view so its words are not sent whole (order-list.ts:176-224, orders/page.tsx:58-60).
- The store itself is read through 'use cache' with a per-store tag and an hours life (stores.ts:217-222); the admin does not re-read it per request. Both writers of currency rates refresh that tag (localization.ts:191 and 217), so rates in the cached store are safe to use.
- Guard reads are shared inside one render with React cache(): readSession, getAccount, loadMembership (auth.ts:120, 214, 354). A page and its Suspense children asking requirePermission twice cost one read.
- The member's row is read on every request on purpose (auth.ts:319-327: a security decision is never stale). Nothing here proposes caching it.
- A soft navigation between pages of one store does not render the shell again. The shell's cost is paid on hard loads, saves and refreshes only.
- The store Home streams its six secondary cards behind Suspense (drafts, today, move watch, failed alerts, analytics alerts, briefing offer). The Analytics overview gives each section its own Suspense (analytics/page.tsx:60-92).
- The AI manager's panel loads its chat and starts its conversation only when opened (ai-manager-launcher.tsx:107-127); the account menu's rows mount only while the menu is open.
- Basic and Advanced (D454) is a client switch over the menu and the hub cards only (useAdminView is read in 3 files: admin-view.tsx, section-hub-cards.tsx, store-admin-nav.tsx). No page computes a data card that Basic hides.
- No save revalidates a whole layout by path: revalidatePath is called 4 times in 2 files, each for one page. The one global tag refresh (CATALOG_TAG) is in vat-admin.ts only, for a platform-wide VAT change.
- Each admin hard load asks 24 to 46 link prefetches for the menu, but each answer measured 380 to 600 bytes of the prerendered shell (m/routes.json), so no page data rides on them. Admin routes are partial prerenders (m/build.log) and the proxy's matcher leaves out everything under /admin/ (src/proxy.ts:55-58).
- Nothing in the admin's guard writes per request in the steady state: the two-step mirror is written only on a mismatch and the break-glass note at most once in 12 hours (auth.ts:158-175). Only the store layout schedules work after a render (after() at layout.tsx:70 and 73; the one other is the hosting page).
- Only one generateMetadata runs in the admin (the root layout's favicon, from cached platform settings); pages use static metadata.
- Plan limits are memoised per instance for a minute (limits.ts:24-47). Cron health on the platform home is one statement.
- No feature in this dimension is unused code paying a running cost for nobody: every read found serves a screen. The findings are about how often and how much, never about whether a feature should exist.
