- **Where:** `src/app/admin/(gated)/[store]/settings/payments/page.tsx:49`, `src/app/admin/(gated)/[store]/settings/payments/page.tsx:56`, `src/app/admin/(gated)/[store]/settings/payments/page.tsx:61-64`, `src/app/admin/(gated)/[store]/settings/payments/page.tsx:68`, `src/app/admin/(gated)/[store]/settings/payments/page.tsx:70`, `src/app/admin/(gated)/[store]/settings/payments/page.tsx:73-74`, `src/server/settings.ts:35-52`, `src/server/connect.ts:31-39`, `src/server/connect.ts:265-275`, `src/server/payment-methods.ts:87-94`, `src/server/express-checkout.ts:172-178`, `src/server/mollie.ts:281-292`, `src/server/mollie.ts:339-346`
- **Evidence:** The one settings page traced in full. It runs 5 statements together (the provider, the Stripe accounts, the audit log's last 20 rows, the invoice setting, the method choices), then one at a time: the checkout provider, the test account (one statement and, while a Kaizen-made test account is not yet active, a call to Stripe's API awaited in the render, connect.ts:270-275), the method states, the wallet domains, and with Mollie on two more statements and then a call to Mollie's API for its methods (mollie.ts:281-292), also awaited. commerce.stripe_accounts is read by getStripeAccounts(), methodStates() and walletDomains() for different columns of the same rows, and a fourth time by ensureTestAccount(). The page has no Suspense (rg: 0). That is 9 statements in 5 waves for a Stripe store whose test account is active, and up to 13 statements and two outside API calls before anything paints.
- **Cost today:** 4 or more sequential waits and 2 to 3 repeated reads per view of Payments, and for a new store (which starts in test mode, D20) a wait on Stripe on the first visits. Every owner opens this page to go live, but rarely after. Paid by: The owner on each visit of Payments; the database; Stripe's and Mollie's API quotas.
- **Saving:** Estimate: 2 to 3 statements and 3 sequential waits per view; a new store's first paint of Payments no longer waits for Stripe.
- **Risk:** Low. The set-up result arriving a moment after the page must not hide a Stripe problem: the streamed section shows it as the page does today. Noticed by e2e/admin.spec.ts and billing.int.test.ts.

## The fix

1. src/server/connect.ts: one reader for the page, paymentAccountsFor(storeId), returning per mode the account's id, card_payments, requirements_due, method_states, wallet_domains and wallet_domains_at in one statement; build getStripeAccounts()'s shape, methodStates()'s and walletDomains()'s answers from it in the page. The three functions stay for their other callers.
2. src/app/admin/(gated)/[store]/settings/payments/page.tsx:49-73: put checkoutProviderOf(), mollieConnection() and chosenCheckoutProviders() in the first Promise.all (each depends only on the store).
3. Move the two outside calls behind Suspense: the test account's set-up result (lines 61-64) and Mollie's method list (line 74) each in a small async component with a one-line fallback, so the page paints from the database and the two answers stream in. D20's promise stays: a problem from Stripe is still shown on this page.

**Done when:** AD-12's counter shows the Payments page's database reads in 2 waves and at most 7 statements for a Stripe store with an active test account (9 in 5 waves today), and the page file has a Suspense around each outside call.
