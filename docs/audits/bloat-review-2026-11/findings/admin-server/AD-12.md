# AD-12 ✓ Nothing counts what a screen costs the server, so the Home grew to 30 statements unseen

What the server does for an admin navigation (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** no check. **Priority:** P0. **Effort:** M. **Confidence:** high. **Step:** 1.6.
- **Second check:** confirmed.
- **Where:** `src/server/control-center.ts:49-59`, `src/server/control-center.ts:290-303`, `src/db/client.ts:36-53`, `src/db/client.ts:63-80`, `docs/performance.md:139`, `docs/audits/code-review-2026-11.md:503`, `e2e/signed-in/admin-scripts.spec.ts`, `src/server/ratchet.scan.test.ts`
- **Evidence:** The admin has budgets for scripts (seven screens in admin-scripts.spec.ts) and ratchets for unchecked reads, but no count of statements or server time per screen. The skeptic's search of src and docs for a statement or query budget, a per-request counter or Server-Timing found none. control-center.ts states its own rule ('a handful of queries, never per store') in a comment and has since grown to 21 statements plus per-store reads, with nothing to notice it. The admin's speed beacon reports TTFB, which with a static shell says nothing about the data behind it. With no real traffic yet, production's statistics cannot show it either. Every statement the app sends goes through one pool made in src/db/client.ts:63-80, so one place can count them all.
- **Cost today:** No running cost of its own. It is why AD-1, AD-2, AD-6, AD-7 and AD-14 were not seen: each feature added one more read to a shared screen. Paid by: Everyone later: the owner in wait, the database in load, the team in audits like this one.
- **Saving:** No direct saving. It keeps the savings of AD-2, AD-4, AD-6, AD-7, AD-8 and AD-11, and before opening it gives the first real numbers per screen.
- **Risk:** Low. The wrapper sits on every statement, so it must add no await and must never throw; the counter must not log statement text or values. A budget that counts loaders, not the rendered page, can miss a read added straight in a page file: step 2's log line is the net for that.
- **Already tracked:** no (code review step 4.6 'Measure, then tune' is Open and is about how people use Basic and Advanced, not a statement budget)

## The fix

1. Step 1, the counter. src/db/client.ts create(): wrap the pool's query so each statement adds one to the store of an AsyncLocalStorage when one is running, and nothing otherwise. Export countStatements(run) that runs a function inside a fresh store and returns { result, statements, ms }. It counts; it never keeps a statement's text or values (D400).
2. Step 2, the log line. For renders, where the app cannot wrap the request: a per-render counter from React cache() (cache(() => ({ statements: 0, started: Date.now() }))) that the same wrapper also bumps; in src/app/admin/(gated)/layout.tsx's Gate, take the object and log one line in after(): log('info', 'admin.render', { statements, ms }) through src/server/log.ts. Outside a render cache() returns a fresh object each call, so jobs and routes are unaffected.
3. Step 3, the budget. A new src/server/admin-statements.int.test.ts runs, against the seeded store and its owner, the loaders of five screens inside countStatements(): the store shell (storeShellData of AD-4), the store Home (controlCenter for one store, getSetupProgress, demoContent), the orders list (resolveOrderList, listOrdersPage, listOrderViews, tagSuggestions), the products list for an editor, and the platform Home's five loaders. It compares each count to src/server/admin-statements.baseline.json and fails when one rises, and when one falls until the baseline is lowered, exactly as ratchet.scan.test.ts does with scripts/ratchet.mjs.
4. Step 4, the menu. The count test of AD-1 (canOpen called at most once per menu item) is the menu's budget.
5. Step 5, the rule. One paragraph in docs/performance.md beside the first-scripts budgets, and a line in CLAUDE.md's Conventions: a change that adds a read to the shell or to a home screen raises a number in the baseline and says why in its commit.
6. Order: step 1 before the other findings (they measure with it); write the baseline with today's numbers, then let each fix lower them.

**Done when:** pnpm test:int runs src/server/admin-statements.int.test.ts with five screens in its baseline, and one admin page load in a local production build writes one admin.render log line with a statements count.
