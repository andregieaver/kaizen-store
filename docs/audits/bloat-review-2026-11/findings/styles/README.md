# Styles (CS)

Part of `docs/audits/bloat-review-2026-11.md`, on commit 0bd814c. Read by one reviewer, challenged by a second (who re-opened every citation, re-measured every number and applied the owner's note that the platform is not open yet) and planned by a third. A tick (✓) marks a finding the second reviewer confirmed or corrected; one the planner added has none. Each finding has a file of its own beside this one.

**In short.** Styles are one of the leaner areas, and no finding here rests on a feature being unused. Every page of every surface loads one stylesheet of 183 KB (25.8 KB Brotli); compiling the proposed split with the project's own Tailwind gives shoppers a sheet of 130 KB (19.8 KB Brotli: 28% less raw, 22% less on the wire), leaves the admin's as it is, needs no more scan memory than today (204-212 MB against 221-223 MB), and stops admin-only and test-only edits from renaming the shoppers' file. The rest is copies: a launch theme's home page carries an estimated 45 to 71 KB of style text, of which 10.6 to 17.6 KB is one fixed breakpoint sheet repeated per row and 6.6 to 9.5 KB a second copy of the layout's sheets. The completeness check added one thing the report missed and the split depends on: the admin's form, print and editing parts are drawn on public pages with colour roles that have no value there, so the main button on Kaizena Flow's status and illegal-content report pages has no fill (seen in the built HTML); before opening is the cheap time to fix both, with no shopper's cache to disturb and a missed class found by the team.

## Refuted by the second reviewer

These were in the first reading and did not hold. They are in no step.

- **Serving the optional component CSS (menu hover, brands, gallery, header stages, table, modal) as separate files, the draft's further 3.3 KB gzip.** All six launch themes set a hover on their header menu, so menu hover is used on every page of a launch-theme store. The rest is about 2.6 KB gzip over five components and would need a file and a gate each.
- **Moving a store's layout-level CSS to an external per-store stylesheet.** On a first visit it trades about 2 KB of inline Brotli for one more render-blocking request, and inside a session the layout is not resent. Kept as a watch item for when real stores' layout CSS commonly passes about 10 KB.
- **The draft's figure that 26% of commits change every shopper's stylesheet.** 30 of 115 commits touched a className line, but only 13 (11%) added a class the tree did not already name.

## Well made, and should stay

- Hand-written CSS has almost no dead weight: 93 of 96 class names, 112 of 113 attributes and all 39 keyframes in globals.css, motion.css, admin.css and the two schemes are used by non-test code (the verified report's sample). The exceptions are four alternatives in the admin's own admin.css, under 0.3 KB.
- Every block of feature CSS (motion, brands, gallery, lightbox, menu hover, table, modal, header stages) has code that emits its attributes or classes. None is a candidate to retire; that the demo store draws none of them says nothing about use.
- Tailwind's scan is cheap since D378: 0.6 s and about 220 MB for 5,931 files. Scanning all of src is not a build cost worth chasing on its own.
- The page builder does not style with inline attributes: a store page carries 23-696 bytes of style="". Settings become hashed classes in a part sheet (src/lib/part-css.ts), which keeps owners' CSS able to win (D100). The sheet itself is compact: Meridian's 10 rows are 6.7 KB as one sheet, 1.3 KB gzip, with two @media blocks in all.
- Style generation is not paid per request: store pages are prerendered shells revalidated every 15-60 minutes, and the reads behind them are cached ('use cache' in src/server/text-styles.ts:50 and src/server/fonts.ts:159). The builder's canvas recomputes the page's part CSS on each edit in about 5.5 ms for the largest launch theme's home page: under a frame.
- Fonts are done well: one stylesheet per family from a cached route, kept for a year, cut to the EU's scripts and the builder's weights (src/app/api/fonts/css/[slug]/route.ts, docs/performance.md:61-62).
- The admin's own CSS is already a separate file that only admin pages load (21 KB, 3.5 KB Brotli). Loading both colour schemes costs 0.44 KB Brotli: not worth a second file.
- The motion script is loaded only where a page needs it (src/components/motion-support.tsx:10-20).
- The dark variant's double writing (by attribute and by the device) is 0.17 KB Brotli, and it is what lets a page be dark without scripts (D99). Leave it.
- Theme variables are small and bounded (1.4-1.8 KB per store) and owners' CSS is checked and capped at 50,000 characters a sheet (src/lib/custom-css.ts:19).
- Class names kept in stored pages are the themes' own (meridian-hero and the like in src/lib/signature/*.ts), styled by the theme's CSS, not Tailwind utilities; the four migration files hold no class attribute. So no stored content depends on Tailwind's scan, and the split of CS-1 cannot orphan it.
- Inline layout-level CSS is the right default at today's sizes: it is paid once per full page load, and an external file would add a render-blocking request to every first visit.
