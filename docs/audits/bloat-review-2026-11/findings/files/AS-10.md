# AS-10 ✓ The build's page worker runs with source maps on: about 4.7 MB of heap per MB of server code it loads, and 704 MB of maps written that no function carries

Files that ship or are stored (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** oversize. **Priority:** P0. **Effort:** S. **Confidence:** medium. **Step:** 1.20.
- **Second check:** corrected.
- **Where:** `next.config.ts:39`, `next.config.ts:79`, `node_modules/next/dist/build/index.js:408`, `node_modules/next/dist/lib/worker.js:71`, `node_modules/next/dist/docs/01-app/02-guides/memory-usage.md:122`, `node_modules/next/dist/server/config-shared.d.ts:873`, `node_modules/next/dist/server/config-shared.d.ts:1711`, `docs/build-memory.md:24`, `docs/build-memory.md:40`, `docs/build-memory.md:44`, `.next/required-server-files.json`, `a scratch script`
- **Evidence:** The second check counted 704 MB of .map files beside 205 MB of server chunks and none in any trace; I re-counted both. New in this pass, the mechanism: Next makes its one static worker (it collects page data and renders the static pages) with enableSourceMaps: config.enablePrerenderSourceMaps (build/index.js:396-408), and that starts the worker with --enable-source-maps (lib/worker.js:71). The build's settings show enablePrerenderSourceMaps true and no source map setting in next.config.ts. Node then reads the map of every chunk the worker loads. I loaded built entries in one bare node process with and without the flag: 142 entries (1,452 chunks, 106.6 MB of chunk JS): heap 290 MB without, 788 MB with; RSS 372 against 921 MB; 2.9 s against 5.1 s. 43 entries (70.5 MB): heap 214 against 543 MB. The proxy's bundle alone (13.2 MB): heap 78 against 133 MB, three runs each. That is about 4.7 MB of heap per MB of chunk each time. docs/build-memory.md says a worker holds 1.3 to 1.9 GB, the margin under Vercel's 8 GB is about 0.8 GB, and on 11 November a build was killed for memory while collecting page data with one worker. Next's memory guide names switching source maps off as a lever; build-memory.md's list of what was tried does not mention them.
- **Cost today:** On Vercel's build: several hundred MB of the page worker's memory (estimate: up to about 960 MB if it loads all 205 MB of chunks, by the measured ratio; not measured in a build), about 2 s more per 100 MB of chunks loaded, and 704 MB written to disk per build. Paid by: The build on Vercel's 8 GB machine. A build that runs out of memory fails the deploy for every store, and every push to main is a deploy.
- **Saving:** Not yet measured in a build. Measured mechanism: 4.7 MB of heap per MB of server code a worker loads (+498 MB for 107 MB of chunks). If step 3 stays: 704 MB less written per build.
- **Risk:** An error thrown while prerendering on Vercel would show positions in built chunks, not source lines; the same commit's CI build still shows source lines. Production stack traces do not change: no function carries a map today. Both settings are Vercel-only and one line to undo.
- **Already tracked:** Partly: code review step 1.8 'Give the build room' (FH10), Open. It does not name source maps.

## The fix

1. next.config.ts, in nextConfig: add ...(ON_VERCEL ? { enablePrerenderSourceMaps: false } : {}). It is a top-level key, not under experimental. CI's builds and local builds keep their maps.
2. Measure it as docs/build-memory.md did: the build with VERCEL=1 under an 8 GB cgroup cap, sampled per process, before and after. Add both peaks as rows of the table in docs/build-memory.md and name the setting under 'What changed'.
3. A second run by the same method: add turbopackSourceMaps: false to the ON_VERCEL part of experimental (next.config.ts:82). Expect no .map under .next/server (find .next/server -name '*.map' | wc -l prints 0; 704 MB less written). Keep it only if the compile's peak (5.8 GB today) or the build's time falls; record the result either way.
4. docs/audits/code-review-2026-11.md: note the result under step 1.8 in the Progress table and its change log.

**Done when:** docs/build-memory.md's table has a row for each of the two settings with the build's peak under the 8 GB cap, and the kept setting's peak is below today's 7.2 GB.

**Tests and rules that hold today's behaviour, and change with it:**

- next.config.ts:34-39: 'Each setting that reads this was measured under an 8 GB cap (docs/build-memory.md)': the new settings must be measured the same way before they stay.
- docs/build-memory.md: the lists under 'What changed' and 'Watch'.
- No test, script or CI step reads a source map (rg over src, e2e, scripts and .github). scripts/await-deploy.mjs and scripts/next-build.mjs are not affected.
- CLAUDE.md, Commands: the sentence on Vercel's build (one worker, no Turbopack cache) gains 'no source maps' if the setting stays.
