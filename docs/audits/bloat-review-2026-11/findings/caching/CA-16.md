# CA-16 Nothing holds what is static: one cookie read in a shared part can move every store page to per-request, and no check would say so

Caching and rendering (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** no check. **Priority:** P0. **Effort:** S. **Confidence:** high. **Step:** 1.11.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `.next/prerender-manifest.json`, `e2e/performance.spec.ts:10`, `scripts/ratchet.mjs`, `src/server/store-writers.scan.test.ts:1`, `.github/workflows/ci.yml:152`, `docs/performance.md`, `src/app/s/[store]/[market]/layout.tsx:201`
- **Evidence:** Searched in this pass: no test or script in e2e, scripts, src or .github reads .next/prerender-manifest.json, x-nextjs-cache or a page's compute mode (rg: nothing). The 10 e2e assertions on Cache-Control all hold no-store or immutable; none holds that a public page stays cacheable. e2e/performance.spec.ts holds first scripts by bytes for 8 routes and page weight, largest picture and first byte for 2 store routes (lines 124-127); it counts no requests and does not know whether a page came from the cache. docs/performance.md, docs/build-memory.md and docs/capacity.md do not say which routes are static or what makes a page per-request (rg prerender, static shell: one unrelated line). One scan test holds a tag refresh (writers of commerce.stores). Yet the state is easy to read from a build: this pass counted 508 static and 262 resuming routes, the holes in each shell, each page's tags and its revalidate period with a few lines of node. And it is easy to lose: the store layout shows how one cart cookie and one header read in a shared part made 148 routes per-request (CA-1), one tag made every store depend on every other (CA-11), and two reads on the default profile set a page's period to 15 minutes (CA-10).
- **Cost today:** No running cost by itself. It is why the costs of CA-1, CA-4, CA-5, CA-10, CA-11 and CA-17 grew unseen, and why a fix to any of them can be undone by the next change without a red check. Paid by: Every later change: the server per request and shoppers, once a regression ships; an agent's session, to find it again.
- **Saving:** None directly. It holds the gains of CA-1, CA-10, CA-11 and CA-15, and turns the next silent move from static to per-request into a red check.
- **Risk:** A baseline that changes with the demo content would fail for no reason: keep to counts and modes, not bytes. A change that rightly adds a hole must lower or raise the baseline in the same change, which is the point. Low.
- **Already tracked:** no. The code review's ratchet (1.2, 1.3) counts unchecked reads and writes, not render modes.

## The fix

1. New script scripts/render-modes.mjs, run after a build. For a named list of routes it reads .next/prerender-manifest.json and each route's .html and .meta under .next/server/app and records: compute (static, resuming, blocking); holes (templates B:n without a $RC completion); the tags in x-next-cache-tags that name no store, owner or route (catalog and ai-providers on the demo home today); initialRevalidateSeconds; whether <title> and og:title stand before </head>. It also records the totals by area (508 static, 262 resuming of 772; 137 patterns without a fallback).
2. Baseline scripts/render-modes.baseline.json with about twelve routes: /, /docs, one docs article, /themes, /s/demo/no, /s/demo/no/om-oss, one blog article, /s/demo/no/products, one category, one product, /s/demo/no/search, /s/demo/no/cart. The script fails when a route's compute gets worse, its holes rise, a tag that names no store appears, its revalidate falls, or a public page loses its title in the head. Like scripts/ratchet.mjs it also fails when a number got better until --write lowers the baseline, so gains are recorded.
3. .github/workflows/ci.yml, job e2e: after 'pnpm build' (line 152) add a step 'node scripts/render-modes.mjs'. No second build, a few seconds.
4. e2e/performance.spec.ts: add request budgets beside the byte budgets: prefetch requests in the 3 s after load for the store home, a built page, the cart and one admin screen (11, 34, 42 and 32 today; set each to today's number and lower it with CA-4, CA-5 and SC-1), and requests in the 3 s after one Add to cart (16 today; CA-17).
5. docs/performance.md: a section 'What is static', with the table of route kinds and what makes each per-request (the cart cookie, the country header, searchParams, stock, sign-in, a crawler's user agent), and the rule: a new cookies(), headers() or connection() in a layout or a shared part moves every page under it to per-request, and the check will say so.
6. CLAUDE.md, Conventions: one line naming the script and the baseline, as ratchet.scan.test.ts is named there.

**Done when:** node scripts/render-modes.mjs passes on CI's build, and a trial change that adds one cookies() read to the store's footer makes it fail, naming /s/demo/no and its holes going from 3 to 4.
