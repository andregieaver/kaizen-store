# CA-11 ✓ One store owner saving their AI key marks every page of every store stale

Caching and rendering (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** oversize. **Priority:** P0. **Effort:** S. **Confidence:** high. **Step:** 0.16.
- **Second check:** confirmed.
- **Where:** `src/server/ai.ts:242`, `src/server/chat-agent.ts:138`, `src/server/docs-guide-settings.ts:137`, `src/app/admin/(gated)/[store]/settings/ai/actions.ts:34`, `src/app/admin/(gated)/[store]/settings/ai/actions.ts:50`, `src/app/admin/(gated)/platform/ai/actions.ts:52`, `src/app/admin/(gated)/platform/ai/actions.ts:66`, `.next/server/app/s/demo/no.meta`
- **Evidence:** Opened in this pass. chatWidgetFor() (chat-agent.ts:135-138) tags itself with chatTag(storeId) and the global AI_TAG ('ai-providers', ai.ts:242), and the chat widget is in every site layout. The demo home's .meta lists ai-providers among its tags, and so does Kaizena Flow's front page; the verified report counted the tag on 319 of 1,316 prerendered .meta files. A store's own save or removal of its AI settings calls updateTag(AI_TAG) (settings/ai/actions.ts:34 and :50); the platform's actions do the same (platform/ai/actions.ts:52 and :66). rg finds no other writer of ai_providers outside src/server/ai.ts.
- **Cost today:** One owner's save marks every page of every store and Kaizena Flow's site stale; each is rendered again on its next visit. With many stores this happens whenever any one of them touches its AI settings. How often owners do that is not known. Paid by: The server and the database; the next visitor of every other store.
- **Saving:** A store's AI save refreshes 1 store instead of every store and the platform's site.
- **Risk:** Low. chatWidgetFor must carry both tags, since a store may use the platform's key; a store that only carried its own tag would miss the platform switching AI off. Noticed by the chat specs.
- **Already tracked:** no. Step 3.10 (FF3, Open) covers the catalogue tag only.

## The fix

1. src/server/ai.ts:242: beside AI_TAG add export const aiTag = (storeId: string) => 'ai-providers:' + storeId. AI_TAG stays the platform provider's tag.
2. src/server/chat-agent.ts:138: cacheTag(chatTag(storeId), AI_TAG, and aiTag(storeId) when storeId is not null). A store may run on the platform's key, so it keeps both.
3. src/app/admin/(gated)/[store]/settings/ai/actions.ts:34 and :50: updateTag(aiTag(owner.store.id)) in place of updateTag(AI_TAG). The platform's two calls (platform/ai/actions.ts:52, :66) stay on AI_TAG. docs-guide-settings.ts:137 reads the platform's provider and stays on AI_TAG.
4. Better still, move the refresh into saveAiSettings() and removeAiSettings() in src/server/ai.ts with refreshTag() (src/server/refresh.ts:10), so a new caller cannot forget it: refreshTag(storeId ? aiTag(storeId) : AI_TAG).
5. A unit test for aiTag and a source-scan line: no file under src/app/admin/(gated)/[store] names AI_TAG.

**Done when:** rg -n 'AI_TAG' 'src/app/admin/(gated)/[store]' returns nothing (3 lines today: the import and 2 updateTag calls), the new scan line passes, and after saving a store's AI settings on a local build the other store's pages still answer from the cache.

**Tests and rules that hold today's behaviour, and change with it:**

- src/server/chat-ai-use.int.test.ts calls chatWidgetFor(); must pass unchanged.
- The signed-in e2e spec of Settings, AI (rg -l 'settings/ai' e2e): saving a store's own key must show the chat widget on that store's next page load.
- Run the agents' safety eval only if a prompt changes; it does not here (CLAUDE.md, AI features).
- No written rule names the tag. Step 3.10 (FF3, Open) of the code review covers the catalogue tag only.

**Notes:** A tag that is too wide, and it gets worse with every store added. Cheapest to fix before opening. CA-16's baseline lists the tags on a store page that name no store, so the next global tag is seen when it appears.
