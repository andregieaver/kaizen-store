- **Cost today:** After each deploy: the first visit to any page of any store but the demo is a blocking render with 25 or more database reads (count from the demo home; time not measured), and every instance's cached reads start empty. Each deploy also rebuilds 772 prerendered routes (1,426 pages; 263 s here with the type check). Today's cold runs measure an idle platform, not load. Paid by: Shoppers of real stores (first view after a deploy), the database, the build.
- **Saving:** Not measured. Each deploy skipped saves one Vercel build and keeps every store's built pages and every instance's cached reads alive until the next. With 80 deployable commits in two days, many arrive in bursts. It also stops an earlier run from deploying a later commit before that commit's own gate has passed.
- **Risk:** D5 says a push to main deploys, and before opening that speed is the point: with the skip, a commit pushed just before another waits for the later one's gate (minutes), and if the later gate fails neither is deployed until it is fixed, which is what the gate is for. A mistake in the workflow could leave a commit undeployed: noticed by /api/health not reporting it and by the run ending without the wait step. Nothing changes for a push with a migration.
- **Already tracked:** Partly. Step 1.8 (FH10, Open) of docs/audits/code-review-2026-11.md covers the build's memory and deploying what was checked; step 0.2 (FH1, In progress) the deploy gate. Neither covers what a deploy does to the caches.

## The fix

1. The owner's choice, for when stores are open: keep one deploy per push (today), or let a run skip its deploy when a newer commit is already on main. The steps below assume the second.
2. .github/workflows/ci.yml, job pending (no migration): the step 'Is a migration pending at the head of main by now?' (line 310) already fetches the head. Add a step after it that compares git rev-parse FETCH_HEAD with GITHUB_SHA; when they differ, set superseded=true and skip the deploy-hook step (line 317) and the wait (line 326). The newer push's own run deploys the head after its own gate. Do not skip in the release job: a run that applied a migration deploys, as now.
3. scripts/await-deploy.mjs already accepts a later deployment that includes the commit; a skipped run prints that the head's run deploys it, and ends green.
4. Do not move reads to 'use cache: remote' or unstable_cache now. Remote entries do not survive a deploy and add a network lookup per read (Next's table: persists across deploys, No). unstable_cache does persist across deploys (use-cache.md:261) but hands values written by old code to new code, which at this deploy pace risks an old-shaped Store meeting a new build. Revisit after opening with a measured hit rate for loadStore (stores.ts:216) and the platform's loadSettings.
5. Write what 'cached' means beside the Catalogue reads rule in docs/rules/storefront.md:112 and in docs/performance.md: a 'use cache' result lives in one instance's memory and one deployment; a built page lives until the next deployment; only the template store is built ahead, so the first view of any other store's page after a deploy is a full render. New code must not lean on a cached read being warm.
6. After opening, count blocking first views per deploy in Vercel's logs and decide then between building the busiest stores ahead (generateStaticParams) and CA-7's shells.
