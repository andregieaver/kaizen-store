# CA-15 Bing, Google's shop and ads crawlers and every link preview get a full render of every page, static ones included

Caching and rendering (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P1. **Effort:** S. **Confidence:** medium. **Step:** 2.2.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `next.config.ts:41`, `node_modules/next/dist/build/index.js:2046`, `node_modules/next/dist/shared/lib/router/utils/html-bots.js:15`, `node_modules/next/dist/docs/01-app/02-guides/streaming.md:681`, `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/htmlLimitedBots.md`, `node_modules/next/dist/docs/01-app/01-getting-started/08-caching.md:610`, `.next/prerender-manifest.json`, `src/lib/experiments.ts`
- **Evidence:** Found and measured in this pass. With Cache Components, Next skips the prerendered page for user agents on its 'HTML-limited bots' list and renders the page per request (streaming.md:681-685: such bots 'skip the prerendered shell and render the page dynamically so metadata can be placed in the head'). The build writes the rule into every app page's entry in .next/prerender-manifest.json (experimentalBypassFor, a user-agent matcher; build/index.js:2046-2075: 'For PPR routes, bypass the shell … and produce a dynamic render'), static pages included: /docs has it. Measured on the local production server: with a browser's user agent / and /docs answer x-nextjs-cache HIT, s-maxage=3600; with Bingbot's they answer Cache-Control private, no-cache, no-store and no HIT. The default list (html-bots.js:15), tested with node against 16 user agents: it matches Bingbot, Storebot-Google (Google's shopping crawler), AdsBot-Google, Google-InspectionTool, facebookexternalhit, facebookcatalog (Meta's catalogue crawler), Applebot, Yandex and Slackbot; it does not match Googlebot, GPTBot or ClaudeBot, which get what a browser gets. next.config.ts does not set htmlLimitedBots. The reason for the bypass does not hold here: 386 of 388 prerendered public pages already have <title> before </head> in the static file (the two others are the docs search pages), and none of the 68 generateMetadata functions outside the admin takes searchParams. A render made for a bot is not kept, so a crawler's visit does not warm the page for the next person.
- **Cost today:** One full page render per crawler request, on a mostly cold instance, with every cached read the page uses (25 on the demo home) asked of the database; also for the 508 pages a person gets from the cache. Volume in production is not known (not queried in this review). It grows with stores, products and feeds: the shopping and catalogue crawlers visit every product a feed lists. Before opening, crawlers are a large share of the little traffic there is, which fits production's counts of 'cached' reads that still ran. Paid by: The server per crawler request; the database.
- **Saving:** Per crawler request: a full render becomes a cache hit on static pages and a resume on the others, and a page first seen by a crawler is kept for the next person. Total not known until step 1 is measured.
- **Risk:** What a no-script crawler reads changes place: parts that stream (a product's stock and structured data, a filtered listing) arrive at the end of the document in hidden containers instead of in place. Googlebot already reads stores this way (it is not on the list), which bounds the risk, but Bing and the feed crawlers are a business matter: check them after the change (step 6) and put a crawler back on the list if its tool shows a missing price or availability. A public page later written with metadata that reads the request would lose its title for crawlers taken off the list: CA-16's check notices.

## The fix

1. Measure first, outside this review: in Vercel's logs, count page-route function runs over 7 days whose user agent matches Next's default list (html-bots.js:15) against all page-route runs. If the share is small after opening, stop here.
2. Hold the property that makes the bypass unnecessary: CA-16's script checks that every prerendered public page has <title> and og:title before </head> in its static file (386 of 388 today; list the docs search pages as the exception).
3. next.config.ts, beside cacheComponents: add htmlLimitedBots with a pattern that keeps only the link-preview fetchers, which never run scripts and come once per shared link: /facebookexternalhit|Twitterbot|LinkedInBot|Slackbot|Discordbot|WhatsApp|SkypeUriPreview|redditbot|quora link preview|vkShare|tumblr|bitlybot/i. The config replaces Next's list (htmlLimitedBots.md), so Bing, Yandex, Baidu, Applebot, DuckDuckBot, every *-Google and Google-* fetcher and facebookcatalog then get what Googlebot already gets: the static file, or the shell and the stream. A comment says why.
4. Check after a build: experimentalBypassFor in .next/prerender-manifest.json carries the new pattern, and curl -A 'bingbot' on pnpm start gets x-nextjs-cache: HIT for / and /docs.
5. New e2e test (request API, no scripts, Bingbot's user agent): the demo home, a product page, a category page and a blog article each hold title, description, canonical, og:title, the product's name and price, and the product's JSON-LD somewhere in the HTML.
6. After the deploy, look at Bing Webmaster Tools' URL inspection and Google's Rich Results Test (it fetches as Google-InspectionTool) for one product page; they should now show what Googlebot reads.

**Done when:** On pnpm start, curl -sD - -A 'Mozilla/5.0 (compatible; bingbot/2.0)' http://localhost:3000/docs shows x-nextjs-cache: HIT (private, no-cache, no-store today), and the new no-script crawler test passes.

**Tests and rules that hold today's behaviour, and change with it:**

- e2e/smoke.spec.ts and the SEO specs (rg -l 'canonical|ld\+json' e2e) read pages as a browser; the new test reads them as a crawler without scripts.
- The app's own bot rule (isBot() in src/lib/experiments.ts, used by the country hint, A/B tests and visit counting) is separate and stays.
- docs/rules/storefront.md:590-593: a product's stock and add-to-cart stream in and need JavaScript; a no-script crawler finds them at the end of the document in hidden containers, as Googlebot does today. Write that sentence there.
- docs/performance.md: add the config and its reason. No existing rule or plan names htmlLimitedBots (rg in docs: nothing).

**Comes after:** CA-16 (the title-in-head check); CA-1 (makes home, built and blog pages whole static files, so a crawler gets complete HTML with nothing streamed)
