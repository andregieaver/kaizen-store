# CA-17 One Add to cart redraws the whole page and re-fetches every prefetched link, to change one number

Caching and rendering (`README.md` beside this file), part of `docs/audits/bloat-review-2026-11.md`.

- **Kind:** eager. **Priority:** P1. **Effort:** S. **Confidence:** high. **Step:** 2.4.
- **Second check:** added by the planner, not checked a second time.
- **Where:** `src/app/s/[store]/[market]/cart/actions.ts:93`, `src/app/s/[store]/[market]/cart/actions.ts:139`, `src/components/cart-drawer.tsx:126`, `src/components/add-to-cart.tsx:64`, `src/components/product-bar.tsx:85`, `src/components/cart-link.tsx:26`, `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cacheLife.md:258`, `docs/rules/storefront.md:599`, `docs/audits/bloat-review-2026-11/scripts/sources/ca-plan/afteradd.mjs.txt`
- **Evidence:** Measured in this pass on the local production build, phone size, /s/demo/no/p/demo-keramikkopp: in the 4 s after one press of Add to cart the browser made 16 requests, 193,042 bytes decoded. The action's answer was 81,709 bytes: addToCart ends with refresh() (cart/actions.ts:139), so the server draws the whole page again and sends its payload. Then 15 prefetch requests, 111,333 bytes, for links the page had already prefetched before the press (12 requests then): Next's doc says a Server Action that calls refresh 'immediately clears the entire client cache' (cacheLife.md:258). 62,294 of those bytes are the cart page, prefetched in 4 requests now that there is a cart. Each of the 15 also passes the proxy. On this page the only thing drawn from the cart is the count in the header's and the bar's cart link (cart-link.tsx:26); a product's stock is read in its own per-request hole and is held only at checkout (rule, storefront.md:598). The written rule says cart mutations 'are server actions that call refresh()' (storefront.md:599).
- **Cost today:** Per Add to cart from a product page or a tile: one page render in the action (81.7 KB answer on the demo product) and about 15 more requests, each a proxy run and some a render. It grows with shoppers, on the path to payment. Paid by: The shopper's browser (phone data, a busy moment right after the press); the server per request.
- **Saving:** Measured ceiling per Add to cart on the demo product page: 15 of 16 requests and about 190 of 193 KB decoded; one page render and 15 proxy runs fewer.
- **Risk:** Something else on an adding page that was quietly kept fresh by the refresh would go stale after an add (a 'you have 2 in your cart' line, a quantity cap shown on the page): step 2 looks for it and the e2e specs for stays, bookings and quantity rules notice. Low once CA-1 is in.
- **Already tracked:** no. AD-13 in the admin-data dimension is the admin's twin (saves that draw the route twice).

## The fix

1. After CA-1: addToCart already returns the new count and useOpenCartAfterAdd sets it in the browser (CA-1 step 6). Remove refresh() from addToCart (src/app/s/[store]/[market]/cart/actions.ts:139). Without refresh, updateTag or revalidateTag the action answers only its return value and the client cache is kept.
2. Check what else the adding pages draw from the cart: rg -n 'getCart\(|getCartCount\(|readCartId\(' src/components src/app/s --glob '!**/cart/**' --glob '!**/checkout/**'. Anything found on a product page, a listing or a built page either takes its value from the action's answer or keeps a refresh for that page only.
3. Keep refresh() in updateCartLine and the cart's other actions (cart/actions.ts:145-150 and below): the cart page and the drawer draw themselves from the server, and the drawer opened after an add is a navigation that renders fresh.
4. e2e/performance.spec.ts (CA-16 step 4): after one Add to cart on /s/demo/no/p/demo-keramikkopp, in 3 s: one POST whose answer is under 5 KB and no request that carries next-router-prefetch.
5. docs/rules/storefront.md:599: 'Mutations are server actions that call refresh() where the page draws the cart (the cart page and the drawer); adding from another page returns the new count instead'.

**Done when:** The new test in e2e/performance.spec.ts passes: after one Add to cart on the demo product page the browser makes 1 request in 3 s with an answer under 5 KB (16 requests and 193,042 decoded bytes today), and the cart link reads 'Handlekurv (1)'.

**Tests and rules that hold today's behaviour, and change with it:**

- The e2e assertions on the cart link's name after an add (cart.spec.ts:38, shop-components.spec.ts:47 and 129 for tiles, stays.spec.ts:152 and the bookings specs for the date pickers, campaigns.spec.ts, discounts.spec.ts:23, recommendations.spec.ts:72 and 100) must pass unchanged: they are the hold that the count still moves.
- e2e specs that add and then open the drawer on a phone (cart.spec.ts, navigation.spec.ts:57): the drawer must show the new line.
- Rule to reword: docs/rules/storefront.md:599 (cart mutations call refresh()).
- checkout-kinds.int.test.ts holds cart totals against what placeOrder() charges; untouched.

**Comes after:** CA-1 (the count must be drawn in the browser first)

It only becomes removable once CA-1 has moved the count into the browser, so it is a second gain from the same structural change.
