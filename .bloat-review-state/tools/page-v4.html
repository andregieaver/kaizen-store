Review · 11 November 2026 · commit 0bd814c

Is Kaizena Flow bloated?

Yes, but not where bloat usually hides. The code itself is tidy: no file is unreachable, one export in a hundred is unused and one line in a hundred is a copy. The weight is in what gets loaded and run without need. A shopper's browser loads scripts of which more than half never run. Every server function carries the same ten megabytes, whatever its job. A feature costs the same whether or not a store uses it. And about 37,000 scheduled runs a day look for work that is almost never there.

The platform is not open yet. The 60 stores are the team's own demo and test stores, so an unused feature or an empty table is expected and is not a finding. What counts is what a feature costs a store that does not use it, and that grows with every store that signs up. The full review and its 38-step plan are in the repository at docs/audits/bloat-review-2026-11.md. The second reviewers are running now; 32 of 171 findings have had their second check so far, among them every one behind the plan's first phase.

Measured in a browser

More than half of the script a page loads never runs

Each page of the production build was opened once in a fresh browser, left alone until it went quiet, and asked which bytes of its scripts had executed.

An empty cart loads 938 KB of script. A third of it runs. Every storefront page loads between 0.8 and 1.1 MB, with 54 to 70% untouched when the page is idle.

Kaizena Flow's own front page is heavier than a store's. It loads 1.17 MB and runs 23% of it.

Every admin screen starts at 1.4 MB. The page builder loads 3.8 MB. The admin's home still carries 299 KB of interface text, 113 KB of validation code and about 225 KB of database client that it uses only to sign in.

Measured in a browser

Two thirds of every document is the page sent a second time

A page arrives as markup, then again as data so the browser can wake its interactive parts. That second copy should be small. Here it is the larger part.

An empty cart's document is 104 KB, of which 74 KB is data for the browser. There is nothing in the cart.

The page builder's document is 572 KB and the product editor's 416 KB, before a single script is counted.

Measured in the build

Every server function carries almost the whole application

Next's bundle analyzer lists the source modules behind each route. A route with a small job should load a small set. Only the health check does.

The visit beacon, called on every page view, loads 1,890 modules. Among them are the admin's whole interface text, the AI manager's tools and the full database schema. The health check shows what a lean route looks like: 308.

Another 34 MB of files travel beside every function: a 13 MB product taxonomy in four languages and a 19 MB image library, whether the route reads them or not.

Read from production

Half the database is waiting for opening day

From Postgres's own counters, running since 25 August. No personal data was read.

245 of 486 tables have never held a row. Before opening that is expected, and it says nothing about whether a feature is wanted. It does show which work is done for nobody: every job, query and AI tool tied to those tables runs today as if they were full.

The orders table has 34 indexes for 102 orders. With tables this small the database often skips an index, so "never scanned" overstates a little; each one is still updated on every write.

The verdict

Four causes explain most of the 171 findings

A few imports tie everything to everything

One helper imported through a heavy module, one catalogue object that 602 files import, one schema handed to a client that never reads it. Every route pays for all of it.

Work is found by asking, not by being told

Routes woken every minute to look, pages read whole to find a title, the same store slug asked for 560,000 times.

An idle feature is not free

A feature costs the same whether or not a store uses it: its job runs, its tools go to the AI, its code loads. Little for one store; it multiplies with every store that signs up.

Nothing weighs a change

The storefront's first scripts have a budget, and the storefront is the leanest part. Nothing else has one. 21 findings are this one finding.

The goal: an A in every area

The plan is done when every area is an A, not when its steps are ticked. An A means nothing in the area is loaded, fetched, run or shown without need, and a test or a production figure holds each measure so it cannot slip back unseen. A grade is raised only for fixes seen working in production.

Nothing is slow or broken today: the platform is not open, the database is idle and pages answer quickly. What is at stake at opening is that each cause grows with every store, every visit and every feature. Before opening is the cheapest time to remove them: there is no real data to move and nobody to disturb.

The plan

Five phases, 38 steps, one goal: an A in every area

Each step names the findings it closes and a check that says when it is done. The first phase is small, safe and can be measured from production the day after.

  1. Phase 0 · 12 steps, 9 small

    Stop the work done for nobody

    • Cut the two import hubs 1,890 → 639 modules
    • Wake the per-minute routes only when work waits 12,960 → under 1,500 calls a day
    • Give each job its own period, skip unused features 24,192 → under 9,000 runs a day
    • Prune the scheduler's log 731 → under 200 MB
    • Read one page, not all of them the costliest app query
    • Let the store's index serve the hottest reads 1.1 M full scans
    • Stop asking for what does not change 560,000 slug lookups
    • Stop prefetching what nobody opens cart: 42 → under 15 requests
    • Take three stray imports off every admin screen 1.28 → under 0.8 MB
    • Load the image library on use · end the prefetch loop · let the CDN keep shared answers
  2. Phase 1 · 6 steps

    Budgets, so it stays removed

    • The measurements become commands
    • A budget for what a function loads, for every route's scripts and document, for database questions per page and per round of jobs, for an AI call, for the standing rules
    • A budget for the surface: a new page, table, job or AI tool says who asked for it and what switch it sits behind
  3. Phase 2 · 10 steps

    Load on demand

    • Give each area its own words 2.9 MB off every non-admin route
    • Serve store pages from their static shell home document 135 → under 60 KB, no function run
    • A product view asks for what changes per view 18 → 3 questions
    • Editors load when they are drawn builder 3.3 → under 2.2 MB
    • A lighter admin shell and home 30 → 10 questions
    • A smaller AI manager round 160,000 → under 60,000 characters
    • Caches that outlive a deploy · the remaining import hubs · jobs that find work without loading it · styles and parts per route
  4. Phase 3 · 5 steps · your decisions

    Cost follows use, and one of each

    • A feature costs nothing until a store uses it: no job, no code, no AI tool
    • One Kaizena Flow site, not two
    • One way to model the platform, now that it has a store of its own
    • One engine for one job: order rules and Workflows, campaigns and discount codes, four reward ledgers
    • Decide what opens on day one: the developer platform's public handlers
  5. Phase 4 · 5 steps

    Tidy, and finish the review

    • The database's loose ends, including a leftover schema of 34 tables
    • Families with one core each · unused code by tier · written rules a session can afford
    • Audit the 11 areas that were not, and give the 139 unchecked findings their second look
Waiting for you

Ten questions only the owner can answer

  1. Now that Kaizena Flow has a store of its own, may a store feature serve the platform through it, with a twin built only where there is no store form?
  2. Which feature groups should a new store start with switched on? A product choice, not a saving.
  3. May the old Kaizena Flow pages without a store be removed, now that the store serves the site?
  4. For each pair of overlapping engines, which stays? Before opening, no data needs moving.
  5. Do the developer platform's public handlers open on day one, or behind a switch until someone asks?
  6. May a new table, job or AI tool have to name the gate that keeps it free for stores that do not use it?
  7. May pushes share a deploy, so cached pages live longer?
  8. May CLAUDE.md shrink to a small core with rules loaded by path?
  9. May an AI manager round start with the core tools and load the rest on need?
  10. Should this plan get a pointer in CLAUDE.md, as the code review has?
