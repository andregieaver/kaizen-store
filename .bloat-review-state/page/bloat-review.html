Review · 11 and 12 November 2026 · commit 0bd814c

Is Kaizena Flow bloated?

Not in what it is. In how it loads, asks and checks. The platform is carefully built and not open yet: 0.35% of the code is dead, 1% is a copy, and a feature a store does not use costs it close to nothing. The waste has five causes, and almost all of it is cheap to remove before the doors open. The plan's goal is an A in every area.

25 areas of the system were each read by one reviewer, challenged by a second and planned by a third: 353 findings stand and 22 claims were refuted, several of them this review's own first figures. A panel then set each area's bar for an A in numbers, wove one plan and closed every gap its challengers found: 156 steps, ready to be carried out and not started. The full review is in the repository at docs/audits/bloat-review-2026-11.md.

The verdict, and the goal

5 areas are a D today, 8 a C, none an A. The plan takes every one to an A.

An A means nothing in the area is loaded, fetched, run or shown without need, beyond a small stated tolerance, and a test or a production figure holds each number so it cannot slip back unseen. No area is an A today, the tidy ones included, because almost no number is held by a check. A grade is raised only for fixes seen working in production.

Why

Five causes explain most of the 353 findings

One import cycle ties the server together

229 server modules import each other in a ring, so 559 of 562 pages and the proxy each load the same 10 to 11 MB whatever their job. A few dozen import changes cure it. No feature is removed.

Pages are drawn and sent more often than needed

Every store page view runs a function to place two cart badges. The layout is sent twice in every page. A visitor who does nothing causes 11 to 50 prefetches.

Every admin screen loads twice the script it needs

1.16 MB at the median, where about 0.6 MB will do. Three stray imports put a database client and a validation library on every screen.

Work is found by asking, data fetched whole

13,250 scheduled calls a day find almost nothing. Finding one page reads every page of the store. A product view asks the database 18 times where one answer changes.

Nothing holds the numbers

43 findings are the same finding: no check would notice this growing. The one place with a budget, the storefront's first scripts, is the leanest place in the product.

Nothing is slow or broken today: the platform is not open, the database is idle and pages answer quickly. What is at stake at opening is that these causes grow with every store, page, product, order and visit. Before opening is the cheapest time to remove them: there is no real data to move and nobody to disturb.

Measured in the build

Almost every route carries the whole server

Next's bundle analyzer lists the source modules behind each route. A route with a small job should load a small set. Only the health check does. On the review's machine a route inside the cycle takes about 1 s and 70 to 80 MB to start cold, against 0.16 s and 14 MB outside it.

The visit beacon, called on every page view, loads 1,890 modules. It imports one ten-line check through the chat module, which brings the chat, the AI layer and the support desk with it.

The trial closed one of two doors. The reviewers confirmed the beacon's saving and found the admin reaches the same code through two files of its own. Cutting the cycle itself is step by step in phase 0.

Measured in a browser

More than half of the script a page loads has not run when the page is idle

Each page of the production build was opened once in a fresh browser, left alone until it went quiet, and asked which bytes of its scripts had executed.

A shopper's page is the lean part. Its first scripts are 680 KB, of which 447 KB is the framework itself; the store's own code is about 80 KB compressed.

The admin is where the weight is. The median of 432 signed-in screens is 1.16 MB. Seven small import changes take it to about 0.6 MB in a simulation on the built files.

Kaizena Flow's own front page fetches 437 KB of admin scripts that a visitor cannot use.

Measured in a browser

Two thirds of every document is the page sent a second time

A page arrives as markup, then again as data so the browser can wake its interactive parts. On a store page that second copy is made by a function on every view, to place two cart badges and a country hint, and it carries the whole layout twice.

On the demo store's home page 98 of 138 KB comes from that function. Served from its static shell, the page would need no function run for a visitor without a cart.

The product editor hands the browser 238 KB of interface text and its parts read 79 KB of it.
